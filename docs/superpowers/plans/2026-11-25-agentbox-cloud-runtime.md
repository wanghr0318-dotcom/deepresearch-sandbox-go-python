# AgentBox 自托管推理与跨节点恢复实施方案 v0.1

> 实施者按 Superpowers executing-plans 逐项执行，使用复选框追踪。本文是 2026-11-25 的设计初稿；以下指标均为验收要求。

**目标**　在腾讯云上让自托管模型修复真实仓库任务，执行节点失联后从一致的恢复点续跑，并用同一批任务查明扩容的吞吐和成本收益。

**架构**　CVM A 承担单控制面、PostgreSQL、Gateway 与首个 K8s 执行节点。Agent Pod 经绑定到 attempt 的入口调用 Go Gateway；文件工具操作 manifest/blob，shell 工具申请独立执行 Pod。独立 GPU 云服务器 提供 SGLang 私网端点，CVM B 提供第二个执行节点，COS 保存跨节点可读的不可变产物。

**技术栈**　Go 管 Provider、节点入口、调度和恢复；Python 管 Agent、独立验证器及回放；PostgreSQL 管租约与提交；Shell/YAML 固定部署。单 GPU、单控制面，两台独立 CPU 云服务器 是正式实验边界。

## 基线与全局约束

GitHub main 的 7153fc531c8af570c4b96ffdda27fcc9ee7459ba 已包含 K8s Provider；阶段 0 以该提交为基线。D 盘快照用于核对已有方案，F 盘工作树保留独立改动。历史证据 docs/evidence/2026-10-10-k8s-provider.md 中有 fake 测试和真实单节点 kind 验收，包含预热、server 重启后续跑；独立 KindExec 和跨节点恢复是本期新增交付。Kimi 是既有托管上游。本初稿未创建云资源，未取得新模型、云机容量或故障恢复的实测结果。

每项改动按“先写失败用例 → 最小实现 → 真实入口验证 → 提交代码并归档证据”推进。每轮保存 Git SHA、镜像 digest、权重 revision、模型模板和 parser、实例规格、运行命令、种子、原始逐任务 JSONL 和账单区间。日志中的任务 ID、attempt、节点、Pod UID、模型路由与 trace ID 应可关联。压测前验证记录不含 API 密钥。

## 阶段 1　让 KindExec 在独立 Pod 真正跑起来

修改入口为 internal/provider/k8s/{provider,pod,exec}.go、internal/app/exec.go、internal/gateway/{call/shell.go,workspace/execop.go}。先沿现有分层跟踪谁暂存输入、谁收集输出，复用 Gateway 的 manifest/BlobStore 和已有 shell 包装器。

- [ ] 在 internal/provider/k8s/provider_test.go 添加 KindExec 用例：输入文件 seed.txt 内容 alpha，命令读取它并产生 result.txt。先用 go test ./internal/provider/k8s 验证当前拒绝 KindExec，再实现创建、启动、取输出和销毁。
- [ ] 为独立执行 Pod 使用单次调用身份与受限资源；仅交付本次输入，编排 Gateway socket 和模型凭据对执行容器不可见。退出码、stdout/stderr 和产物分别返回。超时终止进程并最终删除 Pod；清理可重试。
- [ ] 用相同相对路径并行跑两个不同内容的任务，验证结果隔离。覆盖 exit 0、exit 7、超时、重复清理；记录 Agent Pod 与执行 Pod 的不同 UID 及最终残留数。
- [ ] 本地 kind 可做轻量调试；本地磁盘不足时直接在 CVM A 调试。云上部署能加入 B 的 K8s 集群（例如单 server K3s），通过实际 Gateway 发起相同用例，保存 events、日志和输出摘要，作为正式验收。

## 阶段 2　自部署 SGLang，完成第一条任务

- [ ] CPU 侧工具和判题通过后，再开单张 24 GB 级 GPU。固定 Qwen3-8B 权重提交、SGLang 镜像、dtype、聊天模板和工具解析器。单请求逐档增加输入并预留输出空间，记录截断、OOM、可用上下文和显存，再在目标并发下复测。
- [ ] 显式开启工作区工具。按 worker/chatagent/model.py 和 loop.py 的 tools/tool_calls 契约跑三探针：直连端点请求读文件；原请求经 Go Gateway；Python Agent 将工具结果带回模型完成第二轮。保存规范化前后的脱敏数据、参数校验和实际路由。验收禁用 Kimi 回退。
- [ ] 两天仍未接通则做分层诊断。直连格式错先修模板/parser；网关前后字段不一致先修适配；显存不足或当前权重无兼容路径再切小模型，重新登记版本。格式正确但不会解题时先减少任务难度，保留失败记录。
- [ ] 通过正常 Agent 入口自主读、改、测，独立验证补丁。归档一条成功和一条明确失败的轨迹、峰值显存、工具 Pod UID 和实际模型端点。人工注入故障或参考补丁单列，只有模型自主完成的任务计入解题数。

## 阶段 3　单 GPU 基线

- [ ] 扩展到 5–8 个有参考补丁的仓库修复任务，覆盖单文件和跨文件、多轮读取及测试。预实验校准难度后冻结题目、输出预算和评分规则。
- [ ] 直连、经网关两组回放保持模型、输入输出长度分布、到达方式一致，用流式客户端计 TTFT。完整 Agent 当前内部路径是非流式，计整次模型调用时长。另记工具 Pod 排队、启动、运行和清理时间。
- [ ] 以闭环固定并发寻找容量拐点；单机容量表列提交/可评分/解题数、协议中止/基础设施中止、P50/P95、输入与输出 tokens/s（注明统计口径）、显存峰值、模型排队、每小时可评分轨迹、Pod 就绪 P95、CPU 秒及 GiB·秒/可评分轨迹。答错且正常完成评分的样本进入可评分分母；另列动作解析错误次数/模型调用数。
- [ ] 同配置至少独立跑三轮，报告每轮和范围；尽可能让廉价请求级测量每档达到 100 次。长短任务分别报样本量，小样本列逐题记录。预热池敏感性用 CPU 和可控上游单独测。

## 阶段 4　节点失联后的 Agent 状态恢复

- [ ] CVM B 加入 A 所在集群，控制面和 PG 留在 A。先证明正常任务确实调度到 B。internal/provider/k8s/slots.go 当前依赖本机路径；在 B 为 attempt 建本地 Gateway 入口，经私网接控制面，预热 Pod 也必须绑定正确入口。单独验证迁到 A 后 socket 重绑、旧身份失效。
- [ ] checkpoint 关联 Agent 消息、步骤、预算、稳定调用 ID 和工作区 manifest 摘要。候选 blob 先写 COS，校验大小与摘要，再用 PG 事务条件提交 checkpoint 指针。上传中断或事务未提交时恢复最后一个完整版本。
- [ ] 在任务归属中实现租约、续租和 attempt 条件写。使用数据库时钟判断到期；过期执行者无法提交 checkpoint、变更共享工作区指针或发布最终结果。调用 journal 区分已完成、未发出、结果未知；外部副作用结果未知时按工具语义核对或停止，不盲目重放。
- [ ] B 完成文件修改并提交 checkpoint 后让 B 整机离线。以新 attempt 在 A 重建 Pod、消息、文件和 socket，再跑测试并评分。另做网络分区使旧 B 进程仍存活，恢复网络后主动尝试迟到写入；整机断电与迟到写入留两套时间线。
- [ ] 测故障到检测、故障到下一次成功工具调用、重做步骤、重复外部调用、迟到提交拒绝数及残留 Pod（注明观测时点，含 B 恢复后）。真实模型回合需安排 GPU 窗口；高频故障回归使用可控上游，两者分别标注。

## 阶段 5　扩容与可选缓存对照

- [ ] A 单执行节点与 A+B 使用同一 GPU、模型、任务混合、开环到达序列、全局并发上限、预热配置和缓存策略。固定控制面负载并记录 A 上 PG/Gateway 的资源消耗。选择能暴露排队的到达率，记录发出、排队、完成和丢弃数。
- [ ] 比较有效吞吐、解题率、执行队列与模型队列、GPU 利用率、CPU/内存和单位成本。吞吐持平只构成观测；先排除到达率/并发上限、数据库及启动开销。有模型侧排队、直连容量平台期等交叉证据才归因 GPU。
- [ ] 缓存实验先用固定 tokenizer 核查完整模板渲染后的共享 token 前缀。确认所用 SGLang 版本的默认状态、明确开关及命中指标定义，控制初始缓存状态，回放同一请求序列，对比命中、TTFT 与有效吞吐。

阶段 0–2 预计 5–10 个有效工作日，阶段 3–5 再留 2–4 周。按 6–8 个日历周排期（含库存、排障和复跑缓冲）；从 2026-11-25 起约落在 2027-01-06 至 01-20，面向 2027 年 2 月初投递。延期时依次去掉缓存实验、缩减扩容档位、减少题目数；保留真实自托管验收和跨机恢复。阶段 1 和 2 的耗时最值得用于第一次重新估算。

## 简历写法：问题、方案、结果（STAR）

把 S（场景）和 T（要解决的问题）合成每条的开头，A 写自己实现的关键机制，R 写在什么条件下测出了什么。以下以 Agent Runtime 岗为例，下面给出六条可轮换的素材。投模型服务平台岗时，可把自托管推理放在第一条。

### 改造完成后的投递稿（方括号内填对应验收数据）

**AgentBox｜分布式 Agent 执行与评测平台（Go / Python / Kubernetes / PostgreSQL / SGLang）**

面向需要多轮读代码、改文件和跑测试的仓库修复任务，在腾讯云搭建执行与评测平台。Go 管理任务和沙箱，Python Agent 调用自托管模型，独立验证器在干净仓库中评定最终补丁。

- **跨节点恢复。** 为解决执行节点掉线后只能依赖原机工作区续跑的问题，将 Agent 消息、步骤与 COS 工作区快照绑定到同一 checkpoint，以 PostgreSQL 租约和 attempt ID 校验提交归属。双节点故障实验中，[成功恢复数/注入次数] 次从对端续跑，从故障到下一次成功工具调用的中位耗时为 [秒]，旧节点恢复连接后的 [拒绝数/迟到提交总数] 次过期提交被拒绝。
- **独立工具执行。** 为让 Agent 在 Kubernetes 上运行仓库测试，扩展 KindExec，将工作区输入物化到独立 Pod，收集退出码与产物，并清理超时任务。在 [并行任务数] 个并行任务中验证工作区隔离，覆盖 [通过数/总数] 个退出和清理用例，观测到 [数量] 个残留 Pod。
- **仓库级独立评测。** 为让修复结果可重复验收，固定仓库、依赖和测试版本，将补丁应用到干净副本独立评分，记录工具调用与中止原因。在 [题目数] 道题的 [提交数] 次运行中，[可评分数] 次得到判定，[解对数] 次通过，另记录 [解析中止数] 次动作解析中止与 [基础设施中止数] 次基础设施中止。
- **SGLang 自托管。** 为获得可实测的模型服务容量，在腾讯云单 GPU 上部署 SGLang，固定模型版本和工具解析配置，通过 Go 网关驱动多轮 Agent。在 [GPU、模型、上下文长度、并发] 下，流式推理首 Token 延迟 P95 为 [毫秒]，输出吞吐为 [token/s]，峰值显存为 [GiB]。
- **容量测量与扩容。** 为判断新增 CPU 执行节点的收益，对比直连模型、经网关和完整 Agent 三条路径。固定 GPU、模型与请求到达序列后，将执行节点从一台增至两台，每小时可评分轨迹由 [A] 条变为 [B] 条，每千条运行成本由 [C] 元变为 [D] 元。
- **预热池与环境就绪。** 为缩短任务等待沙箱的时间，在 K8s Provider 中实现预热 Pod 池，通过资源版本条件更新协调并发领取。在单节点 kind、镜像已预拉取的条件下，冷启动与命中预热池各顺序测量 20 次，环境就绪 P50 分别为 978 ms 和 11 ms。

结果依据分别来自阶段 4 的接管记录、阶段 1 的工具契约、阶段 3 的逐任务和 SGLang 指标、阶段 5 的扩容对照与账单，以及已有的单节点预热实验。方括号内填写对应实验的真实数据。

### 现阶段可用的实测条目

- **沙箱启动。** 为缩短交互任务等待执行环境的时间，在 Kubernetes Provider 中实现预热 Pod 池，通过资源版本条件更新协调并发领取。在单节点 kind、镜像已在节点的实验中，冷启动与命中预热池各顺序测量 20 次，环境就绪 P50 分别为 978 ms 和 11 ms。[历史实验记录](../../evidence/2026-10-10-k8s-provider.md)

这组数字只用于描述预热命中的就绪时间。腾讯云上的自托管推理、跨机恢复、整任务吞吐和费用在相应阶段验收后写入投递稿。
