# AgentBox 自托管推理与跨节点恢复实施方案 v0.1

> 实施者按 Superpowers executing-plans 逐项执行，使用复选框追踪。本文是 2026-11-25 的设计初稿；以下指标均为验收要求。

**目标**　在腾讯云上让自托管模型修复真实仓库任务，执行节点失联后从一致的恢复点续跑，并用同一批任务查明扩容的吞吐和成本收益。

**架构**　CVM A 承担单控制面、PostgreSQL、Gateway 与首个 K8s 执行节点。Agent Pod 经绑定到 attempt 的入口调用 Go Gateway；文件工具操作 manifest/blob，shell 工具申请独立执行 Pod。独立 GPU 云服务器 提供 SGLang 私网端点，CVM B 提供第二个执行节点，COS 保存跨节点可读的不可变产物。

**技术栈**　Go 管 Provider、节点入口、调度和恢复；Python 管 Agent、独立验证器及回放；PostgreSQL 管租约与提交；Shell/YAML 固定部署。单 GPU、单控制面，两台独立 CPU 云服务器 是正式实验边界。

## 基线与全局约束

GitHub main 的 7153fc531c8af570c4b96ffdda27fcc9ee7459ba 已包含 K8s Provider；阶段 0 以该提交为基线。D 盘快照用于核对已有方案，F 盘工作树保留独立改动。历史证据 docs/evidence/2026-10-10-k8s-provider.md 中有 fake 测试和真实单节点 kind 验收，包含预热、server 重启后续跑；独立 KindExec 和跨节点恢复是本期新增交付。Kimi 是既有托管上游。本初稿未创建云资源，未取得新模型、云机容量或故障恢复的实测结果。

每项改动按“先写失败用例 → 最小实现 → 真实入口验证 → 提交代码并归档证据”推进。每轮保存 Git SHA、镜像 digest、权重 revision、模型模板和 parser、实例规格、运行命令、种子、原始逐任务 JSONL 和账单区间。日志中的任务 ID、attempt、节点、Pod UID、模型路由与 trace ID 应可关联。压测前验证记录不含 API 密钥。

## 阶段 4　节点失联后的 Agent 状态恢复

[阶段 4 详细计划与三个 subagent 的分工](2026-11-26-agentbox-phase4-recovery.md)

- [ ] CVM B 加入 A 所在集群，控制面和 PG 留在 A。先证明正常任务确实调度到 B。沿用阶段 1 的 Pod 内 Gateway 代理。目标节点上的新 Pod 建立新 attempt 的入口，经私网访问控制面，预热 Pod 领取后同样绑定本次身份。单独验证迁到 A 后 socket 重绑、旧身份失效。
- [ ] checkpoint 关联 Agent 消息、步骤、预算、稳定调用 ID 和工作区 manifest 摘要。候选 blob 先写 COS，校验大小与摘要，再用 PG 事务条件提交 checkpoint 指针。上传中断或事务未提交时恢复最后一个完整版本。
- [ ] 在任务归属中实现租约、续租和 attempt 条件写。使用数据库时钟判断到期；过期执行者无法提交 checkpoint、变更共享工作区指针或发布最终结果。调用 journal 区分已完成、未发出、结果未知；外部副作用结果未知时按工具语义核对或停止，不盲目重放。
- [ ] B 完成文件修改并提交 checkpoint 后让 B 整机离线。以新 attempt 在 A 重建 Pod、消息、文件和 socket，再跑测试并评分。另做网络分区使旧 B 进程仍存活，恢复网络后主动尝试迟到写入；整机断电与迟到写入留两套时间线。
- [ ] 测故障到检测、故障到下一次成功工具调用、重做步骤、重复外部调用、迟到提交拒绝数及残留 Pod（注明观测时点，含 B 恢复后）。真实模型回合需安排 GPU 窗口；高频故障回归使用可控上游，两者分别标注。

### 从项目负载推导 CPU 和内存

代码行数和仓库大小用于估算构建及存储开销。**在线规格由同时运行的任务数、工具 Pod 数和常驻服务决定。** 在云机上先测空载的 Linux、K3s、PostgreSQL、Gateway、镜像与日志占用，再跑一条 CSV 任务，分别记下 Agent Pod、执行 Pod、Gateway 与 PG 的内存工作集、CPU 和 I/O。节点对照使用 Kubernetes 的实际 `allocatable`，核对系统预留、Pod requests，以及并发运行时的内存峰值。 [K3s 资源测量](https://docs.k3s.io/reference/resource-profiling)

| 容量项 | 初始估算与验证 |
|---|---|
| 常驻进程 | 暂按 **3 GiB** 做预算示例，实机空载测出后替换。监控、编译与并发下载若同机运行，也计入预算或移出正式测量窗口。 |
| Python Agent | 当前 CLI 每任务默认 **1 GiB**。首次功能验收按 **2 个任务槽**，即 2 GiB 上限预算。 |
| 独立工具 Pod | 当前实现的 CLI 默认工具内存 **512 MiB**，上限 **1 GiB**，默认全局 4 个工具槽，且独立于任务内存总量。阶段 1 先限 **2 个工具槽、每任务 1 个**，按 2 GiB 做保守上限。新 K8s 路径须核对这些参数确实映射到 Pod limits。 |
| 预热、helper、缓存与回收期 | 另留 **2 GiB** 作为起测余量。工具输入输出落盘时核对临时存储占用。如使用内存卷，纳入内存预算。并发实验前将编排预热池大小固定并记录。 |

示例为 **3 + 2 + 2 + 2 = 9 GiB**，因此推荐 16 GiB 作为并发验收档。4 核 8 GiB 可先按 **1 个 Agent + 1 个工具槽**验收，测量后再提高并发。初始验收由现有 `cmd/agentbox/server.go` 和 `internal/app/exec.go` 的默认值导出配置，避免在 8 GiB 主机上直接采用 8 GiB 的任务总预算再加默认工具槽。上线前记录实用的 requests/limits、节点可分配资源、槽位和超时。

### 验收后如何决定加资源

1. **先找容量拐点。** 从 1、2 个 Agent 开始，并发继续增加前先看上轮稳定区间。记录 CPU 使用和 throttling、内存工作集和 OOM、Pending 原因、磁盘剩余与 I/O 延迟，以及运行队列与工具 Pod 就绪 P95。固定任务和上游响应条件，分别测单次烟测和重复负载。
2. **按瓶颈单项调整。** 如果连续测到 CPU 饱和或 throttling，同时排队上升，先区分节点满载与 Pod CPU limit 过低；前者再比 8 vCPU，后者先改限额复测。若出现内存压力或 OOM，先定位是 Pod 单体上限、预热池空闲开销还是节点总内存不足，再决定限并发或加内存。若主要在等模型，就先查推理队列，CPU 扩容的收益由阶段 5 决定。
3. **磁盘按运行产物估算。** CPU 盘覆盖 OS、镜像和解压层、Go 依赖、PG 数据与 WAL、日志及工作区。GPU 盘另含驱动、CUDA 容器镜像、权重、下载临时文件和模型缓存。用实际拉取结果核对可用空间，保留约 20% 作为运维余量，压测前固定日志保留策略。
4. **GPU 从权重和 token 负载反推。** Qwen3-8B 的 BF16/FP16 权重粗估约 **16 GB**（十进制，以实际权重文件和加载方式为准）。24 GB 还需容纳 KV Cache、激活与运行时开销，不能直接据此承诺某个上下文或并发。先用短输入单并发跑通工具链，再逐档增加输入长度和并发，固定输出预算，记录峰值显存、模型排队、TTFT 和 OOM。如目标负载超出显存，先比较缩短上下文、较小兼容模型或受支持的量化，再评估更大显存。缓存对照固定同一模型、精度和 GPU。 [Qwen3-8B 权重与配置](https://huggingface.co/Qwen/Qwen3-8B)


CPU 和 GPU 优先选按量计费，购买前按腾讯云地域、库存和账户实时报价核算，设置预算告警与到期释放提醒，预算告警本身不会终止计费。项目总账包含租用、调试、失败、空闲、云盘、COS、快照、公网等实际发生项。运行成本 = 实验窗口内全部相关费用 ÷ 可评分轨迹数 × 1000；同时报告成功任务成本，分母为零时记录“无成功样本”。固定费用按时间归属并登记，避免重复计入。[腾讯云 GPU 计费说明](https://cloud.tencent.com/document/product/560/8025)

阶段 1 预计 1–2 周，SGLang 接入单独留出部署和工具兼容的排障时间，阶段 3–5 再留 2–4 周。按 6–8 个日历周排期（含库存、排障和复跑缓冲）；从 2026-11-25 起约落在 2027-01-06 至 01-20，面向 2027 年 2 月初投递。延期时依次去掉缓存实验、缩减扩容档位、减少题目数；保留真实自托管验收和跨机恢复。阶段 1 和 2 的耗时最值得用于第一次重新估算。
