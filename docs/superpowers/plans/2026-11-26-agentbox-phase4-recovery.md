# 阶段 4 实施计划 · 执行节点失联后的 Agent 恢复

**收尾验收入口**　[场景、结果与适用范围](../../evidence/2026-11-28-phase4-closeout/public-summary.md)包含三代接管、真实 COS、PG、真实模型与看板。各节日期对应当次实验；原始环境和逐次日志索引在本地交接文档中。

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标**　在 B 已提交一次工具结果后使整台 B 离线，由 A 从已提交版本续跑同一任务；让仍持有旧凭据的 B 恢复连接，验证所有旧写入被拒绝。

**架构**　单控制面，K3s server、PostgreSQL、Gateway 保留在 A，B 只运行 K3s agent。COS 保存不可变快照，PG 是任务归属和已提交恢复点的唯一裁决者。新 Pod 复用现有 Gateway relay，领取新 attempt 的授权。

**技术栈**　Go、Python chatagent、K3s、PostgreSQL、腾讯云 CVM/COS。计划基于 `c6cd0c9`。

### 4 · 合流与故障矩阵（主 agent 审核，3 操作）

先合入 1、2，再接线并复跑 A 单节点回归。进入整机实验前，必须能从空工作区仅凭 PG/COS 恢复，无需旧节点文件；用新目录排除误用 A 旧缓存。每次新建独立任务。历史 run-01 和 run-04 作为两条确定性基线（后者含完整消息摘要），run-02、03 保留为同点重复记录。后续两个 CPU 实验名额优先覆盖不同时间点：C2 内容上传被中断、C2 所有对象已校验但 PG 提交前中断。两次均预先提交 C1，恢复后逐项校验只见 C1。每个新场景先取一条可复核轨迹；断机接管、分区迟到写入及结果未知分别验收。复测用于定位不稳定性，单次观测只报告原值。

| 注入点 | 故障动作 | 必须同时观察到 |
|---|---|---|
| B 写完文件、C1 已在 PG 提交 | 核对 B 实例后关机；A 保持服务 | 原 B 上的 Pod/attempt 与 A 上新 Pod/attempt 不同；同一 task、C1；文件与完整消息摘要相同、预算与调用号延续；下一次工具成功；独立判分 4/4 |
| B 仍运行且持有旧身份 | 隔离 B，等 PG 确认换主后恢复网络；从仍存活的 X 主动请求续租、提交 checkpoint、发布文件 head 和最终结果 | 四类旧写均被拒绝；新 head 和结果保持；记录旧 relay 请求的响应及实际尝试数。若旧进程已死，本轮不能证明迟到拒写，重新注入 |
| 保存 C2 期间 | 分别中断对象上传，以及在对象已完整、PG 提交前停止发布者 | 新 attempt 只见完整 C1；无半文件；原 journal 的已完成调用不重复；保存 COS 与 PG 时间线 |
| 工具副作用返回前 | 受控服务已登记一次调用，切断回包后使执行者失联 | 出现“结果未知”；自动恢复不产生第二次外部副作用；保留核对/停止记录 |

#### 按一次任务的执行链路选注入点

先让三道题各通过无故障对照，再统一在提交后注入。另选多轮读写题逐个覆盖下表，每次只变一个位置。断机由独立控制通道触发；以事件或提交屏障定位，不按估算秒数盲断。若上传和 PG 事务在 A 执行，单独记录 B 掉线后 A 实际提交还是放弃；要验证上传中断或事务回滚，另在对应发布路径注入，区分两种故障来源。

| 位置 | 核对依据与预期 |
|---|---|
| 接单后、首个 checkpoint 前 | 原始 task 和输入仍在 PG 时从初始输入恢复；查已有调用记录，记录重做量。 |
| 模型/工具请求尚未发出或已发出但未收到回包 | 未发出允许重新调度；在途依调用 ID 查结果和副作用，保留不确定状态与重复计费可能。 |
| 工具结果已持久化，下一 checkpoint 尚未提交 | 恢复上个 checkpoint；请求指纹相同时复用同一调用的已记结果，核对实际执行次数。 |
| 文件上传中、对象完整但 PG head 未提交 | 恢复 PG 选定的完整版本；分别检查无半文件、无未提交版本可见。 |
| checkpoint 已提交、B 尚未收到确认 | 从新 checkpoint 继续，同一提交重试幂等；用 checkpoint ID 和序号验证。 |
| 最终结果已提交、B 尚未收到确认 | 读取终态；不创建重复任务结果，不重复发布。 |

#### 五并发实测口径（2026-11-28）

本轮 B 的 Kubernetes allocatable CPU 为 4000m，每个会话 Pod 请求 1010m。按 request 计算，四个需要 4040m，调度上限为三个；其他 Pod 已申请的 CPU 会进一步减少剩余额度。当时尚未按 Pod 采 CPU。收尾两轮同配置按 UID 读 cgroup，B 上每轮 3 个会话的实测平均用量约 32–37m，逐任务表在[验收记录](../../evidence/2026-11-28-phase4-closeout/public-summary.md)。

以 A 发出停机请求为零点。故障后首次重新排队来自 events.sse 的 turn_status=queued；该事件记录任务状态变化，不能单独确定节点失联或 PG 判定租约到期的准确时刻。Pod Ready 来自 Kubernetes 的 Ready 时间戳，精度为整秒。

| 批次与任务 | 首次重新排队（秒） | 进入恢复槽队列（秒） | 等待槽位（秒） | 新 Pod Ready（约，秒） | 确认恢复检查点（秒） | exec_shell 成功（秒） | 评分 |
|---|---:|---:|---:|---:|---:|---:|---|
| 第一批 01 | 3.360 | 126.397 | 0 | 127 | 128.386 | 130.905 | 4/4 |
| 第一批 02 | 3.361 | 126.398 | 0 | 127 | 128.447 | 132.914 | 4/4 |
| 第二批 05 | 3.360 | 126.399 | 35.590 | 162 | 163.394 | 165.987 | 4/4 |

本轮三个任务的重新排队原因为 crashed_signal。01、02、05 的会话 evicted 事件分别在 +126.392、+126.392、+126.394 秒出现，随后在 +126.396、+126.395、+126.397 秒进入 restoring。它们的 attempt_created（attempt_no=2）分别在 +128.227、+128.219、+163.256 秒记录。该事件与 PG 中新 attempt 和 current_attempt_id 在同一事务写入，事件时间不是数据库提交完成的精确时间。此轮清理前未导出旧 attempt 的 lease_expires_at 和 fenced_at，因此不能把重新排队至 evicted 的约 123 秒逐项归因。会话 evicted 与 Kubernetes Node Ready 属于不同事件。

三只替代 Pod 的 creationTimestamp 分别为 01:45:59、01:45:59、01:46:34 UTC。网关预热池参数默认为 0，实测命令未启用，Pod 的 pool 标签值为空。A 在紧邻的无故障对照中已运行同一镜像摘要，两个容器均为 IfNotPresent。没有取得逐 Pod 镜像拉取事件；这些时延适用于已使用过该镜像的节点，不能当作首次下载、解包和启动的时延。

第二批获槽后 3.998 秒得到成功工具结果。35.590 秒的等待解释了本轮额外延迟的主要部分。固定两个恢复槽限制同时驻留的恢复 worker 数，等待时长还取决于前序 worker 何时释放。本轮不能估计延迟上限。
