# M2 Plan 7：Gateway（edge、call、upstream）实施计划

> **执行方式**：有界多 agent：主 agent 负责接口、集成与验收，子 agent 在隔离 worktree 中实现指定文件；只有互不依赖且不共享运行时资源（WSL、cgroup、PostgreSQL、端口）的任务并行；运行验收串行。每个任务 TDD。
> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development。

**Goal:** 实现规格 §9 的真实 Gateway：每 attempt 一个 Unix socket 入口（edge）、访问检查、调用 journal 与两层账本中的 task 层（call）、模型/搜索/抓取上游 adapter 与 SSRF 验证 dialer（upstream），接入 task actor 与启动装配，并以 fake upstream 完成 E11b、E17–E20、E48 与不变量 I3、I14（journal 部分）。

**Architecture:** `gateway/edge` 只做 Unix socket HTTP/1.1 服务、连接↔attempt 绑定与撤销；`gateway/call` 是唯一的记账与 journal 所有者，经窄接口 `call.Store` 使用 PostgreSQL 的事务用例；`gateway/upstream` 只做供应商协议与出站防护，不记账。actor 决定撤销（先持久化、再关连接）。凭据只在 core 进程内，不进沙箱、不进日志。

**Tech Stack:** Go 1.23（net/http over AF_UNIX、pgx）、PostgreSQL 16、RFC 8785 JCS 指纹、OpenAI 兼容 chat 协议。

**规格依据：** §9（全部）、§3.1、§6（budgets/calls/call_tries/reservations）、§7.1（锁顺序：`tasks FOR SHARE → task_control FOR SHARE → subruns FOR SHARE → attempt_access FOR SHARE → budgets → subrun_budgets → exec_quotas → calls → reservations`）、§11.2（无缓存时的流程：Tx1 resolving → Tx2 预留 → 上游 → 完成）、§14.6（日志字段）、§16.3 I3/I14、§16.4 E11b、E17–E20、E48、§19 默认值；代码组织设计 §2.1（gateway 三包职责）、§3（规则 1：底层包不依赖 gateway）、§4（用例表 `gateway/call`）、§5（撤销：actor 决定、edge 执行）。

## Global Constraints

- **依赖方向**（archtest 固定）：`gateway/call` 不导入 `net/http`、不知道供应商协议；`gateway/upstream` 不导入 `persistence`、不记账；`gateway/edge` 不导入 `persistence`，只调用 `call` 与 `task` 定义的接口；`sandbox`、`cgroup`、`rootfs`、`provider/local` 不依赖 `gateway/*`；`task` 不导入 `gateway/*`（`task.Access` 由 edge 实现，装配在 `internal/app`）。
- **凭据**：供应商 Key 只从宿主环境变量加载（`AGENTBOX_MODEL_API_KEY`、`AGENTBOX_SEARCH_API_KEY`），不写日志、不进 `init` 消息、不进沙箱环境变量；审计只记元数据（§9.9）。测试以 grep 断言日志与事件中无 Key。
- **两个原子提交点**（§9.5）：上游请求只在"调用前事务"提交之后发起；结果 blob 完整保存之后才做结算事务。
- **默认值**（§19）：调用期限 120 s；每逻辑调用累计 3 次 try；每任务上游在途 ≤ 4；每 provider 全局限额（配置，默认 8）；每 attempt 连接 16、活跃请求 32、请求体 4 MiB；抓取 5 MiB / 20 s / 5 跳、默认端口 80/443；模型与搜索响应 8 MiB；退避基数 2 s、上限 60 s、抖动，遵从 `Retry-After` 但受期限约束。
- **预算**：task 层 `budgets.limit_micro` 来自任务 `limits.budget_micro`（微美元整数），未指定取服务配置 `--default-budget-micro`（**待审批默认值：2_000_000 = 2.00 USD**），显式值须为正且 ≤ `--budget-cap-micro`（默认 50_000_000）。sub-run 层（`subrun_budgets`）与 exec 配额属 M4，本计划不建表。
- **测试**：每包一个 `*_test.go`；数据库用例只在真实 PostgreSQL 上测试；fake upstream 是进程内 `httptest`/Unix 服务器，不访问外网；需要 root 的只有真实沙箱冒烟（Plan 8）。
- **分支**：`m2-batch`，自 `m1-batch2` 创建；Plan 7、8 依次在其上执行；推送与合并另行授权。

```go
package call

type AccessFacts struct{ TaskID, AttemptID string; Active bool; Current bool; Desired string }
type Budget struct{ LimitMicro, ReservedMicro, SpentMicro, UnknownMicro int64 }
func (b Budget) Available() int64 // limit − spent − reserved − unknown

type CallState string // resolving | in_flight | completed | failed | unknown
type CallRecord struct {
    TaskID, CallID, Fingerprint, Endpoint string
    State CallState; Source string // upstream（M2 唯一来源）
    ResultRef string; TriesUsed int
    CreatedAt, DeadlineAt time.Time
    CostCharged int64; FirstAttemptID, UpstreamRequestID string
    SupersedesCallID, SupersedeReason string; PossibleExternalDuplicate bool
}
type BeginCallRequest struct{ TaskID, CallID, AttemptID, Fingerprint, Endpoint string; Deadline time.Duration; SupersedesCallID, SupersedeReason string }
type BeginCallResult struct{ Record CallRecord; Existing bool } // Existing：已有同 ID 记录（调用方按 §9.4 表处理）
type ReserveTryRequest struct{ TaskID, CallID, AttemptID, EnvID string; EstimateMicro int64; MaxTries int }
type Try struct{ TaskID, CallID string; TryNo int; ReservationID string; AttemptID string }
type Settlement struct{ Try Try; Outcome string /* ok|retryable|fatal|unknown */; ActualMicro int64; LatencyMs int64; UpstreamRequestID string; ResultSHA256 string /* 仅 ok：结果 blob 的 sha，即 calls.result_ref */; ResultSize int64 /* 仅 ok：blobs.size */; Error string }

type Store interface {
    // CheckAccess 在一致快照中读取 §9.2 的事实（attempt_access.state、tasks.current_attempt_id、task_control.desired）。
    CheckAccess(ctx context.Context, taskID, attemptID string) (AccessFacts, error)
    // BeginCall 是 Tx1：复查访问 → 无记录则登记 resolving（created_at、deadline_at = created_at + Deadline）；有记录则返回它（含指纹供比较）。
    BeginCall(ctx context.Context, r BeginCallRequest) (BeginCallResult, error)
    // ReserveTry 是 Tx2：复查访问与期限（db now() < deadline_at）、累计 tries_used < MaxTries、预算可用 ≥ 估算；
    // 分配 try_no、创建 reservation（held）、budgets.reserved += 估算、calls.state = in_flight、tries_used += 1。
    // 身份 (task_id, call_id, try_no) 幂等：COMMIT 丢失后以同一 try_no 重试返回原记录，不重复预留（E11b）。
    ReserveTry(ctx context.Context, r ReserveTryRequest) (Try, error)
    // SettleTry 完成一次 try 的结算：ok → spent += actual（可赤字），reservation settled，calls completed + result_ref + scope_blobs(task)；
    // retryable/fatal → 释放预留（released），calls 保持 in_flight（retryable，由调用方决定是否再 try）或 failed（fatal）；
    // unknown → unknown += 估算（charged_unknown），calls.state 按调用方给的终态（unknown 或保持 in_flight 待下一 try）。
    // 每笔 reservation 只进入一个桶（互斥记账）；幂等：同 try 重复结算返回已有结果。
    SettleTry(ctx context.Context, s Settlement) (CallRecord, error)
    // FailCall 把没有 try 或已耗尽的调用置为 failed（含 call_deadline_exceeded）。
    FailCall(ctx context.Context, taskID, callID, reason string) error
    // ResetResolving 把遗留的 resolving（无 try）复位为可重新解析（启动时调用，§11.2）。
    ResetResolving(ctx context.Context) (int, error)
    // LoadBudget / LoadCall / ListCalls 供 /v1/budget、重放与 inspect 使用。
    LoadBudget(ctx context.Context, taskID string) (Budget, error)
    LoadCall(ctx context.Context, taskID, callID string) (CallRecord, []TryRecord, error)
    ListCalls(ctx context.Context, taskID string) ([]CallRecord, error)
}
type TryRecord struct{ TryNo int; AttemptID, EnvID, State, Outcome string; LatencyMs, CostMicro int64; ReservationID string }
```

**迁移 0003（字段按规格 §6）：** `budgets(task_id PK FK tasks, limit_micro, reserved_micro, spent_micro, unknown_micro)`；`calls(PK(task_id, call_id), subrun_id NULL, fingerprint, endpoint, state CHECK, source, result_ref, tries_used, created_at, deadline_at, cost_charged, first_attempt_id, upstream_request_id, supersedes_call_id, supersede_reason, possible_external_duplicate)`；`call_tries(PK(task_id, call_id, try_no), attempt_id, env_id, state, outcome, latency_ms, cost_micro, reservation_id)`；`reservations(reservation_id PK, task_id, subrun_id NULL, call_id, try_no, kind CHECK(money), amount, state CHECK(held|settled|released|charged_unknown), UNIQUE(task_id, call_id, try_no))`。`CreateTask` 同事务插入 `budgets` 行（`limit_micro` 取 `limits.budget_micro`）。

**规则：** 锁顺序按 §7.1；每个用例一个事务；`SettleTry(ok)` 同事务先插入 `blobs(sha, size)`（同 runner 的 `recordBlob`）再写 `scope_blobs(task)` 与 `calls.completed`；`limits.budget_micro` 缺失时 `CreateTask` 写 `limit_micro = 0`（fail closed，Task 5 后 API 总会填入），负数或非整数为 ErrInvalid；新增错误码写在 `internal/persistence/errors.go`（本任务 Files 增加该文件）；错误契约沿用 `persistence`（ErrRejected 代码新增 `access_revoked`、`not_current_attempt`、`cancel_requested`、`budget_exhausted`、`tries_exhausted`、`call_deadline_exceeded`、`fingerprint_mismatch`、`call_in_progress`）；`ReserveTry` 对 `budget 可用 ≤ 0` 返回 `budget_exhausted`，对可用 > 0 但 < 估算返回 `budget_insufficient_for_request`（两者都是 ErrRejected）。

type Coordinator struct{ /* store Store; adapters map[upstream.Kind]upstream.Adapter; blobs BlobStore; limits Limits; events HostEvents; clock; perTask/perProvider 并发信号量 */ }
type Limits struct{ CallDeadline time.Duration /*120s*/; MaxTries int /*3*/; PerTaskInflight int /*4*/; PerProviderInflight int /*8*/ }

**规则（§9.4、§9.5、§9.7、§11.2 无缓存分支）：**
1. 解析：`adapter.Resolve(body)`；拒绝重复 JSON 键（`400 duplicate_json_key`，由 `jcs`/解析器保证）；计算指纹。
2. Tx1 `BeginCall`：无记录 → `resolving`；已有记录 → 指纹不同 → `409 fingerprint_mismatch` + host 事件 `replay_divergence`；`completed` → 读取 `result_ref` blob，返回 `Replayed=true`；`resolving`/`in_flight` → `409 call_in_progress`；`unknown` → 在累计上限内新建 try；`failed` → 仅 `Retry=true`、可重试类别且未达上限时新建 try，否则返回持久化失败。
3. Tx2 `ReserveTry`（估算来自 `adapter.Estimate`）：被拒即返回对应 4xx（`402 budget_exhausted`/`budget_insufficient_for_request`、`403 access_revoked`、`409 not_current_attempt`、`409 cancel_requested`、`504 call_deadline_exceeded`、`429 tries_exhausted`）。
4. 上游执行使用 **Gateway 自有 context**：期限 = `min(deadline_at, now+adapter 超时)`；Worker 侧 HTTP 请求取消或连接断开**不取消**上游 try（§9.1 表：继续至期限并结算供重放）；只有"取消类离开原因"（`task_control.desired = cancel`、attempt 被取消撤销）取消在途 try：edge 在撤销时按原因调用 `c.CancelAttempt(attemptID, reason)`，`reason == cancel` 才取消。
5. 结算：`ok` → 结果 blob `Put` 成功后 `SettleTry(ok)`（先 blob 再事务）；`retryable` → 释放预留，若 `tries_used < MaxTries` 且 `now < deadline_at` 则退避（基数 2 s、翻倍、上限 60 s、抖动，遵从 `Retry-After`，不超过剩余期限）后重试；否则 `FailCall`；`unknown` → `SettleTry(unknown)`（unknown 只计一次：同一 try 的迟到响应只记 `call_tries` 诊断），再按上限决定是否新建 try；`fatal` → `SettleTry(fatal)` → failed。
6. 并发：每任务在途 ≤ 4、每 provider ≤ 8，用带 ctx 的信号量等待，等待时间计入期限；超期 → `504 call_deadline_exceeded`。
7. 可能脱离本地控制的请求（发出后 ctx 取消、无法确认）标记 `possible_external_duplicate`。
8. 日志字段：`task_id, attempt_id, call_id, try_no, endpoint, provider, status, latency_ms`；不含 Key、不含提示词。

**Tests（`call_test.go`，fake `Store`（内存，实现 I3 检查）与 fake adapter）：** 指纹对字段顺序不敏感、对 `applied_defaults` 敏感；重放返回同一 blob 且 `Replayed`；指纹不同 → `fingerprint_mismatch` + 事件；`in_flight` → `call_in_progress`；429 ×3 → 3 次 try 后 `tries_exhausted`，unknown 只计一次；期限到达不再新建 try；Worker ctx 取消后 try 继续并完成结算（随后同 ID 重放命中）；`cancel` 原因取消在途 try 并结算 unknown/released；并发限额阻塞直至释放；blob 写失败不结算（无 `completed`）。

**验证：** `go test -count=1 ./internal/gateway/call/ ./internal/jcs/ ./internal/api/`。

type Calls interface { // 由 call.Coordinator 满足

type Edge struct{ /* 每 attempt 一个 listener 与连接集合 */ }
