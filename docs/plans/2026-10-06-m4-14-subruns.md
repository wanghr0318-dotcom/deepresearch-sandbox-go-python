# M4 Plan 14：受限多 Agent（sub-run 并行研究）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 实现 v0.2 规格 §13 的受限多 Agent：一个研究 turn（task）内至多 4 个逻辑 sub-run 并行执行子主题（主 Agent kimi-k3 规划与写报告，每个 sub-run 内由 kimi-k2.6 驱动搜索/阅读循环），宿主持久化 sub-run 定义与状态机、两层预算账本、每 sub-run 并发上限与取消传播；用户可见的研究流程与界面不变（[M4 设计](../superpowers/specs/2026-10-06-m4-chat-sessions-design.md) §4.1 第 3 步：Plan 13 的顺序子主题改为并行 sub-run），每轮 30 次工具额度由全部 sub-run 共享。

**Architecture:** 新的纯逻辑包 `internal/subrun`（状态机、定义哈希、ID 规则、恢复判定、窄 Store 接口，无 I/O）；migration 0007 建 `subruns`、`subrun_budgets`；`internal/persistence/postgres` 实现 sub-run 生命周期用例，并在 Gateway 的预留、结算、账本转换、缓存完成事务中加入 sub-run 层；`internal/gateway/call` 按 sub-run 归属记账、限制每 sub-run 在途 ≤ 2、支持按 sub-run 取消；`internal/gateway/edge` 接受 `X-Agentbox-Subrun`；`internal/protocol` 与 Python SDK 增加 sub-run 扩展消息；runner 处理 `subrun_*` 事件、deadline 与 `T_subrun_cancel`；attempt 生命周期在恢复时重新绑定或判定超时；SDK 新增 `SubrunManager`（单一状态所有者生成 checkpoint 的 `subruns[]`）；Plan 13 的研究流程把子主题循环换成 `asyncio.gather` 上的 sub-run。Anthropic 多 Agent 研究模式：主 Agent 规划 → 并行子 Agent 各自上下文 → 主 Agent 汇总 → 引用核对。

**Tech Stack:** Go 1.24 标准库、pgx（已有）、`internal/jcs`（已有）；Python 3.12+ asyncio（已有 SDK）、pytest；Vue 3 + Vitest（仅运维 inspect 视图与用户侧分组校验）。不引入新的 Go 模块、Python 包或 npm 依赖。

**规格依据：** v0.2 规格 §2（sub-run 术语）、§5.2（扩展协商）、§5.4 sub-run 扩展、§5.5 规则 2/4/6、§5.8（业务事件含 `subrun_*`）、§5.11 fixtures、§6（`subruns`、`subrun_budgets`、`reservations.subrun_id`、`calls.subrun_id`、`events.subrun_id`）、§7.1 锁顺序、§8.4、§9.1 取消表、§9.2、§9.3、§9.6、§9.7 并发、§11.4、§13 全节、§14.3（`subrun_cancel_timeout`）、§14.6、§16.3 I13、§16.4 E24、E40–E45、§16.6 串并行对比、§16.7 M4 门槛、§19（`T_subrun_cancel` 10 s、每任务 sub-run 上限 4、每 sub-run 上游占用 2）；M4 设计 §2 D3/D5、§4、§5、§9。

**前置与并行关系：** 本计划在 **Plan 12（会话后端）与 Plan 13（Agent、工具包、对话界面）联调合入 `m4-batch` 之后**整体开始；其中 Task 1–3 只新建文件或对共享文件做追加式修改，**可在 Plan 12–13 完成前启动**（见任务表"早启动"列与各任务的冲突说明），但合入 `m4-batch` 的顺序由协调者在 Plan 12 的协议任务与 migration 0006 之后安排。

## Global Constraints

- **数量与递归**：每个 task（会话中即每个 turn）至多 4 个逻辑 sub-run；恢复时以同 ID 同定义重发 `subrun_start` 视为同一逻辑 sub-run，不重复计数。不允许递归：SDK 的 sub-run 上下文不提供 `start_subrun`（宿主无法区分发起者，规格 §13.2 已声明 sub-run 不是安全边界）。
- **sub-run ID**：`^[a-z0-9][a-z0-9_-]{0,31}$`，且不等于 `root`；研究 Agent 使用 `st1`…`st4`（子主题序号）。
- **`subrun_start` 字段**：`subrun_id`、`parent_step_id`（非空，≤ 256 字节）、`deadline_ms`（1–3 600 000，必填）、`budget_cap_micro`（可选，≥ 0；缺省表示 sub-run 层只做归属、不设上限）。定义哈希 = `sha256(JCS({parent_step_id, budget_cap_micro | null, deadline_ms}))`。
- **deadline**：首次持久化时 `deadline_at = 数据库 now() + deadline_ms`；同定义重发不改变 `deadline_at`；~~暂停期间继续计时~~（M4 验收后修订：暂停期间不计时，暂停时记录 `remaining_ms`、继续时重新起算，见规格 §13.5）；恢复不重置（规格 §13.5）。研究 Agent 默认 `deadline_ms = 600000`（`research.subrun_deadline_ms` 可配）。
- **状态机**（规格 §8.4）：`started → end_proposed → completed`（仅当已提交 checkpoint 的 `subruns[]` 列出 `completed` 与 `result_ref`）；`started | end_proposed → cancel_requested → cancelled`（取消原因为 `deadline` 时终态为 `timed_out`）；`started | end_proposed → failed`（`subrun_end{failed}` 或 checkpoint 列出 `failed`）；恢复时已过期的非终态 → `timed_out`；task 取消裁决时非终态 → `cancelled`（`failure_reason = task_cancel`）；task 成功裁决时仍非终态 → `failed`（`failure_reason = not_completed_at_result`）。终态 `completed | cancelled | failed | timed_out` 不可回退；已 `cancel_requested`/`cancelled` 的不能改为 `completed`（`invalid_transition`）。
- **`subrun_started` 答复**（补充规格）：`{subrun_id, status: started | rejected, code?}`；`code` 取 `subrun_limit`、`conflict`（同 ID 不同定义）、`subrun_closed`（该 ID 已是终态）、`invalid_field`。
- **result_ref**：sub-run 的结果是一个 `visibility: internal` 的产物 `subruns/<subrun_id>.json`（`{summary, sources[], partial}`），其 sha256 即 checkpoint `subruns[].result_ref`（产物保存已把它授权到 task scope，满足规格 §5.5 规则 2）。
- **Gateway 归属**：带 `X-Agentbox-Subrun` 的请求须满足：该 sub-run 属于本任务、`bound_attempt_id = 当前 attempt`、状态为 `started`；否则 `409 subrun_closed`（规格 §9.2）。带该头时 `X-Agentbox-Call-Id` 必须以 `<subrun_id>/` 开头，否则 `400 invalid_request`。
- **两层账本**（规格 §9.6）：预留须同时满足 task 可用 ≥ 估算与（有上限时）sub-run 可用 ≥ 估算，两层在同一事务中更新；结算、unknown、释放、重启时的 `held → charged_unknown` 两层同步。sub-run 层可用 ≤ 0 → `402 subrun_budget_exhausted`；可用 > 0 但小于估算 → `402 budget_insufficient_for_request`（消息注明层级）。缓存命中与合并 follower 不动账本。预算耗尽不自动取消 sub-run。
- **并发**（规格 §9.7）：每任务上游在途 ≤ 4（不变）；每 sub-run 在途 ≤ 2；获取顺序 sub-run 槽位 → task 槽位 → provider 槽位（避免持有 task 槽位等待 sub-run 槽位）。不承诺公平性。
- **singleflight**：键 `(task_id, attempt_id, subrun_id | "root", cache_key)`（已有，规格 §11.4）；按 sub-run 取消时只取消该 sub-run 的共享请求。
- **取消**（规格 §13.4）：宿主取消一个 sub-run = 同一事务置 `cancel_requested` → `call.Coordinator.CancelSubrun`（在途 try 按"未发出释放 / 有 usage 按实际 / 无法确认 unknown"结算）→ 发送 `subrun_cancel_requested`（deadline 触发时）→ 启动 `T_subrun_cancel`（默认 10 s，`--subrun-cancel-timeout`）；超时未收到 `subrun_end{cancelled}` → 终止整个 attempt（session 模式下终止 incarnation），`outcome_class = subrun_cancel_timeout`（故障重试，从 checkpoint 恢复）。Worker 发起的 `subrun_cancel`（编排层放弃）走同一路径，但不再回发 `subrun_cancel_requested`。task 取消不逐个发送 `subrun_cancel_requested`：attempt 级 `cancel` 与 Gateway 的 `CancelAttempt` 已覆盖，裁决事务把非终态 sub-run 置为 `cancelled`。`reason: policy` 保留，本计划不产生。
- **扩展协商**（规格 §5.2）：宿主在 `init`（task 模式）/ 会话 `init`（session 模式）中携带 `extensions: ["subruns"]`；Worker 的 `ready` 必须回 `subruns: 1`；不一致 → 拒绝该 Worker（`extension_mismatch`）。未协商时收到任何 `subrun_*` 或带 `subrun_id` 的 `progress` → 协议违规 `extension_not_negotiated`。宿主是否启用由 server 标志 `--worker-subruns`（默认 true）决定（仓库尚无 `/etc/agentbox/worker.json` 清单读取，作为已知简化记录在证据中）。
- **未知 sub-run**：`subrun_end`、`subrun_cancel`、带 `subrun_id` 的 `progress` 引用尚未 `subrun_start` 的 ID → 协议违规 `subrun_unknown`。
- **工具额度**：每轮 30 次（`web_search` + `web_fetch`）由 Plan 12 的 Gateway 按 task 计数，sub-run 的调用同样计入同一计数，Gateway 不设 sub-run 级工具上限；主 Agent 在 `todo_write` 时给每个子主题分配份额（软上限，由 SDK 的 `BudgetView` 执行）；工具结果中的"剩余"始终是 task 级剩余。
- **报告预留**：主 Agent 启动 sub-run 前读取 `/v1/budget`，保留报告与引用核对所需额度 `report_reserve_micro`（默认按 `report_max_tokens × kimi-k3 输出单价 × 1.5` 计算），其余平均分给各 sub-run 作 `budget_cap_micro`。
- **模型**：主 Agent（规划、汇总、报告、引用核对）用 `orchestrator_model`（kimi-k3）；sub-run 内的工具循环与子主题摘要用 `worker_model`（kimi-k2.6）。两者都须在服务端模型白名单中（沿用 Plan 11）。
- **调度开关**：研究配置 `research.scheduling: parallel | serial`（默认 `parallel`）与 `research.fixed_plan`（可选，给定时跳过规划、按给定子主题执行）。用户路径从不设置二者；只有串并行对比（运维路径）设置。`serial` 也使用 sub-run（逐个启动），保证两组的任务拆分、提示词与记账路径完全相同，只差调度。
- **锁顺序**（规格 §7.1）：`… → task_event_seq → subruns → attempts → attempt_access → … → budgets → subrun_budgets → exec_quotas → calls → reservations`。Gateway 事务：`tasks FOR SHARE → task_control FOR SHARE → subruns FOR SHARE → attempt_access FOR SHARE → budgets → subrun_budgets → calls → reservations`。
- **Migration 0007 的顺序风险**：`migrate.go` 以 `max(version)` 判断已应用，**若某个库先应用了 0007 再出现 0006，0006 会被静默跳过**。因此：0007 只能在 Plan 12 的 0006 合入之后合入 `m4-batch`；早启动阶段的测试只用一次性新建的测试库（每次运行前 `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`），绝不对开发共享库或服务器库应用 0007。
- **测试**：Go 每包一个测试文件（追加到已有文件）；需要数据库的用例读 `AGENTBOX_TEST_DATABASE_URL`，`CI=true` 时缺失即失败；需要 root 的用例非 root 时 `t.Skip` 且必须在 root 命令下真实运行一次。Python 测试在 `worker/tests/`；AF_UNIX 用例设 `AGENTBOX_REQUIRE_UNIX_TESTS=1`。环境与命令见 `.superpowers/sdd-m4/exec-context.md`。
- **分支**：集成分支 `m4-batch`；每个任务一个 worktree；运行验收（root、真实沙箱、服务器）串行。

## 本计划依赖的 Plan 12 / Plan 13 接口（Consumes）

以下名称以 Plan 12/13 的实际实现为准；若名称不同，执行者按"形状"对应，形状不符时报告 NEEDS_CONTEXT，不自行发明契约。

**Plan 12（会话后端）：**
- C12-1 协议 session 扩展已合入 `internal/protocol` 与 `worker/agentbox_worker/protocol.py`（`task_start`、`task_outcome` 等），且 `ready` 的扩展确认采用平铺字段风格（`session_ext: 1`）。
- C12-2 session 模式的 Worker 事件处理复用 `internal/runner` 的 `attemptRun.handle`（或提供等价的按类型分发点），使 task 模式与 session 模式共享同一事件处理代码；本计划只在该分发点加 `subrun_*` 分支。
- C12-3 session task 的 attempt 创建事务（持有 `sessions FOR UPDATE` → `tasks FOR UPDATE`）与最终裁决事务位于 `internal/persistence/postgres`，可在事务内调用本计划的 `rebindSubrunsTx`、`closeOpenSubrunsTx`。
- C12-4 `task_start.resume` 与 task 模式 `init.resume` 由同一函数（当前 `internal/app/adapters.go` 中构造 `protocol.Resume` 处）组装。
- C12-5 工具额度：Gateway 按 task 计数 `web_search`/`web_fetch`，计数与预留/缓存完成在同一事务（`internal/persistence/postgres/gateway.go` 的 `ReserveTry`、`CompleteFromCache`），第 31 次 `429 tool_budget_exhausted`。
- C12-6 edge 在 session 中按 incarnation 绑定入口，`binding` 在每个请求上已知当前 `task_id`、`attempt_id`。
- C12-7 运维路径可在指定会话中创建一个带显式研究配置的 turn（`POST /tasks {session_id, spec}`，规格 §15.1；或 Plan 12 提供的等价运维端点），供串并行对比设置 `research.scheduling` 与 `research.fixed_plan`。

**Plan 13（Agent、工具包、对话界面）：**
- C13-1 `worker/agentbox_worker/tools/`：`Tool`（`name`、`description`、`parameters`、`async run(args, ctx) -> ToolResult`）、`ToolContext`（至少含 `gateway`、`step_id`、`budget: BudgetView`、`emit`）、`ToolRegistry`（`schemas()`、`async dispatch(name, args, ctx)`）。**工具只经 `ToolContext.gateway` 访问 Gateway**（本计划向 sub-run 注入带归属头的 gateway 视图；若 Plan 13 的工具直接取全局 gateway，Task 9 先把它改为经 `ToolContext`）。
- C13-2 `BudgetView`：`used`、`limit`（30）、`share`（本子主题份额），以 Gateway 返回的 task 级计数为准；`exhausted()` 在 task 级用尽或份额用尽时为真。
- C13-3 研究流程模块（下称 `research`，位置以 Plan 13 为准，例如 `worker/assistant/research.py`）提供：`plan_subtopics(...) -> list[Subtopic]`（经 `todo_write`）、`run_subtopic(agent_ctx, subtopic, budget_view) -> SubtopicResult`（kimi-k2.6 的工具循环 + 子主题摘要）、`write_report(...)`、`verify_citations(...)`；以及当前的顺序循环 `for st in subtopics: await run_subtopic(...)`。
- C13-4 研究的 checkpoint 状态中每个子主题有独立条目（状态、已收集来源、摘要），每个工具调用后与每个子主题完成后提交 checkpoint；停止（pause）、继续、立即写报告（"finish now"）语义按 M4 设计 §5。
- C13-5 SDK 会话模式的 turn 上下文（下称 `TurnContext`）提供 `gateway`、`async checkpoint(step_id, state, refs)`、`async progress(...)`、`async register_artifact(...)`、`should_pause()`、内部 `_emit(body)` 与控制消息分发 `_handle_control(msg)`。
- C13-6 用户侧事件（`tool_call`/`tool_result`/`todo_updated` 等）以 `progress` 的 `kind` 与 `data` 承载；对话界面的步骤行按事件渲染。
