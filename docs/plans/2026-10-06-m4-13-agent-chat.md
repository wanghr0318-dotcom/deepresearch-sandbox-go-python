# M4 Plan 13：skill 化的 Agent、工具包与对话界面

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 实现 [M4 会话与对话式 DeepResearch 助手设计](../superpowers/specs/2026-10-06-m4-chat-sessions-design.md) 中归属 Plan 13 的部分：Python Worker 的会话模式（协议 v1 session 扩展的 Worker 侧）、以 Kimi 函数调用驱动的 Agent 循环（kimi-k3 编排，kimi-k2.6 执行子主题的搜索/阅读循环）、`worker/skills/deep-research/` skill、`worker/agentbox_worker/tools/` 工具包、停止摘要、立即写报告、恢复（Restore）的 checkpoint 种子、Worker 侧的 `ask_user`/`awaiting_input`；以及 Vue 对话界面（布局 B：会话侧栏、对话气泡、可折叠步骤行、⟨/⟩ 原始请求/响应、提问卡、停止卡、右侧面板 进度/来源/报告），运维工作台仍在 `#/admin`。

**Architecture:** SDK（`agentbox_worker`）增加 session 模式运行时：一个长期进程按 `task_start → task_accepted → 终态提议 → task_outcome → task_released` 循环执行多轮，每轮仍以 `TaskContext` 暴露 checkpoint/产物/暂停，并携带会话状态与本轮指令（directive）。工具包 `agentbox_worker/tools/` 只含通用工具（统一 `Tool` 接口 + 注册表生成 OpenAI 函数调用 schema），网络只经 SDK 的 Gateway 客户端。新 Worker 应用 `worker/chatagent/`（`python3 -m chatagent`，session 模式）实现每轮的 Agent：系统提示列出 skill 目录与工具；编排模型决定直接回答或 `read_skill("deep-research")` 后按 skill 流程研究；子主题由编排模型调用 `research_subtopic` 交给 kimi-k2.6 的子循环顺序执行（Plan 14 改为并行 sub-run，接口不变）；每次工具调用后与每个子主题完成后写 task checkpoint；报告经引用核对后登记为产物；成功时以 `result.session_state` 提议新的会话状态。Web 端新增 `api/chat.ts`（会话 API + 会话事件流）与纯函数事件归约器 `lib/chat.ts`（事件 → 每轮视图模型），组件只渲染视图模型；全部前端任务针对由 OpenAPI 类型构造的 mock 客户端开发，与 Plan 12 并行。

**Tech Stack:** Python ≥ 3.11 标准库（`asyncio`、`json`、`dataclasses`、`html.parser`、`pathlib`、`http.client` 经 SDK）、pytest、ruff、import-linter（均已有）；Vue 3 + TS + Vitest + `marked` + `dompurify`（均已有）。**不引入新的 Python 运行时依赖（沙箱内仍只用标准库），不引入新的 npm 依赖。**

**规格依据：** 设计文档 §2（D1–D10）、§4（Agent 与 skill）、§5（停止、继续、恢复与提问）、§6（API 与事件，前端只消费）、§7（前端）、§8（错误处理）、§9（测试与验收）；v0.2 规格 §5.2–§5.5、§5.8–§5.9（协议与 session 扩展）、§12.2–§12.4（会话状态一致性与任务释放）、§15.1（OpenAPI 唯一契约）。会话后端、API、SSE 与 Gateway 工具额度计数属于 Plan 12；本计划消费其契约（见"与 Plan 12 的共享契约"）。

## Global Constraints

以下逐字摘自设计文档（§2、§4、§5、§6、§8），是本计划所有任务的约束：

- D1 回答还是研究：模型决定，用户可用"深度研究"开关强制研究；界面显示所走的路径。
- D2 停止摘要：由 checkpoint 生成的结构化进度卡（零成本）+ kimi-k2.6 写的 2–3 句"目前发现"（约 0.01 USD）；按钮"继续""立即写报告"。
- D3 研究方式：工具调用式 Agent（模型决定何时搜索、读哪个网页、何时结束）；每轮 30 次工具调用上限由 Gateway 强制，第 31 次 `429 tool_budget_exhausted`；Agent 在每个工具结果中看到剩余额度。
- D5 已停止的研究遇到新消息：自动取消但保留全部内容，卡片显示"已停止 + 恢复"；其来源与已完成的子主题摘要可作为新一轮的上下文；"恢复"在同一会话中开新一轮，从被取消研究的最后 checkpoint 继续，获得新的 30 次额度。
- D7 DeepResearch 是一个 **skill**：系统提示列出 skill 目录（名称 + 一句描述）与工具；skill 正文经 `read_skill` 按需加载（渐进披露，同 Claude Code）。
- D8 向用户提问：每轮至多一轮、至多 3 个选择题，只在研究范围不明确时（时间、地区、目的、深度）；研究进行中不提问；简单问答不提问。
- D9 工具放在 `worker/agentbox_worker/tools/`（每个工具一个模块、统一接口、注册表生成函数调用 schema）；仓库根的 `tools/` 是 Go 开发工具，不混用。
- D10 界面布局：对话 + 右侧面板（标签：进度 / 来源 / 报告）；窄屏折叠为单列。
- 模型调用、`read_skill`、`read_source`、`ask_user`、`todo_write` 不计数。
- 工具不持有任何凭据，只经 SDK 的 Gateway 客户端调用；`tool_budget_exhausted` 时 Agent 直接进入摘要或报告，本轮成功并标注"已达工具额度（30/30）"。
- 每个工具调用后、每个子主题完成后写 checkpoint（停止、继续、崩溃恢复最多损失进行中的一次调用）。
- Plan 13 中子主题顺序执行；Plan 14 改为并行 sub-run，流程与界面不变。
- 停止：……还没有任何发现时文字为"尚无发现，研究在规划阶段被停止"。
- 立即写报告（至少一个子主题完成时可用）：恢复并附"现在结束"指令，跳过剩余子主题，用已有材料写报告，turn 成功并标注"部分"。
- `ask_user`：turn 进入 `awaiting_input`（一种暂停：保留 checkpoint、释放 run slot）；用户的回答恢复同一 turn 的同一位置；不计入 30 次。
- 原始请求/响应（⟨/⟩）：用户可见工具的输入、输出与发给模型的提示；不可见 Key、费用与内部调用 ID（沿用 Plan 11 的服务端脱敏，运维可见全部）。
- 模型或供应商失败：重试一次；仍失败则 turn `failed`，显示面向用户的提示（"模型服务暂时不可用，请重试"），会话仍可继续。
- 单个工具调用失败（如网页不可达）：记录并继续，计 1 次额度。

本计划补充的工程约束：

- **推理模型**：kimi-k3、kimi-k2.6 是推理模型。`max_tokens` 取宽裕值（编排 16384、子主题 8192、报告 16384、停止摘要 4096；服务端 `MaxTokensCap` 须不低于这些值）。回复去掉思考段后**既无正文又无 `tool_calls`** 一律是错误（`EmptyCompletion`，消息含 `finish_reason`），先以加倍 `max_tokens` 重试一次，仍为空则按"模型失败"处理；从不当作空回答。
- **Gateway 约束**（`internal/gateway/upstream/chat.go`）：非流式；消息字段只允许 `role/content/name/tool_call_id/tool_calls`，`content` 必须是字符串（带 `tool_calls` 的 assistant 消息写 `""`）；允许顶层 `tools`、`tool_choice`。`reasoning_content` 不回传给上游。
- **确定性**：提示词与工具参数只由 checkpoint 状态确定性地生成（不含时间、随机数）；恢复后重发同一调用时请求体不变（调用指纹稳定）。状态压缩在写 checkpoint **之前**作用于内存中的状态，之后的提示词使用压缩后的状态。
- **大小**：task checkpoint 的 inline state ≤ 200 KiB（协议上限 256 KiB，留余量）；`result.session_state` ≤ 192 KiB；单条 progress 事件 ≤ 64 KiB；每 checkpoint refs ≤ 1024。
- **Python**：沙箱内 Worker 只用标准库；`chatagent` 与 `agentbox_worker.tools` 不导入 `urllib`、`requests`、`httpx`、`socket`（直接）、`subprocess`、数据库模块（import-linter 契约）；测试一个关注点一个测试文件；Agent 与工具测试使用进程内的 `ScriptedGateway`（不依赖 AF_UNIX，在 Windows 上运行），只有 Gateway 客户端头部解析用 `conftest.py` 的 AF_UNIX fake（WSL 中运行）。
- **Web**：不新增 npm 依赖；报告与任何 Markdown 只经 `lib/markdown.ts` 的 `renderMarkdown`（marked + DOMPurify）进入 `v-html`；原始请求/响应以文本（`<pre>` + `JSON.stringify`）显示，从不 `v-html`；用户视图不显示费用、模型名、调用 ID、预算微美元；会话 cookie 不进入脚本、URL 或存储。
- **分支与提交**：集成分支 `m4-batch`；每个任务一个 worktree；只提交任务列出的文件；不 push、不 merge。运行验收串行。

## 与 Plan 12 的共享契约

设计 §6 只给出端点与事件名；以下是 Plan 13 依赖、须与 Plan 12 一致的细节。**本计划按此实现；Plan 12 的计划或实现与此不同时，由协调者裁定后两边同步修改，不得各自发明。**

**协议（session 扩展，Worker 侧由 Task 1 实现，Go 侧与 `protocol/fixtures/v1` 的 session 用例归 Plan 12）：**

| 消息 | Plan 13 采用的字段 |
|---|---|
| `init`（宿主→Worker） | `mode: "session", session_id, incarnation_id, session_resume?{checkpoint_id, state \| staged_state_path, refs}` |
| `ready`（Worker→宿主） | `protocol_version: 1, mode: "session", worker, capabilities[], extensions: {"session_ext": 1}` |
| `task_start` | `task_id, attempt_id, attempt_no, traceparent, config, config_version?, budget_limits?, input_refs, out_dir, base_session_checkpoint_id, resume?{checkpoint_id, step_id, state \| state_ref, refs}`，**新增** `directive?`、`carryover?`（见下） |
| `directive` | `{"kind":"finish"}`（立即写报告）\| `{"kind":"answer","question_id":str,"answers":[{"index":int,"choice":str\|null,"other":str\|null}]}` \| `{"kind":"restore","from_task_id":str}`；缺省 = 正常开始或继续 |
| `carryover` | 新一轮到达时被取消的 paused turn 的最后 task checkpoint：`{"task_id":str,"state":object}`（D5 的"其来源与已完成的子主题摘要作为新一轮的可用上下文"） |
| `paused`（Worker→宿主） | `attempt_id, checkpoint_id, awaiting_input?{"question_id":str}`；带 `awaiting_input` 时宿主无需 pause 请求即裁决为 `awaiting_input` |
| `result` | `attempt_id, summary（本轮回复文本，≤ 64 KiB）, outputs[]（有报告时为 ["report"]）, session_state` |
| `quiesced` | `session_checkpoint_id`（尚无会话 checkpoint 时省略该字段） |
| 其余 | `task_accepted`、`task_outcome{attempt_id, verdict, committed_session_checkpoint_id?}`、`task_outcome_query`、`task_released`、`quiesce`、`session_close`、`closed` 按 v0.2 规格 §5.4；session 模式中 task 相关事件均带 `attempt_id` |

**turn config**（`task_start.config`，由 server 生成）：`{"text":str, "deep_research":bool, "orchestrator_model":str, "worker_model":str, "tool_budget":int}`；缺省模型为 null 时请求不带 model。

**Gateway：** 每个 `web_search`/`web_fetch` 响应（含缓存命中、合并、重放）带头 `X-Agentbox-Tool-Budget: <used>/<limit>`；额度用尽返回 `429 {"error":{"code":"tool_budget_exhausted"}}`。session task 的 fetch 结果 blob 在 turn 成功后可在同一会话后续 turn 中经 `GET /blobs/{sha}` 读取（授权到 session scope）；读取失败时 `read_source` 退回状态中保存的摘录。

**Worker 进度事件 → 会话 SSE：** Worker 以 `progress{step_id, kind, message, data}` 发出下表事件；Plan 12 把 `kind` 作为会话 SSE 事件的 `type`、`data` 作为 `payload` 透传给所有者（按 kind 的字段允许列表）。会话 SSE 帧 `id` 为会话内单调序号；事件体为 OpenAPI `SessionEvent`：`{seq, session_id, turn_id?, type, ts, payload}`。

| kind | data（payload） |
|---|---|
| `route` | `{route: "answer"\|"research"}` |
| `skill_read` | `{name, description, file?}` |
| `thinking` | `{text（≤ 600 字）, raw:{call_id}}` |
| `ask_user` | `{question_id, questions:[{question, options[2–4]}]}`（界面固定追加"其他…"） |
| `todo_updated` | `{items:[{id, title, status: pending\|in_progress\|done\|skipped, budget}]}` |
| `tool_call` | `{tool_call_id, tool, args, subtopic_id?}` |
| `tool_result` | `{tool_call_id, tool, ok, subtopic_id?, preview, raw}`；`preview` 为 `{kind:"search", query, results:[{title, site, snippet, url}]}` \| `{kind:"fetch", n, title, url, site, excerpt}` \| `{kind:"text", text}`；`raw` 为 `{call_id}`（Gateway 调用）\| `{inline:{request, response}}`（本地工具，≤ 16 KiB） |
| `budget` | `{used, limit}` |
| `subtopic` | `{id, title, status: running\|done\|skipped\|failed, summary?}` |
| `assistant_delta` | `{text, final: bool}`（Gateway 非流式：拿到完整回复后按 ≤ 400 字切块依次发出） |
| `report_ready` | `{artifact_id, version, title, partial: bool, note?}` |
| `turn_stopped` | `{card:{todo, subtopics_done, sources, budget:{used, limit}}, findings, can_finish: bool}` |

宿主产生的会话事件（Plan 12）：`session_status{status}`（`frozen`、`evicted`、`restoring`、`idle`）、`turn_status{turn_id, status}`（`queued`、`running`、`paused`、`awaiting_input`、`succeeded`、`failed`、`cancelled`，失败时带面向用户的 `message`）。

**HTTP（OpenAPI，前端以生成类型使用）：** 设计 §6 的端点；另需 `GET /turns/{id}/calls/{call_id}` → `CallDetail{request, response}`（⟨/⟩，服务端按 Plan 11 规则对用户脱敏）；报告下载沿用 `GET /tasks/{turn_id}/artifacts/{artifact_id}?version=`（turn 即 task，所有者可读）。前端引用的 schema 名：`Session`、`SessionList`、`Turn`、`TurnList`、`MessageRequest`、`MessageResult`、`TurnControlResult`、`AnswerRequest`、`SessionEvent`、`CallDetail`；名字以 Plan 12 定稿的 OpenAPI 为准，`web/src/api/chat.ts` 中集中起别名，改名只改别名行。

**行为：**
1. 握手：`init.mode == "session"` 且 `session_id`、`incarnation_id` 非空；`session_resume` 有 `state` 时直接采用，有 `staged_state_path` 时经 `load_staged` 读取（文件不存在或不是 JSON → `error{code:"invalid_field"}` 并退出 1）。`ready` 带 `mode:"session"` 与 `extensions:{"session_ext":1}`。`run_worker`（task 模式）收到 `mode:"session"` 仍为 `unsupported_mode`；`run_session_worker` 收到 `mode:"task"` 同样为 `unsupported_mode`。
2. 空闲时只接受 `task_start`、`quiesce`、`session_close`；`task_start` → 发 `task_accepted{attempt_id}` → 以新 `TaskContext`（`resume` 与 call id 计数器按 task 模式规则从 `task_start.resume` 恢复）运行应用。运行中只接受 `checkpoint_result`、`artifact_result`、`pause`、`cancel`（`attempt_id` 须为当前 attempt，否则 `control_protocol_error`）；运行中收到 `task_start` 为协议错误。
3. 应用返回 `Result` → `result{attempt_id, summary, outputs, session_state}`（`session_state` 经 `_snapshot` 归一化，> 192 KiB 时 `WorkerFailure("state_too_large")` 改发 error）；返回 `Paused` → `paused{attempt_id, checkpoint_id, awaiting_input?}`；`WorkerFailure`/异常 → `error`；宿主 `cancel` → 不发终态提议。
4. 之后等待 `task_outcome{attempt_id}`：超时（`timing.ack_timeout`）发 `task_outcome_query{attempt_id}`，至多 `max_ack_attempts` 次，仍无结果 → 退出 1（宿主销毁 incarnation）。`verdict == "succeeded"` 且有 `committed_session_checkpoint_id` → `SessionInfo` 换成提议的状态与该 ID；其他裁决 → 丢弃工作副本。然后发 `task_released{attempt_id}`，回到空闲。
5. `quiesce` → `quiesced{session_checkpoint_id?}`（无 checkpoint 时省略字段），继续等待（可被 thaw 后的 `task_start` 唤醒）；`session_close` → `closed` 并退出 0；stdin 关闭 → 退出 0（空闲）或取消当前 attempt 后退出 1。
6. 事件 `seq` 每 incarnation 从 1 严格递增（共用一个 `Outbox`）；`SessionStreamChecker` 在测试中校验整个转录。

正文按下列章节写（每节给出规则与简短示例；措辞面向编排模型，祈使句）：

1. **何时使用 / 何时不用**：使用——比较多个选项、行业/市场/技术现状与趋势、文献或政策综述、需要可核验引用的判断；用户打开了"深度研究"开关时总是使用。不用——单一事实、定义、计算、闲聊、对上一份报告的追问（先用对话记忆与 `read_source` 回答）。
2. **流程总览**：① 判断范围 → ② 必要时提问（一轮）→ ③ `todo_write` 计划 → ④ 逐个 `research_subtopic` → ⑤ 写报告 → ⑥ 引用自查。每一步之前想清楚目的；不得跳过 ③ 直接大量搜索。
3. **提问规则**（D8，逐条）：每轮至多**一轮**、至多 **3 个选择题**；只在范围不明确且会显著改变研究方向时提问，维度限于**时间、地区、目的、深度**；每题 2–4 个具体选项（界面自动追加"其他…"），选项互斥、可直接执行；用户已说明的维度不问；简单问答不问；**计划写出之后、任何搜索之后都不再提问**；不提问时在报告"背景与范围"中写明所作的默认假设。附一个合格提问示例与一个不应提问的示例。
4. **计划与额度规则**（D3）：本轮 `web_search + web_fetch` 合计 **30 次**（每个工具结果末尾显示剩余；模型调用、`read_skill`、`read_source`、`ask_user`、`todo_write` 不计数）。计划 **2–4 个子主题**，`todo_write` 中为每个子主题写 `budget` 与 `brief`；**分配**：子主题份额合计 ≤ 26，保留 ≥ 4 次用于收尾补缺；每个子主题典型 6–8 次（约 2 次搜索 + 4–6 次阅读）。**广度/深度**（参照 dzhng/deep-research）：问题宽 → 子主题多（4 个）、每个 5–6 次；问题窄而深 → 子主题少（2 个）、每个 10–12 次。剩余 ≤ 3 时停止新搜索，转入写报告；额度用尽时立即用已有材料写报告并注明"已达工具额度"。
5. **子主题简报写法**（参照 Anthropic 多 Agent 研究系统）：每个 `brief` 写明目标问题、需要的产出（关键事实、数据、分歧点）、优先来源类型、边界（不覆盖什么，避免与其他子主题重复）、份额。示例一个。
6. **执行子主题**：按清单顺序调用 `research_subtopic(id)`；返回的摘要用 `[n]` 引用来源编号；根据摘要调整后续子主题（可用 `todo_write` 更新状态或改写未开始的简报，不可新增超出额度的子主题）；全部完成或额度不足时进入写报告。
7. **搜索与阅读策略**（供子主题执行者，`research_subtopic` 把本节放入其系统提示）：先宽后窄，查询短而具体（中文主题同时尝试英文关键词）；先看搜索摘要再决定读哪页；只读最可能含一手信息的页面；同一 URL 不读两次；需要重看时用 `read_source(n)`；来源质量按 `references/source-quality.md`。
8. **写报告**：结构按 `references/report-template.md`（需要时 `read_skill("deep-research", "references/report-template.md")`）；每个事实性陈述用 `[n]` 引用工具结果中给出的来源编号，可多引 `[2][5]`；**不得编造编号、不得引用未阅读的搜索结果**；不写参考文献列表（系统自动附证据列表）；数字注明时间与口径；写明局限与待核实事项；语言与用户一致。
9. **引用自查**：交付前逐段检查每个 `[n]` 都对应一个已阅读来源、内容确实支持该陈述；不支持的陈述删除或改为"未找到可靠来源"。系统随后机械校验：不在来源列表中的编号会被删除。
10. **停止、立即写报告与恢复**：收到"现在结束"指令时不再调用研究工具，直接按第 8 节用已有材料写报告并在开头注明"部分研究"；从停止或恢复继续时先查看清单状态，不重复已完成的子主题。

**编排循环（`Agent.run`，本任务覆盖正常路径与额度用尽）：**
1. 开始：`phase="orchestrating"`；`messages = [system, *history_messages, {"role":"user","content": cfg.text}]`。`deep_research=True` 时由运行时直接执行一次 `read_skill("deep-research")`（追加合成的 assistant `tool_calls` 与 tool 结果，发 `skill_read` 与 `route{research}`），不依赖模型遵守指令。
2. 每轮：`call_model(step_id="orch", tools=registry.schemas(可用工具))`。可用工具：始终有 `read_skill`、`web_search`、`web_fetch`、`read_source`；`flags.skill_read` 后加 `ask_user`、`todo_write`；`flags.planned` 后加 `research_subtopic`；`finish_requested` 或额度用尽后不给工具（`tool_choice` 省略且 `tools=None`）。回复有 `reasoning` 或带工具调用时的正文 → `thinking`（≤ 600 字，`raw.call_id`）。
3. 有 `tool_calls`：逐个按顺序执行。发 `tool_call` → `asyncio.to_thread(registry.dispatch, …)`（`research_subtopic` 改为 `await self.run_subtopic(id)`）→ 追加 `{"role":"tool","tool_call_id","content"}` → 发 `tool_result`（计数工具再发 `budget`；`todo_write` 再发 `todo_updated`；`read_skill` 成功发 `skill_read`，首次读 deep-research 发 `route{research}`）→ `refs` 并入 `result.blobs` 与本次模型调用 blob → `commit("orch")`。`control == "await_user"`：记 `pending_question`、发 `ask_user`、`commit("ask")` 后返回 `LoopOutcome("awaiting", checkpoint_id)`（同一模型回复中其后的工具调用不执行，以 tool 消息"已跳过：等待用户回答"补齐以保持转录合法）。`control == "budget_exhausted"`：追加 `finish_instruction("budget")` 的 user 消息，记 note "已达工具额度（N/N）"。
4. 无 `tool_calls`：`content` 即最终文本。`route` 未定时定为 `answer` 并发 `route`。`route == "research"` 且至少一个子主题 `done`（或有来源）→ 报告路径：`citation_pass` → `render_report` → `publish_report` → `report_ready` → `assistant_text(报告摘要 + "完整报告见右侧「报告」")` → `LoopOutcome("report")`；否则 → `assistant_text(content)` → `LoopOutcome("reply")`。
5. `rounds` 达 `max_orchestrator_rounds` → 追加 `finish_instruction("rounds")` 再调用一次不带工具的模型；`BudgetExhausted`（费用预算）→ 有子主题完成则同 4 写报告并 note"预算耗尽，部分结果"，否则 `WorkerFailure("budget_exhausted")`。

**子主题子循环（`Agent.run_subtopic(id)`）：** `phase="subtopic"`、`current_subtopic=id`、发 `subtopic{running}`、todo 该项 `in_progress`；`step_id = f"sub-{id}"`，模型 `cfg.worker_model`，工具 `web_search`、`web_fetch`、`read_source`；系统提示 `subtopic_system(item, SKILL 第 7 节, budget.line(id))`。每次工具调用后 `commit(step_id)`；份额用尽（`share_left == 0`）或全局额度用尽时下一次调用不给工具并要求"现在写子主题摘要"；模型无工具调用时正文为摘要（`[n]` 为本轮来源编号）。完成 → `status="done"`、`summary`、`sources`、todo `done`、发 `subtopic{done, summary}`、`commit("orch")`；返回给编排模型的 tool 内容为"子主题 <title> 摘要：…\n<budget.line()>"。子循环中 `ModelUnavailable` → 该子主题 `failed`，编排继续。

**行为：**
1. **停止**（宿主 pause → `ctx.should_pause()`）：`Agent.commit` 在 checkpoint 提交后发现暂停请求 → `state.stops += 1` → 有发现时 `stop_summary`（模型调用在最后一个 checkpoint **之前**发生，保证 call id 计数器被保存）→ 再 `checkpoint("stop", …)`（含 `stop_findings`）→ 发 `turn_stopped{card, findings 或 NO_FINDINGS, can_finish}` → 返回 `Paused(checkpoint_id)`。暂停发生在等待提问（`awaiting`）时不生成摘要。
2. **继续**（`continue`）：`TurnState.from_json(resume.state)`；`pending_question` 存在 → 重新发 `ask_user` 并再次返回 awaiting（同一 `question_id`），否则从 `phase`/`current_subtopic` 原处继续；额度视图沿用（Gateway 计数延续）。崩溃恢复（`attempt_no > 1`，无 directive）同 `continue`。
3. **立即写报告**（`finish`）：`finish_requested=True`、`partial=True`、未完成的 todo 项与子主题 → `skipped`（发 `todo_updated`），note "部分研究"；编排追加 `finish_instruction("user_finish")`，不再提供工具；`can_finish` 为假（无完成的子主题）时：有来源则仍写报告，否则以 reply"尚无可用材料，未生成报告。"成功结束。
4. **回答**（`answer`）：`directive.question_id` 须等于 `pending_question.question_id`，否则 `WorkerFailure("invalid_directive")`；把答案格式化为 tool 消息"用户的回答：1. … 2. 其他：…"（`tool_call_id` = 提问调用）→ 清除 `pending_question` → 继续编排。不计额度。
5. **恢复**（`restore`）：`resume.state` 来自被取消的 turn（宿主授权）→ `seed_restore` → 从原处继续；`report_ready` 等事件属于新 turn。
6. **carryover**：`fresh` 且 `ctx.carryover` 存在 → `carryover_context` 的文本进入编排系统提示（"上一轮被停止的研究的发现"），来源 `adopt` 进本轮 `SourceStore`（续编号），可被 `read_source` 与报告引用。
7. **会话状态**：成功（reply 或 report）→ `Result(summary=回复全文, outputs, session_state=memory.with_turn(TurnRecord(...), 本轮来源).to_json())`；`paused`/`awaiting`/失败不提议会话状态（宿主保持 base）。
