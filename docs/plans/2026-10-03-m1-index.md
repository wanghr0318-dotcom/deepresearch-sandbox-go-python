## M1 完成验收（由 Plan 6 收口；首个切片只是其中第一项）

- 端到端：`submit → checkpoint → 杀死 Worker → 新 attempt 恢复 → result → 回收`。
- 另列：server 被 SIGKILL 后重启，经 reconcile/recovery 启动路径恢复（仅杀 Worker 不能覆盖该路径）。
- 门槛实验 E1–E10、E11a、E12–E16、E46；不变量 I1、I2、I4–I8、I16（规格 §16.7）。
- 里程碑报告须分别标注：已完成集成的能力、仅验证了可行性的能力。

## 所有计划的共同验收条件

代码组织设计 §9 的函数级质量约束；架构检查（§3.2）与 lint 在 GitHub Actions 中通过。

## 执行方式（每份计划相同）

```
writing-plans ──► 项目负责人审阅（含外部评审）并批准 ──► using-git-worktrees（每份计划独立分支与工作区）
   ──► subagent-driven-development：
         每个任务：新的实现子 agent，严格 TDD（先失败测试 → 最小实现 → 通过 → 提交）
                  → 规格符合性评审子 agent → 代码质量评审子 agent（代码组织设计 §9）→ 修正 → 下一任务
   ──► verification-before-completion（真实命令与真实输出）
   ──► requesting-code-review（整份计划评审）
   ──► 推送 + Draft PR（中间 PR 用 Refs；只有最终验收 PR 用 Closes）
   ──► 项目负责人审阅 diff 后合并
```

- **门槛：按计划审批。** 计划获批后，其全部任务由子 agent 连续执行，不逐任务停顿；该计划 PR 的推送随计划批准一并获准。合并始终由项目负责人决定。
- **角色：** 主 agent 负责跨计划接口（协议、持久化、provider 契约）、编写计划、派发子 agent、集成与验收；子 agent 只执行一个边界明确的任务，只看到该任务的文本（含精确接口与测试命令）。
- **并行：** 互不依赖的计划在不同工作区与分支中并行执行，不编辑同一文件。
- **波次：** ① Plan 3 → ② Plan 4 ‖ Plan 2（分别依赖 Plan 3 契约合入与 spike 结论）→ ③ Plan 5 → ④ Plan 6 → M2–M4 各自另写计划。
- **始终成立：** 写计划、执行、推送、合并彼此独立；不强推；子 agent 不涉及 spike 内容；测试失败或非预期 skip 即停止该波次，不绕过。
