- 门槛实验 E1–E10、E11a、E12–E16、E46；不变量 I1、I2、I4–I8、I16（规格 §16.7）。
- 里程碑报告须分别标注：已完成集成的能力、仅验证了可行性的能力。

**判定（2026-10-05，`m1-batch2` @ f03922f）**：

## 执行方式

```
writing-plans ──► 项目负责人审阅并明确批准 ──► 主 agent 持续协调实现、修复与联合验收
   每个任务：实现子 agent（新增行为与缺陷修复走 TDD）→ 按风险评审 → 修正
   ──► verification-before-completion（真实命令与真实输出）──► 本地验收记录 ──► 项目负责人授权推送与 Draft PR ──► 项目负责人决定合并
```

- **门槛：按批审批。** M1 第 1 批（Plan 4）与第 2 批（Plan 2、5、6）各审批一次；获批后主 agent 持续协调到验收，只在契约变化、范围扩大或实质阻塞时汇报。推送与合并不随计划批准获准，始终由项目负责人单独授权。
- **子 agent 的上下文包：** 不只给任务文本，还给出相关规格章节、相关不变量、共享接口、文件所有权与已有实现（每份计划列出"上下文包"）。避免局部符合任务而整体违反架构。
- **按依赖提交推进，不等合并：** 接口已评审、依赖提交已集成验证后，下游计划可基于固定提交继续开发；合并是另一条流程，不成为并行工作的瓶颈。
- **失败只暂停受影响的任务：** 共享契约或集成基线失败时，暂停依赖它的任务；独立模块的局部失败由所属 agent 修复，其他任务继续。
- **评审力度按风险：** 协议契约、状态机、事务、恢复、资源生命周期 → 规格符合性与代码质量双评审；配置、文档、纯改名 → 单次评审。TDD 用于新增行为与缺陷修复，不为文档或改名制造失败测试。
- **测试布局：** 按代码组织设计 §9.3，测试集中在少数固定位置，只覆盖契约与风险路径。
- **平台覆盖：** Windows 只能验证可移植部分（编解码、schema、fixtures）；进程控制、Unix socket、沙箱内 Worker 必须在 Linux 验证。最低支持版本必须在 CI 中实际覆盖（Python 3.11）。
- **始终成立：** 写计划、执行、推送、合并彼此独立；不强推；子 agent 不涉及启动序列 spike（Plan 1B 由项目负责人提供）。
