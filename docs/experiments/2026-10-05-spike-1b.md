# Plan 1B spike：降权启动序列实验记录

日期：2026-10-05　分支：`m1-1b-spike`　代码：`experiments/spike-1b/`　原始日志：`experiments/spike-1b/results/`

本文是有边界的实验记录，不是生产代码说明。它回答规格 §4.6 的开放问题 B1–B6，给出经实验验证的最终启动序列、失败行为表与 §16.2 核对结果。**规格本身未修改**，§4.6 的回写由协调者依据本文另行提交审阅。

## 0. 结论摘要

- **最终序列在本机全部通过**：经典 mount(2)、新挂载 API、宿主侧预挂载三种挂载策略下，checker 的 32 项检查全部 PASS；最终序列连续重复 20 次，20 次全部 32/32 PASS（`final-repeat.log`）。
- **候选序列有两处必须修改**：
  1. **securebits 必须在 setresuid 之前设置并锁定**。候选文本的顺序（先切 UID、清能力，再设 securebits）实测失败：`helper/securebits: operation not permitted`（B3）。
  2. **附加组必须在 clone 之前由宿主清空**。进入 user namespace 并写入 `setgroups=deny` 之后无法再清空。Go 的 `SysProcAttr.Credential{Groups: []}` 在这种配置下会**静默跳过** setgroups，宿主的组 0 以 `65534` 的身份留在 workload 中（B1）。
- **新发现、须写入实现的要求**：init 从 `ExtraFiles` 继承的控制 socket **不带** `FD_CLOEXEC`；helper 用 `close_range(4, ~0, CLOSE_RANGE_CLOEXEC)` 做兜底（B5）。helper 的身份与能力变更**必须**锁定 OS 线程，并对所有线程生效；不锁线程的对照组 20 次里 9 次让 workload 以 uid 0、带能力运行（B4）。只看 exec-status 管道 EOF 无法区分"helper 已 exec"与"helper 在 exec 前被杀"，需要额外确认（B6）。
- **WSL2 特有现象**：WSL 的 init 给所有进程预装了 1 个 seccomp filter，所以 §16.2 的"`Seccomp_filters ≥ 1`"在 WSL2 上恒为真、无判别力；检查须改为"≥ 宿主基线 + 1"（见 §9）。

## 3. B1：附加组的清空时机与 `setgroups=deny`

**假设**：`setgroups=deny` 必须在宿主写 `gid_map` 之前写入；此后命名空间内任何进程（包括 ns root）都不能再调用 `setgroups`。因此附加组只能在 clone 之前、在宿主侧清空。

**实验**：

| 场景 | 做法 | 结果 |
|---|---|---|
| `final-*`（`-groups clear`） | launcher 在 clone 前对自身执行 `syscall.Setgroups([]int{})`（Go 对所有线程生效） | workload `groups_empty PASS getgroups=[] status.Groups=""` |
| `b1-inherit` | 不清空 | `CHECK groups_empty FAIL getgroups=[65534] … status.Groups="65534"` |
| `b1-credential` | `SysProcAttr.Credential{Groups: []uint32{}, NoSetGroups: false}` | 同上 FAIL：`getgroups=[65534]` |
| `b1-credential-nonempty` | `Credential{Groups: []uint32{0}}` | `create_err: fork/exec …: operation not permitted` |

**证据**：

```
[launch] launcher supplementary groups before: [0]
[launch] launcher cleared its supplementary groups before clone: []
[launch] host view of init: Uid=[300000 300000 300000 300000] Gid=[300000 300000 300000 300000] Groups=[] …
[launch] host view of init setgroups: deny
[wl:out] CHECK uid PASS resuid=1000,1000,1000
[wl:out] CHECK gid PASS resgid=1000,1000,1000
[wl:out] CHECK groups_empty PASS getgroups=[] err=<nil> status.Groups=""
```

`b1-credential` 的成因见 Go 源码 `syscall/exec_linux.go:496`：

```go
if !(sys.GidMappings != nil && !sys.GidMappingsEnableSetgroups && ngroups == 0) && !cred.NoSetGroups {
	_, _, err1 = RawSyscall(_SYS_setgroups, ngroups, groups, 0)
```

映射存在、setgroups 被禁用且组列表为空时，Go **跳过** setgroups 且不报错，于是宿主组 0 原样保留。组 0 在命名空间内未映射，显示为 overflow gid 65534，但内核做权限检查时仍按宿主 gid 0 计算（对宿主上 group 0 可读的文件构成泄漏面）。组列表非空时，setgroups 在 `deny` 之后执行，返回 EPERM。

**结论**：

- 时机：**宿主侧，clone 之前**。由宿主进程（或专用的启动子进程）先清空自身附加组，clone 出的子进程继承空组。命名空间内无法补救。
- 与 `setgroups=deny` 的关系：`deny` 是写 `gid_map` 的前提（Go 以 `GidMappingsEnableSetgroups: false` 实现，先写 `deny` 再写 `gid_map`）。写入后组列表冻结，所以必须在进入命名空间前就已为空。
- 仍需 `Credential{Uid: 0, Gid: 0, NoSetGroups: true}`，让子进程在命名空间内成为 uid/gid 0，否则 execve init 时会丢失命名空间能力。**不能**依赖 `Credential.Groups` 清空附加组。
- 最终身份：init 为 ns 0/0（宿主 300000），groups 为空；workload 为 resuid 与 resgid 均为 1000/1000/1000（宿主 301000），groups 为空，`/proc/self/setgroups` 为 `deny`。
- 生产实现建议：Runtime 启动时清空自身附加组，并在每次 clone 前断言 `/proc/self/status` 的 `Groups:` 为空。若服务进程不宜修改自身组，就经一个 `Credential{Groups: []}` 的中间 exec（不带 NEWUSER）再 clone。

## 4. B2：挂载策略

**假设**：三种策略都可行，差别在于宿主可见性、锁定语义与子挂载处理。

**实验与结果**：

| 场景 | 策略 | 结果 |
|---|---|---|
| `final-classic` | ns 内 `mount(2)`：`MS_REC|MS_PRIVATE` → 模板自 bind → `MS_BIND|MS_REC` 绑定 `/usr`/`/etc`/`/in`，对子树逐个 `MS_REMOUNT` ro（保留各自 atime 标志）→ tmpfs → `/dev` → proc → 掩蔽 → 根 remount ro | 32/32 PASS |
| `b2-classic-nonrec` | 同上但非递归 bind | `init_err: init/mount_rootfs: bind /usr (rec=false): invalid argument` |
| `final-newapi` | ns 内 `open_tree(OPEN_TREE_CLONE|AT_RECURSIVE)` → `mount_setattr(AT_RECURSIVE, RDONLY|NOSUID|NODEV, MS_PRIVATE)`（树游离时设置）→ `move_mount` | 32/32 PASS |
| `final-hostprep` | 宿主在 clone 前 bind + remount ro；ns 内递归自 bind 一次后 pivot | 32/32 PASS |
| `b2-hostprep-norebind` | 宿主预挂载，ns 内不自 bind | `init_err: init/pivot_root: invalid argument` |

**证据**：

- 非递归 bind 失败：`/usr` 在宿主有子挂载；在非初始 user namespace 中，这些子挂载是 `MNT_LOCKED`，内核拒绝会暴露锁定子挂载下层内容的非递归 bind（EINVAL）。
- 经典 remount 不递归：子挂载必须逐个 remount ro，否则会保持 rw（`b2-self-procexe-nodetach` 的 mountinfo 中可见旧根下的 `/usr/lib/wsl/lib=rw`）。最终结果中所有 `/usr/*` 子挂载均为 ro：
  ```
  CHECK rootfs_ro_nosuid_nodev PASS /=ro,nosuid,nodev,relatime /usr=ro,nosuid,nodev,relatime /usr/lib/wsl/drivers=ro,nosuid,nodev,noatime /usr/lib/wsl/lib=ro,nosuid,nodev,noatime /usr/lib/modules/6.6.87.2-microsoft-standard-WSL2=ro,nosuid,nodev,noatime /etc=ro,… /in=ro,…
  ```
- 宿主侧预挂载在宿主可见，并且需要清理：
  ```
  [launch] host mountinfo: 485 429 8:80 /tmp/spike-1b/rootfs /tmp/spike-1b/rootfs ro,nosuid,nodev,relatime - ext4 …
  [launch] host mountinfo entries under /tmp/spike-1b while the sandbox runs: 4
  ```
  ns 内挂载（classic/newapi）对应的数字为 0。
- 宿主预挂载在 ns 内被锁定，ns root 也不能恢复 rw；`pivot_root` 拒绝锁定的 new_root：
  ```
  [init] hostprep: remount /tmp/spike-1b/rootfs/usr rw from namespace root -> operation not permitted
  [init] hostprep: after rebind, remount root rw -> operation not permitted
  RESULT label=b2-hostprep-norebind outcome=init_err … reason="init/pivot_root: invalid argument"
  ```
- 私有传播与旧根脱离（workload 内）：
  ```
  CHECK mounts_private_propagation PASS entries=27 (no shared:/master:/propagate_from tags)
  CHECK old_root_detached PASS mounts at /=1 root="/tmp/spike-1b/rootfs" unexpected mountpoints=[]
  CHECK no_sys_no_cgroupfs PASS /sys entries=0
  CHECK proc_masked PASS /proc/acpi=dir(tmpfs ro empty:true) /proc/asound=absent /proc/kcore=devnull:true /proc/keys=devnull:true /proc/latency_stats=devnull:true /proc/timer_list=devnull:true /proc/timer_stats=absent /proc/sched_debug=absent /proc/scsi=dir(tmpfs ro empty:true)
  CHECK proc_readonly PASS /proc/bus=true /proc/fs=true /proc/irq=true /proc/sys=true /proc/sysrq-trigger=true
  CHECK writable_areas PASS /tmp/w=ok /out/w=ok /w=… read-only file system /usr/w=… read-only file system /in/w=… read-only file system
  ```
  负对照 `b2-self-procexe-nodetach`（不卸载旧根）被 checker 判为 FAIL（`old_root_detached`、`rootfs_ro_nosuid_nodev`、`no_sys_no_cgroupfs` 三项），说明这些检查有判别力。
- 本内核不存在 `/proc/asound`、`/proc/timer_stats`、`/proc/sched_debug`，init 记录后跳过。

**结论**：**选定"命名空间内新挂载 API"**（`open_tree` + `mount_setattr(AT_RECURSIVE)` + `move_mount`），理由如下：

1. 只读、nosuid、nodev 与私有传播都在树游离时设置，挂载出现时已是最终属性，没有"已挂载但仍可写"的窗口；
2. `AT_RECURSIVE` 一次覆盖所有子挂载，免去经典 remount 逐个处理并保留 atime 锁定标志的易错逻辑；
3. 挂载只存在于沙箱的 mount namespace，宿主不可见，进程消失即随命名空间释放，不需要宿主侧清理，也没有崩溃后残留。

经典 mount(2) 作为功能等价的回退方案也已验证，条件是必须使用 `MS_BIND|MS_REC` 并逐个 remount 子树。宿主侧预挂载能用，但需要额外的 ns 内自 bind 才能 `pivot_root`，还会在宿主留下需要清理的挂载，不推荐。proc 和 tmpfs 在本实验中用经典 `mount(2)`（命名空间内允许）；`fsopen/fsmount` 未测试，没有必要。

## 5. B3：`SECBIT_NOROOT | SECBIT_NO_SETUID_FIXUP` 的设置时机

**假设**：(a) 若 init 在启动 helper 之前锁定 `SECBIT_NOROOT`，helper 的 execveat 将不再获得 "root execve" 语义，permitted 为空；(b) 若按候选文本在 setresuid 之后再设 securebits，`setresuid(1000)` 会触发 setuid fixup 清空 permitted/effective，`CAP_SETPCAP` 消失，`PR_SET_SECUREBITS` 将以 EPERM 失败；(c) 正确时机是 helper 内、清空 bounding 之后、setresgid/setresuid 之前。

**实验与结果**：

| 场景 | 顺序 | 结果 |
|---|---|---|
| `final-*` | bounding 清空 → **securebits 0x0f 锁定** → setresgid → setresuid → capset 全 0 → 清 ambient → NNP → seccomp → execve | PASS；`securebits_value PASS got=0xf`、`securebits_locked PASS … clearing attempt -> operation not permitted` |
| `b3-candidate` | bounding → setresgid → setresuid → capset 0 → ambient → **securebits** → … | `start_err: helper/securebits: operation not permitted` |
| `b3-init-noroot` | init 在启动 helper 前锁定 securebits 0x0f | `start_err: helper/drop_bounding: drop cap 0: operation not permitted` |
| `b3-final-noclear` | 最终顺序去掉显式 capset/ambient 清空 | workload 仍全部 PASS，但 helper 在 exec 前 uid 1000 下仍持有能力（见下） |

**证据**：

```
[init] B3 variant: init locked securebits=0xf before starting the helper
RESULT label=b3-init-noroot outcome=start_err … reason="helper/drop_bounding: drop cap 0: operation not permitted"
RESULT label=b3-candidate outcome=start_err … reason="helper/securebits: operation not permitted"
```

`b3-final-noclear` 中 helper 在 execve 之前的线程状态（`NO_SETUID_FIXUP` 生效：UID 切换后能力保留）：

```
tid=10 Uid=[1000 1000 1000 1000] … CapPrm=00000000000001e0 CapEff=00000000000001e0 CapBnd=0000000000000000 CapAmb=0000000000000000 NoNewPrivs=1 …
```

execve 之后 workload `threads_caps_all_zero PASS`：调用者非 root、bounding 为 0、目标没有文件能力，execve 后 permitted 必然为 0。

init 自身的状态（三种挂载策略相同）：

```
init thread: tid=1 Uid=[0 0 0 0] … CapInh=0000000000000000 CapPrm=0000000000000020 CapEff=0000000000000020 CapBnd=00000000000001e0 CapAmb=0000000000000000 NoNewPrivs=0 …
```

即 init 的 bounding 为 {KILL, SETGID, SETUID, SETPCAP}（0x1e0），permitted 与 effective 均为 {KILL}（0x20）。helper 经 execveat 获得 permitted = bounding = 0x1e0（root execve 语义），与 init 自身的 permitted 无关。所以 init 的 permitted 可以只保留 KILL。

**结论**：securebits 在 **helper 内、清空 bounding 之后、setresgid/setresuid 之前**设置并锁定。此时 helper 仍有 `CAP_SETPCAP`，且已经通过 execveat 获得全部所需权限；init 不得设置 `SECBIT_NOROOT`。设置后 `NO_SETUID_FIXUP` 让 UID 切换不再自动清空能力，所以显式 `capset(0,0,0)` 与 `PR_CAP_AMBIENT_CLEAR_ALL` 仍要保留：在本配置下它们是纵深防御（execve 本身也会清零），但它们保证了"exec 前 helper 已无能力"，缩小 setresuid 与 execve 之间的窗口。锁定值为 `0x0f`（NOROOT、NOROOT_LOCKED、NO_SETUID_FIXUP、NO_SETUID_FIXUP_LOCKED），workload 中可读且无法清除。

## 6. B4：线程级身份、TSYNC 与 `clone3 → ENOSYS`

**假设**：Linux 的凭据与能力是**每线程**属性，Go 进程有多个 OS 线程。execve 只继承调用线程的凭据，所以 helper 必须 (a) 锁定 OS 线程，让所有步骤与 execve 在同一线程执行，并且 (b) 最好让变更作用于所有线程（`syscall.AllThreadsSyscall`，要求 `CGO_ENABLED=0`；Go 的 `syscall.Setresuid/Setresgid` 本身即如此实现）。

**实验与结果**：

| 场景 | helper 方式 | 结果 |
|---|---|---|
| `final-*`（`capmode=all`） | `LockOSThread` + 全线程系统调用 + seccomp TSYNC | exec 前 helper 的 6 个线程全部 uid 1000、能力 0、NNP 1；workload 32/32 PASS |
| `b4-perthread` | `LockOSThread` + 仅当前线程 | exec 前其余 5 个线程仍为 uid 0、`CapEff=0x1e0`；workload 仍 32/32 PASS（execve 在已降权的锁定线程上发生） |
| `b4-nolock`（重复 20 次） | 不锁线程，仅当前线程，步骤间让出调度 | 11 次 `start_err: helper/seccomp: permission denied`；9 次 workload 启动但 3–7 项 FAIL（uid 0、能力未清、securebits 未设） |
| `b4-clone3-eperm` | 对照：seccomp 让 clone3 返回 EPERM 而非 ENOSYS | Python 线程失败：`RuntimeError: can't start new thread`；`py_clone3_enosys FAIL r=-1 errno=EPERM` |

**证据**：

`b4-perthread`，exec 前：

```
tid=10 Uid=[0 0 0 0] … CapPrm=00000000000001e0 CapEff=00000000000001e0 CapBnd=00000000000001e0 … NoNewPrivs=1 Seccomp=2 Seccomp_filters=2
…
tid=9 Uid=[1000 1000 1000 1000] … CapPrm=0000000000000000 CapEff=0000000000000000 CapBnd=0000000000000000 … NoNewPrivs=1 Seccomp=2 Seccomp_filters=2
```

（TSYNC 把 filter 与 NNP 同步到所有线程，但 UID 与能力没有同步。）

`b4-nolock` 汇总（`results/summary.txt`）：

```
11 start_err "helper/seccomp: permission denied"      ← TSYNC 调用落在既无 NNP 也无 CAP_SYS_ADMIN 的线程上
 9 start_ack fail=3..7                                ← 例：CHECK uid FAIL resuid=0,0,0；CHECK gid FAIL resgid=0,0,0；CHECK securebits_value FAIL got=0x0；
                                                          threads_caps_all_zero FAIL … CapPrm=00000000000001e0 CapEff=00000000000001e0 CapBnd=00000000000001e0
```

最终序列下 workload 内（Go 9 个线程、Python 5 个线程）：

```
CHECK threads_caps_all_zero PASS threads=9 bad=[]
CHECK threads_no_new_privs PASS threads=9
CHECK threads_seccomp_filter PASS threads=9           （每线程 Seccomp=2，Seccomp_filters=2 = WSL 基线 1 + 本 filter）
CHECK clone3_enosys PASS clone3(NULL,0) -> function not implemented (without seccomp the kernel returns EINVAL)
CHECK py_clone3_enosys PASS r=-1 errno=ENOSYS
CHECK py_threads PASS 16 threads ran
CHECK py_thread_status PASS threads=5 bad=[]
CHECK py_subprocess_run PASS rc=0 out='sub-ok'
CHECK py_subprocess_shell PASS rc=0 out='SHELL-OK'
CHECK py_posix_spawn PASS status=0
CHECK py_fork PASS exit=7
CHECK py_threadpool PASS ok
CHECK py_ran PASS python3 -> ok (Go os/exec also starts it under the same filter)
```

**结论**：

- helper 必须 `runtime.LockOSThread()`，所有降权步骤与 execve 在同一线程执行。锁线程是**必要条件**，不锁线程的对照组 45%（9/20）让 workload 带特权运行。
- 推荐同时使用全线程变更（`AllThreadsSyscall`），保证 helper 在任何时刻都没有残留特权线程；seccomp 用 `SECCOMP_FILTER_FLAG_TSYNC`。该方案要求 `CGO_ENABLED=0`：启用 cgo 时 `AllThreadsSyscall` 返回 ENOTSUP。生产构建须固定这一点，或改用 libc 的 setxid 广播。
- `clone3 → ENOSYS` 不影响 Python 3.14 / glibc 2.43 的线程、`subprocess`、`posix_spawn`、`fork`、线程池。EPERM 对照证明 glibc 确实先调用 clone3，正是 ENOSYS 触发了回退到 clone；所以规格"`clone3` 整体返回 ENOSYS"的选择是必要的，不能改成 EPERM。
- 附带观察：`multiprocessing` 的 fork Pool 失败（`FileNotFoundError`），原因是 SemLock 需要 `/dev/shm`，而本实验的 `/dev` 没有提供。这不属于 §16.2；若 Worker 需要，模板应提供 `/dev/shm` tmpfs。

## 7. B5：特权 FD 泄漏

**假设**：Go 的 `os.Open` 等默认带 `O_CLOEXEC`，但 (a) `exec.Cmd.ExtraFiles` 在子进程中**不带** `FD_CLOEXEC`；(b) init 的 helper 二进制 O_PATH fd、exec-status 管道、接收的管道 FD 若有任何一处遗漏 CLOEXEC，就会经 helper 一直传到 workload。

**实验与结果**：

| 场景 | 注入 | 结果 |
|---|---|---|
| `final-*` | 无 | `fds_no_extra PASS extra=[]`；`fds_012_pipes PASS`（0/1/2 均为 `pipe:[…]`） |
| `b5-leak-ctl-nohygiene` | init 复制控制 socket 时不加 CLOEXEC，helper 不做 close_range | `CHECK fds_no_extra FAIL extra=["10->socket:[823812] cloexec=false"]` |
| `b5-leak-self-nohygiene` | helper 二进制 O_PATH fd 不加 CLOEXEC，helper 不做 close_range | `CHECK fds_no_extra FAIL extra=["200->/tmp/spike-1b/rootfs/opt/spike/spike1b cloexec=false"]` |
| `b5-leak-ctl`、`b5-leak-self` | 同上泄漏，但 helper 执行 `close_range(4, ~0, CLOSE_RANGE_CLOEXEC)` | PASS |

**证据**：

```
[init] pid=1; fd 3 (control socket from ExtraFiles) inherited with FD_CLOEXEC=false
init fds: 0->/dev/null cloexec=false | 1->…/final-classic.log cloexec=false | 2->…/final-classic.log cloexec=false | 4->anon_inode:[eventpoll] cloexec=true | 5->anon_inode:[eventfd] cloexec=true | 10->socket:[…] cloexec=true | 200->/tmp/spike-1b/rootfs/opt/spike/spike1b cloexec=true
```

init 的 0/1/2 是宿主日志文件（宿主路径），但在 raw fork 子进程中被 `dup3` 覆盖为 workload 管道，不会泄漏。

**过程中发现的缺陷**：首次运行全部 `start_err: init/execveat: permission denied`。原因是 init 关闭继承的 fd 3 后再打开 helper 二进制，新 fd 恰好是 3，而 fork 子进程按约定用 `dup3(exec-status 管道, 3)` 覆盖 fd 3，于是 execveat 执行的是一个管道。修复：所有要交给 fork 子进程的源 FD（包括 helper 二进制 fd）都先 `F_DUPFD_CLOEXEC` 移到高位（≥ 100 / 200），不得落在目标区间 0..3。

**结论**：

- 每个特权 FD 在创建时就带 CLOEXEC：控制 socket（init 启动后第一件事是 `F_DUPFD_CLOEXEC` 移到高位并关闭原 fd 3）、helper 二进制 O_PATH fd（`O_CLOEXEC`）、exec-status 管道（`pipe2(O_CLOEXEC)`）、接收的 FD（`MSG_CMSG_CLOEXEC`）、cgroup 目录 fd（宿主侧）。
- helper 必须执行 `close_range(4, ~0U, CLOSE_RANGE_CLOEXEC)` 作为兜底，并对 fd 3（exec-status 管道）设 CLOEXEC；它在 workload exec 成功时关闭，从而通知 init。
- workload 只剩 0/1/2，三者均为管道；没有指向宿主路径、控制 socket 或 helper 二进制的 FD。

## 8. B6：失败行为

**方法**：用 `-fail-init <step>` 让 init 的每个环境建立步骤失败，用 `-fail <step>` 让每个启动步骤失败。能真实触发的步骤使用真实错误：execveat 用无效 fd → EBADF；setresgid/setresuid 用未映射 ID 99999 → EINVAL；seccomp 用空程序 → EINVAL；execve 用不存在的路径 → ENOENT；securebits 与 init 锁定 NOROOT 两种顺序错误见 B3。其余步骤为注入错误。判据：结果不是 `start_ack`，workload 输出中没有 `WORKLOAD_STARTED` 标记（`workload_started=no`），并且有原因字符串。

**过程中发现的问题**：helper 在通过全部检查之后、execve 之前被 SIGKILL（`-fail helper_sigkill -naive-ack`）时，exec-status 管道同样是"无数据 EOF"。只依据 EOF 的 init 会错误地发出 `start_ack`，随后报告 `exit signal=9`：

```
RESULT label=b6-start-helper_sigkill-naive outcome=start_ack workload_started=no … exit=code=-1,signal=9
```

修复（已包含在最终序列中）：helper 启动时 `PR_SET_NAME("agentbox-helper")`；init 在 EOF 之后轮询 `/proc/<pid>/stat`。comm 已变化，说明 execve 已提交（内核先关闭 CLOEXEC FD，随即设置 comm，所以短暂轮询即可）。comm 仍是 `agentbox-helper` 且状态为 `Z`，说明在 exec 前死亡，init 收割该进程并返回 `start_err`：

```
RESULT label=b6-start-helper_sigkill outcome=start_err workload_started=no … reason="helper/died_before_exec: signal killed"
```

**失败行为表**（全部场景 `workload_started=no`）：

| 阶段 | 步骤 | 实验中的触发方式 | 报告 |
|---|---|---|---|

| init（环境建立） | `mount_private` | 注入 | `init_err{init/mount_private: …}` |

|  | `open_self` | 注入 | `init_err{init/open_self: …}` |
|  | `pivot_root` | 注入；锁定 new_root（真实 EINVAL） | `init_err{init/pivot_root: …}` |
|  | `umount_oldroot` | 注入 | `init_err{init/umount_oldroot: …}` |

## 9. 最终启动序列

与 §4.6 代码块同一形式（spike 已验证；方括号内为本实验参数）：

```
宿主（root）：分配 UID/GID 范围 [0..4095 → 300000..304095] 与 cgroup；
   在 clone 之前清空附加组（宿主进程 setgroups([])，或经一个带 Credential{Groups: []} 的中间 exec）；
   断言 /proc/self/status 的 Groups 为空
→ clone（CLONE_INTO_CGROUP）：NEWUSER|NEWNS|NEWPID|NEWUTS|NEWIPC|NEWNET；
   父进程写 setgroups=deny → gid_map → uid_map；子进程在 ns 内 setgid(0)/setuid(0)（不调用 setgroups）后 execve init
→ init（ns uid 0，持 ns 全部能力）：
   控制 socket（继承时无 FD_CLOEXEC）立即 F_DUPFD_CLOEXEC 移到高位并关闭原 fd
   sethostname
   mount("/", MS_REC|MS_PRIVATE)
   rootfs：新挂载 API——open_tree(OPEN_TREE_CLONE|AT_RECURSIVE) → mount_setattr(AT_RECURSIVE,
     RDONLY|NOSUID|NODEV, propagation=MS_PRIVATE)（游离时设置）→ move_mount；/in 同法；

   tmpfs：/tmp、/run、/out(size=64M,nr_inodes=1024,uid=gid=1000)；/dev = tmpfs + bind null/zero/random/urandom，再 remount ro
   编排环境：bind Gateway socket（宿主属主 = 映射 uid 1000，0600）；session：bind workspace
   新 proc 实例（nosuid,nodev,noexec）→ 掩蔽（目录：ro 空 tmpfs；文件：bind /dev/null）→ 只读路径（自 bind + remount ro）
   打开 helper 二进制 O_PATH|O_CLOEXEC（pivot_root 之前），F_DUPFD_CLOEXEC 移到高位（不得落在 0..3）
   chdir(root)；pivot_root(".", ".")；umount2(".", MNT_DETACH)；chdir("/")
   能力（全部线程）：bounding = {KILL, SETUID, SETGID, SETPCAP}；permitted = effective = {KILL}；inheritable = 0
   不设置 securebits
→ 每个 workload（持 reg.mu）：
   recvmsg(MSG_CMSG_CLOEXEC)，恰好 3 个 FD；exec-status 管道 pipe2(O_CLOEXEC)；全部源 FD F_DUPFD_CLOEXEC 移到高位
   阻塞全部信号 → raw clone(SIGCHLD) → 子进程：dup3 到 0/1/2 与 3（exec-status），setpgid(0,0)，

     fd 3 设 FD_CLOEXEC；close_range(4, ~0U, CLOSE_RANGE_CLOEXEC)
     清空 bounding（使用 CAP_SETPCAP）
     设置并锁定 securebits = NOROOT|NOROOT_LOCKED|NO_SETUID_FIXUP|NO_SETUID_FIXUP_LOCKED（0x0f）
       ——必须在 setresuid 之前（之后 CAP_SETPCAP 已不可用），且不得在 init 中设置
     setresgid(1000,1000,1000)；setresuid(1000,1000,1000)（NO_SETUID_FIXUP：能力不会自动清空）
     显式 capset(eff=prm=inh=0)；PR_CAP_AMBIENT_CLEAR_ALL
     PR_SET_NO_NEW_PRIVS
     seccomp(SET_MODE_FILTER, SECCOMP_FILTER_FLAG_TSYNC)（clone3 → ENOSYS）
     execve workload（同一锁定线程）
   init：exec-status 管道有数据 → start_err{reason}；EOF → 轮询 /proc/<pid>/stat：
     comm 已变 → 登记 pid → start_ack；comm 仍为 agentbox-helper 且为僵尸 → 收割 → start_err{helper/died_before_exec}
→ 任何步骤失败：init 阶段 → 环境创建失败；workload 阶段 → start_err，workload 不运行
```

## 11. 适用性

**WSL2 特有，或在 WSL2 上需要特别解读**：

1. **seccomp 基线**：WSL 的 init 给所有进程安装 1 个 filter（`Seccomp: 2`、`Seccomp_filters: 1`，本 spike 的 init 也继承了它）。§16.2 的"`Seccomp_filters ≥ 1`"在 WSL2 上无判别力，检查须改为"≥ 宿主基线 + 1"，并辅以功能探测。裸机通常基线为 0，需重新核对该数值。
2. **`/usr` 子挂载**（`/usr/lib/wsl/*`、`/usr/lib/modules/…`）是 WSL 特有的。它们导致了非递归 bind 的 EINVAL 和"子挂载须逐个 remount"的现象。生产模板是自包含目录、没有子挂载，但宿主上模板目录之下若有挂载，同样会触发这一行为。
3. 宿主 `/` 为 private 传播（WSL 默认）。systemd 管理的裸机默认 `/` 为 shared，`MS_REC|MS_PRIVATE` 和 `pivot_root` 对 shared 父挂载的限制须在裸机上重新验证。
4. `RLIMIT_NOFILE`：WSL root shell 为 10240/1048576；workload 观察到 1048575/1048576（见风险 R4）。不同环境数值不同。

**须在裸机 Linux 内核上重新验证（发布门槛前）**：

- 全部 §16.2 条目（`run.sh` 可直接运行；需要 root、cgroup v2、user namespace、python3）；
- 新挂载 API（内核 ≥ 5.12 才有 `mount_setattr`）、`close_range(CLOSE_RANGE_CLOEXEC)`（≥ 5.11）、`CLONE_INTO_CGROUP`（≥ 5.7）在目标内核上的可用性；
- systemd 环境下 `/` 为 shared 时，私有化与 `pivot_root` 的行为；
- 发行版启用 AppArmor 的 user namespace 限制（如 Ubuntu 的 `kernel.apparmor_restrict_unprivileged_userns`）时，root 启动的 userns 是否受影响（本机 WSL 未启用 AppArmor，未覆盖）；
- glibc 与 Python 版本不同时的 clone3 回退（本机 glibc 2.43，Python 3.14.4）；
- aarch64：本 spike 的 seccomp 只覆盖 x86_64。

与 WSL2 无关的结论（顺序、线程、FD、失败处理等语义结论）预计在裸机上同样成立，但按 §16.1"环境 skip 不计为通过"的要求，仍须在裸机上跑一遍 `run.sh` 并记录。
