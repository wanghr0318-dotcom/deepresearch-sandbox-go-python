# go-agentbox 路线图

> 状态：路线已确认 · 2026-10-03（同日修订：v0.2 定为首个公开发布版本）
> 本文只定义阶段划分、发布主张与发布门槛。每个阶段有独立的设计规格、实施计划与发布。
> 当前阶段规格：[`2026-10-03-v0.2-first-release-design.md`](2026-10-03-v0.2-first-release-design.md)

---

## 1. 定位

一个缩小规模的 Agent Runtime：Go 负责执行与权限边界，Python 负责研究编排。长任务在隔离环境中运行，供应商凭据不进入沙箱，模型生成的代码在独立沙箱中执行，Worker 故障后从已提交进度恢复，每次故障都能从 `task_id` 追到 `call_id`。平台通过同一套 Worker 协议接入一个真实业务（DeepResearch）和一个测试 Worker（sim-worker）。

```
v0.2 证明：任务可恢复、会话与执行权限可管理、并行研究可治理（首发）
 → v0.3 证明：跨节点所有权与恢复正确
 → v0.4 证明：执行后端可替换，且取舍可测量
```

## 2. 阶段总览

| 版本 | 核心目标 | 发布 |
|---|---|---|
| **v0.2 首发** | 单执行主机上的可靠执行、Gateway、PostgreSQL、Redis 缓存、会话生命周期、隔离加固与独立 exec、受限多 Agent、CLI 与 Vue | **首个公开发布** |
| v0.3 多节点 | 远程执行、节点失联、fencing、迁移与排空、共享产物存储 | 公开发布 |
| v0.4 MicroVM | 第二种隔离后端、VM 快照恢复、性能取舍 | 公开发布 |

原计划中的 v0.1（单节点可靠执行）不再单独发布，作为 v0.2 的第一个内部里程碑实现。首发范围是原 v0.1 + v0.2 的合并工作量，并新增 PostgreSQL、Redis 与 Vue，**不是跳过其中任何工作**。

## 3. v0.2 —— 首发

**发布主张**：单执行主机上，长任务 Agent 在隔离环境中运行并能从已提交进度恢复；会话可冻结、驱逐与重建；模型生成的代码在无 Gateway 入口的独立沙箱中执行；受限的并行子研究共享预算并可取消。

**范围**

| 模块 | 内容 |
|---|---|
| Go Runtime | 自研沙箱、进程管理、资源限制、可靠终止与回收、user namespace 与 seccomp 加固 |
| Go 控制面 | 任务/attempt/环境状态机、准入、事件续传、checkpoint、故障恢复 |
| PostgreSQL | 唯一元数据存储（不先做 SQLite 再迁移） |
| Gateway | 凭据隔离、调用 journal、两层预算、撤销、出网控制、exec 调度 |
| Redis | 公开搜索/抓取结果缓存：TTL、过期同步请求、任务内请求合并、完整性校验、故障降级 |
| Python Worker | DeepResearch 与 sim-worker，共用接入协议 |
| 会话与加固 | 冻结/解冻、驱逐与重建；可信编排 Worker + 独立 exec 沙箱 |
| 受限多 Agent | 同一任务内至多 4 个 sub-run、共享预算、取消传播、部分失败 |
| 交互 | 先 CLI，再接回现有 Vue 工作台 |

**Redis 不承担任务真相、预算或恢复依据**，这些由 PostgreSQL 事务保证。消息队列、多节点与 MicroVM 保持后置。

**内部里程碑**（不分别公开发布）

1. **M1 可靠执行**：Go Runtime + PostgreSQL + sim-worker，跑通取消、checkpoint 与恢复；降权启动序列 spike。
2. **M2 真实研究与 Gateway**：Gateway + DeepResearch，完成研究到产物的闭环。
3. **M3 交互与缓存**：Redis 缓存 + Vue，验证缓存收益、降级与任务交互。
4. **M4 生命周期与并行**：会话、隔离加固与独立 exec、受限多 Agent；完整回归后统一发布。

**明确边界**：单执行主机、无跨主机接管；容器级隔离；编排 Worker 为可信代码；不保证 exactly-once；预算是保守估算；workspace 不随 checkpoint 回滚；不做 blob 垃圾回收。

**发布门槛**：CI 确定性测试与故障实验通过；目标环境（指定 WSL2 与 Linux 内核）的 spike、隔离与资源验收通过且无环境 skip；真实模型演示有记录；性能报告附原始数据与条件；README 写明保证与边界；至少两份实验故障复盘。详见规格第 16 节。

## 4. v0.3 —— 多节点调度与恢复

**发布主张**：执行节点失联后，平台能撤销旧执行权，并在其他节点恢复任务。

**范围**：控制面与 node agent 分离；节点注册、认证、心跳、租约；基于资源申请量的调度与准入；节点排空、故障恢复与 checkpoint 迁移；跨节点可访问的产物与 checkpoint 存储（BlobStore 的对象存储实现）。

**关键内容**

1. **过期执行者隔离**：心跳超时不代表旧节点已停止。需要控制面代次与 fencing，让旧 Worker 无法继续调用 Gateway、提交状态或覆盖产物；v0.2 的 `current_attempt_id` 校验是其基础，但完整 fencing 还需要 Gateway、产物提交等入口共同执行撤销规则并处理在途操作。v0.2 的单主机 advisory lock 不提供这些能力。
2. **产物存储迁移**：原节点本地的 checkpoint 与证据必须能被新节点访问。
3. **Gateway edge 下沉到 node agent**，core（预算、journal）保持集中。

**故障实验**：节点进程被杀；节点与控制面网络分区但 Worker 仍存活；排空期间有运行任务；节点恢复后携带过期 attempt 回报。

**可选交付**：Kubernetes 部署。先验证 node agent 所需的权限、挂载与 cgroup 条件；部署清单不等于弹性伸缩。

**发布门槛**：任务能跨节点恢复，旧 attempt 被有效隔离，产物完整可用；能解释节点失联与任务失败的区别。

## 5. v0.4 —— MicroVM 执行后端

**发布主张**：同一套任务与恢复协议能接入不同隔离后端，并展示可测量的取舍。

**范围**：在 Runtime 接口后接入 Firecracker provider；适配 guest 启动、控制通信、Gateway 访问与产物传输；验证 VM 快照与恢复；复用 Worker 协议与故障测试；对比 namespace 与 MicroVM 的启动、恢复、内存开销与密度。

**边界**

- 复用 Runtime 接口不代表底层通信相同：bind-mounted Unix socket 需要改为 provider 适配的通道（例如 vsock），只需替换 Gateway edge。
- 快照不能复制旧身份与旧连接：恢复后必须重新绑定 attempt 权限，处理连接与外部资源失效。
- 隔离强度不能用 benchmark 数字证明：性能表与威胁模型、权限边界说明分别交付。

**投入前门槛**：实际验证 KVM 可用，不假定 WSL2 满足。不把任何商业沙箱产品的实现与 Firecracker 画等号。

**发布门槛**：相同 Worker 能在两个 provider 上运行；快照恢复后的身份与任务状态正确；比较数据说明测试条件与限制。

## 6. 每次发布共享的交付物

| 交付物 | 内容 |
|---|---|
| 能力与边界 | 本版本保证什么、尚不保证什么 |
| 接入示例 | sim-worker 与 DeepResearch 的可复现运行方式 |
| 故障证据 | 新增故障实验，并回归既有恢复行为 |
| 性能报告 | 口径一致；区分冷启动、预热启动与恢复；附原始数据 |
| 架构记录 | 关键选择、替代方案、已发现的局限 |

## 7. 交付流程（v0.2：M1–M4）

| 阶段 | 计划 | 审批 |
|---|---|---|
| M1 当前 | Plan 3（协议与 Worker SDK） | 已批准，执行到验收 |
| M1 第 1 批 | Plan 4（PostgreSQL、BlobStore） | 一次审批 |
| M1 第 2 批 | Plan 2、5、6（Plan 1B 由项目负责人提供后编写） | 一次审批 |
| M2、M3、M4 | 各里程碑开始时一次写完该里程碑的全部计划 | 每个里程碑一次审批 |

- **单个计划的执行**：按依赖分批派发任务；主 agent 负责契约、上下文包（全局约束、接口、文件所有权）、本地集成与联合验收；子 agent 按文件所有权工作，TDD 实现。只有互不依赖的任务并行，且各用独立 worktree。评审力度按风险：高风险任务做规格符合性与代码质量双评审，其余单次评审。
- **停下来汇报的条件**：契约变化、范围扩大、实质阻塞。计划内的问题自主修复，不逐项请求确认。
- **验收**：Linux（WSL）为判定依据，Windows 仅供参考；交付改动清单、真实命令与输出、遗留项，并作为验收记录追加到计划文件末尾。
- **分支与授权**：每个计划一条分支，叠在其依赖之上，提交只在本地。写计划、执行、推送、合并彼此独立；推送与合并始终由项目负责人单独授权。
- **测试**：遵循[代码组织设计](2026-10-03-code-organization.md) §9.3。

## 8. 暂缓项

跨会话长期记忆、自主递归多 Agent、notebook 式有状态 exec、跨任务请求合并与后台缓存刷新、进程内存快照（CRIU）、多节点自动扩缩容、warm pool（仅当测量显示瓶颈在此时引入）、blob 垃圾回收、消息队列。
