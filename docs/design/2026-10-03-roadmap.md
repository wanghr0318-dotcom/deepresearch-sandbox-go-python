# go-agentbox 路线图：从单节点可靠执行到可替换隔离后端

> 状态：路线已确认 · 2026-10-03
> 本文只定义阶段划分、发布主张与发布门槛。每个阶段有独立的设计规格、实施计划与发布。
> 当前阶段规格：[`2026-10-03-v0.1-reliable-execution-design.md`](2026-10-03-v0.1-reliable-execution-design.md)

---

## 1. 定位

一个缩小规模的 Agent Runtime：长任务 Agent 在隔离环境中运行，供应商凭据不进入沙箱，Worker 故障后能从已提交的进度恢复，每一次故障都能从 `task_id` 追到具体的 `call_id`。平台通过同一套 Worker 协议接入一个真实业务（DeepResearch）和一个测试 Worker（sim-worker）。

```
v0.1 证明任务可恢复
 → v0.2 证明会话与执行权限可管理
 → v0.3 证明跨节点所有权与恢复正确
 → v0.4 证明执行后端可替换，且取舍可测量
```

## 2. 阶段总览

| 阶段 | 核心目标 | 发布门槛（摘要） |
|---|---|---|
| v0.1 单节点可靠执行 | 长任务隔离运行、受控访问外部服务、故障后恢复 | 演示"执行 → 提交 checkpoint → 杀死 Worker → 新 attempt 恢复 → 返回产物"，附故障与性能证据 |
| v0.2 生命周期、隔离加固与多 Agent | 会话复用、资源回收与恢复、并行子研究、权限分层 | 冻结/驱逐语义清楚；隔离策略有回归测试；并行研究有对照数据 |
| v0.3 多节点调度与恢复 | 远程执行、节点失联、迁移与排空 | 跨节点恢复成功；旧 attempt 被有效隔离；产物完整可用 |
| v0.4 MicroVM 执行后端 | 第二种隔离实现、快照恢复、性能取舍 | 同一 Worker 在两种 provider 上运行；快照恢复后身份与状态正确 |

**v0.1 达到门槛即可公开发布并用于展示，不等待后续阶段。**

## 3. v0.1 —— 单节点可靠执行

**发布主张**：一个长任务 Agent 在隔离环境中运行，Worker 故障后能够从已提交的进度恢复。

**范围**

- **Go Runtime**：rootfs、namespace、cgroup、进程收割、输出限制、终止与资源回收。
- **Worker 协议**：任务输入、事件、checkpoint、控制消息、产物清单；接入 sim-worker 与 deepresearch-worker。
- **控制面**：任务与 attempt 状态机、准入、SQLite 持久化、事件续传。
- **Gateway**：每 attempt 独立入口、有效性检查、模型/搜索/抓取代理、预算预留与结算、调用 journal。
- **恢复**：应用级 checkpoint、启动 Reconciler、旧 attempt 撤销、残留执行环境清理。
- **验证**：故障实验、分阶段延迟测量、真实研究任务演示。

**必须成立的修正**（详见 v0.1 规格）

1. 宿主提交决定 checkpoint 是否成立，ACK 只是通知。
2. 逻辑调用 ID 跨 attempt 稳定，并校验请求指纹。
3. 权限撤销覆盖已建立的连接与后续提交。
4. 恢复前核对旧执行环境，不依赖 Pdeathsig 推断其已退出。
5. 任务终态与资源清理状态分别记录。
6. 结果未知的外部费用保守记账，不直接退回全部预留。

**发布门槛**：能演示"执行 → 提交 checkpoint → 杀死 Worker → 新 attempt 恢复 → 返回产物"，并附故障实验与性能测量证据。

## 4. v0.2 —— 生命周期、隔离加固与多 Agent

**发布主张**：平台能管理可复用的 Agent 会话，并控制并行研究与生成代码的资源和权限。

分三条能力线，不混成一个"大生命周期"。

### 4.1 会话生命周期

session 与 task/attempt 分离：一个会话可包含多次任务，任务结束不一定销毁会话环境。

```
running → idle → frozen
                   ├─ thaw → running
                   └─ 恢复到可提交边界 → checkpoint → evicted
                                                       ↓
                                                  restoring → idle
```

- **frozen 状态不能主动生成应用 checkpoint。** 要么冻结前已提交可用 checkpoint，要么解冻后协作式提交，再释放环境。
- frozen 保留进程与内存，不宣传为释放内存；evicted 才表示执行环境资源已释放。
- restoring 是过程，恢复后进入稳定状态；不设长期的 rehydrated 状态。
- 第一版常驻 Agent 只支持明确的唤醒方式，不承诺后台监听连接能透明恢复。

### 4.2 隔离加固

- user namespace / rootless、capability drop、`no_new_privs`、只读基础文件系统、适配工作负载的 seccomp 策略。
- **生成代码与编排 Worker 的隔离边界。** 外层沙箱不能自动保护 Worker。若承诺生成代码无法访问 Gateway、无法修改研究状态，应提供独立的代码执行沙箱或等效的权限隔离，而非仅换一个子进程。
- mount、ptrace、raw socket 等用例称为**权限边界回归测试**，不据此宣称不存在逃逸漏洞。

### 4.3 受限多 Agent

- 两个并行子研究任务，共享全任务预算。
- 子任务超时、取消传播与部分失败。
- 与串行方案比较质量、时间和成本。
- 不要求每个子 Agent 独占沙箱；调度粒度与安全边界分别设计。

**发布门槛**：会话冻结/恢复与驱逐/重建语义清楚；隔离策略有回归测试；并行研究收益有对照数据。

## 5. v0.3 —— 多节点调度与恢复

**发布主张**：执行节点失联后，平台能撤销旧执行权，并在其他节点恢复任务。

**范围**

- 控制面与 node agent 分离。
- 节点注册、认证、心跳、租约。
- 基于资源申请量的简单调度与准入。
- 节点排空、故障恢复与 checkpoint 迁移。
- PostgreSQL 作为多节点部署的元数据存储；SQLite 保留为单节点开发模式，不承诺两种模式部署能力相同。
- 跨节点可访问的产物与 checkpoint 存储（BlobStore 的对象存储实现）。

**关键内容**

1. **租约之外的过期执行者隔离。** 心跳超时不代表旧节点已停止。需要 fencing：旧 Worker 无法继续调用 Gateway、提交状态或覆盖产物。v0.1 的 `current_attempt_id` 校验是其基础，但完整 fencing 还需要 Gateway、产物提交等入口共同执行撤销规则，并处理在途操作。
2. **产物存储迁移。** 只换元数据库不足以恢复；原节点本地的 checkpoint 与证据必须能被新节点访问。

**故障实验**：节点进程被杀；节点与控制面网络分区但 Worker 仍存活；排空期间有运行任务；节点恢复后携带过期 attempt 回报。

**可选交付**：Kubernetes 部署。先验证 node agent 所需的权限、挂载与 cgroup 条件，再选择部署方式。提供部署清单不等于实现了弹性伸缩。

**发布门槛**：任务能跨节点恢复，旧 attempt 被有效隔离，产物完整可用；能解释节点失联与任务失败的区别。

## 6. v0.4 —— MicroVM 执行后端

**发布主张**：同一套任务与恢复协议能接入不同隔离后端，并展示可测量的取舍。

**范围**：在 Runtime 接口后接入 Firecracker provider；适配 guest 启动、控制通信、Gateway 访问与产物传输；验证 VM 快照与恢复；复用 Worker 协议与故障测试；对比 namespace 与 MicroVM 的启动、恢复、内存开销与密度。

**边界**

- 复用 Runtime 接口不代表底层通信相同。namespace 方案的 bind-mounted Unix socket 不能照搬到 VM 内，需要 provider 适配（例如 vsock）。v0.1 Gateway 的 edge/core 拆分为此预留了位置。
- 快照不能复制旧身份与旧连接。恢复后必须重新绑定 attempt 权限，处理连接与外部资源失效。
- 隔离强度不能用一个 benchmark 数字证明。性能表与威胁模型、权限边界说明分别交付。

**投入前门槛**：实际验证 KVM 可用，不假定 WSL2 一定满足。不把任何商业沙箱产品的实现与 Firecracker 画等号。

**发布门槛**：相同 Worker 能在两个 provider 上运行；快照恢复后的身份与任务状态正确；比较数据说明测试条件与限制。
