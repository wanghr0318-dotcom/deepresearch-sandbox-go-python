# go-agentbox v0.1 设计规格：单节点可靠执行

> 状态：设计已评审通过 · 2026-10-03 · **尚未实现，亦未经验证**
> 路线图：[`2026-10-03-roadmap.md`](2026-10-03-roadmap.md)
> 本文中的"保证"指设计目标及对应的验收条件。只有当第 8 节的验收用例在 CI 中通过后，才能对外宣称该保证成立。

---

## 0. 证据边界

本项目交付三类证据，三者不能互相替代：

| 证据类型 | 证明什么 | 不证明什么 |
|---|---|---|
| 模拟故障实验（sim-worker + fake upstream + fault hook） | 在注入的故障下，恢复、记账、回收逻辑符合规格 | 生产环境中的故障分布；真实供应商的计费语义 |
| 真实模型业务验收（deepresearch + 真实模型） | 端到端链路可用；业务流程能恢复 | 生成文本的质量或确定性 |
| 性能测量（`bench/`） | 在注明的环境与样本量下的延迟分布 | 其他环境下的性能；隔离强度 |

所有故障复盘文档必须标注为"实验故障"，不得包装成生产事故。

## 1. 目标、保证与非目标

### 1.1 对外保证

| 编号 | 保证 |
|---|---|
| G1 | Worker 在独立的 namespace + cgroup 沙箱中运行；终止 attempt 时，其整个执行树被清空后才算回收完成 |
| G2 | 已被宿主提交的 checkpoint 不丢失、不回退；Worker 故障后，新 attempt 从最近一次已提交 checkpoint 恢复 |
| G3 | 沙箱中不注入供应商 API Key；所有外部访问经由 Gateway |
| G4 | 已撤销的 attempt 不能再发起调用、读取结果或提交状态 |
| G5 | 已完成且指纹一致的外部调用在恢复后由 journal 重放，不再访问上游 |
| G6 | 预算按"预留—结算"记账；结果未知的调用按全额预留保守计费，不自动退回 |
| G7 | 任务终态唯一且不可变；已接受的取消不会被成功结果覆盖 |
| G8 | 控制面重启后，按持久化的用户意图恢复任务，不遗留、不重复执行环境 |
| G9 | 每次失败都可通过 `task_id → attempt_id → step_id → call_id → try_no` 定位，并由 `agentbox inspect` 汇总证据 |
| G10 | 事件流断线重连后无缺失、无重复，且不会触发任务重新执行 |

### 1.2 不保证（明确声明）

- **不保证 exactly-once 外部调用。** 请求已到达供应商、结果尚未持久化时崩溃，恢复后可能重复调用；该不确定性被记录（`possible_external_duplicate`），不被掩盖。
- **不保证严格费用上限。** 预留是保守估算；实际费用超出预留时如实结算，预算可出现赤字并阻止新调用。
- **不保证防御内核级逃逸。** v0.1 是容器级隔离，共享宿主内核。
- **不保证生成代码无法使用 Gateway。** 能访问 socket 的任意沙箱内代码，在 attempt 被撤销前都拥有该任务范围内的 Gateway 能力。凭据隔离 ≠ 无调用权限。
- **不实现控制面最小权限分离。** v0.1 中 API、Gateway 与需要特权的 Runtime 共处一个进程，这是部署取舍。
- **不保证模型 token 流式输出。** 进度 SSE 是任务事件流，不是模型 token 流。

### 1.3 非目标

会话复用、冻结/驱逐（v0.2）；多节点、PostgreSQL、对象存储（v0.3）；MicroVM（v0.4）；blob 垃圾回收；Vue 前端（后续接入同一 API）。

## 2. 架构与组件

### 2.1 进程模型

v0.1 是单个 Go 二进制 `agentbox server`，包含全部控制侧组件。每个 Worker 运行在独立沙箱中，经由 `StartExec` 启动。

```
agentbox server（单进程）
├─ api          REST + 可续传 SSE；CLI 客户端 agentbox task submit|watch|cancel|result
├─ task         每任务一个 actor：attempt 生命周期决策
├─ admission    全局：排队与容量槽位
├─ runner       AttemptRunner：执行流的唯一读取者，事件处理，完成屏障
├─ coordinator  每 attempt 串行化物理资源操作
├─ store        Store 接口 → SQLite (WAL)
├─ blob         BlobStore 接口 → 本地文件系统，按 sha256 内容寻址
├─ gateway
│   ├─ edge     每 attempt 独立 Unix listener，连接↔attempt 绑定，撤销
│   └─ core     预算预留/结算、journal、上游（llm / search / fetch）
├─ reconcile    启动核对 + 周期清理循环
└─ provider/local  overlay + ns + cgroup + init（M1）
        │ stdin: 控制消息   stdout: 事件 JSONL   stderr: 日志
        │ /run/agentbox/gateway.sock（bind-mount）
        ▼
   沙箱：python -m <worker>
   独立网络命名空间、无外部网络连接，仅开放指定的 Gateway socket；不注入供应商 API Key
```

### 2.2 并发模型与写入所有权

| 组件 | 负责 | 不做 |
|---|---|---|
| Task actor（每任务一个） | 该任务的状态转换、attempt 创建与替换 | 阻塞在 I/O 上。创建、启动、等待、收集均为异步操作，结果以带 `attempt_id` 的消息返回 actor |
| Admission（全局） | 队列与容量槽位，以消息形式授予 | 单任务决策 |
| AttemptRunner | 读取 Worker 输出、按序处理事件、完成屏障 | 写任务生命周期字段 |
| Gateway core | 通过 Store 原子操作共享预算与 journal | 让每个网络请求经过 actor |
| Resource coordinator | 串行化单个 attempt 的全部物理操作，记录 `stopped_at`、intent 状态 | 决定任务状态 |
| Reconciler（启动） | 在 API 接受请求、actor 启动**之前**运行完毕，然后按核对结果启动 actor | 与 actor 同时修改同一任务 |
| Cleanup loop | 只写 `cleanup_*` 字段，处理已 `ended` 的 attempt | 写生命周期字段 |

**过期结果规则**：异步结果携带不可复用的 `attempt_id`。若该 attempt 已不是当前 attempt，结果**不得改变任务状态**；若携带资源（沙箱、admission 授予等），必须转交清理或归还流程，不得丢弃。

### 2.3 依赖关系

```
api            → task, store, blob
task           → store, blob, provider, admission, runner, coordinator, AttemptAccess（接口，由 task 定义）
runner         → store, blob, provider(ExecHandle)
coordinator    → provider, store
gateway/edge   → gateway/core；实现 task.AttemptAccess（启动时注入）
gateway/core   → store, blob, upstream（接口：llm / search / fetch）
reconcile      → store, provider, coordinator, task.Recover（入口）
cmd/agentbox   → 装配具体实现
```

任何包都不向上依赖。`task` 用 fake provider 测试，`gateway` 用 fake upstream 测试。

### 2.4 M1 与 v0.1 的衔接：`StartExec`

M1 计划中的 `Exec` 是阻塞调用、无 stdin、数据经 init 转发，不适合长驻 Worker。另经检查计划文本：Task 7 的 `reapLoop` 在 SIGCHLD 时循环 `Wait4(-1, WNOHANG)`，Task 8 的 `runOne` 用 `exec.Cmd` 启动并等待子进程，**两者会争抢同一子进程的退出状态**（依据计划代码判断，尚未复现）。v0.1 以如下设计替代。

```go
StartExec(ctx, sandboxID, ExecSpec) (ExecHandle, error)

type ExecHandle interface {
    Stdin()  io.WriteCloser       // 控制消息
    Stdout() io.ReadCloser        // 事件 JSONL
    Stderr() io.ReadCloser        // 日志
    Wait() (ExitStatus, error)    // 进程退出状态，或控制连接错误
    Terminate(grace time.Duration) error
}

type ExitStatus   struct { Code int; Signal syscall.Signal }
type ResourceDiag struct { OOMKillDelta uint64; OOMObserved bool }  // 由 Runtime 读取该 attempt 的 cgroup memory.events
```

**控制通道**

- socketpair 由 `SOCK_STREAM` 改为 **`SOCK_SEQPACKET`**：内核保留消息边界，FD 随所属消息传递，无需长度前缀。
- 一条消息即一帧，帧 ≤ 64 KiB；`spec`（argv + env + cwd）≤ 32 KiB。进程数据不经过控制通道。
- 每端一个写 goroutine，经队列串行化写入。
- `start{exec_id, spec}` 与其三个 FD 在同一次 `sendmsg` 中发送。
- 接收方使用 `recvmsg(MSG_CMSG_CLOEXEC)`，FD 原子地带 close-on-exec；同时检查 **`MSG_TRUNC` 与 `MSG_CTRUNC`**，不完整的帧是协议错误，不得执行。
- FD 数量规则：`start` 必须恰好 3 个，其余消息类型 0 个；不符则关闭全部已收 FD 并按协议错误处理。所有错误路径都关闭已接收的 FD。
- 宿主在 `sendmsg` 返回后总是关闭自己持有的子端副本（已在途）；发送失败时同时关闭父端。
- init 在 `StartProcess` 返回后关闭收到的副本。
- init 回复 `start_ack{exec_id, pid}` 或 `start_err{exec_id, reason}`。ACK 前连接断开：结果未知，`StartExec` 返回 `ErrControlLost`，attempt 失败并拆除沙箱。

**进程启动与收割**

- init 是**沙箱内子进程的唯一 reaper**；宿主仍负责等待自己启动的 init。
- 使用 `os.StartProcess`，`ProcAttr.Files = [stdin, stdout, stderr]`，`Setpgid: true`。只有这三个 FD 被继承。不调用 `Process.Wait` / `exec.Cmd.Wait`，不手写 fork。
- 一把锁 `reg.mu` 同时覆盖：
  - **启动**：`StartProcess` → 登记 `pid → exec_id` → 入队 `start_ack`；
  - **收割**：循环 `Wait4(-1, WNOHANG)` → 查表 → 删除登记 → 入队 `exit`，直到返回 0 或 `ECHILD`。`EINTR` 重试，其他错误显式处理。
- 锁内只做**非阻塞入队**；队列溢出视为控制通道故障，触发沙箱终止，不静默丢弃关键帧。帧在锁外由 FIFO 写 goroutine 发送。
- 由于 ACK 在锁内先于该 pid 的任何查表入队，且写出是 FIFO，`start_ack` 必然先于对应 `exit` 发出。宿主仍防御性地暂存先到的 `exit`。
- 未在登记表中的退出是真正的孤儿，计数并记录。
- SIGCHLD 只用于唤醒循环；一个信号可能对应多次退出。

**流的所有权**

- `ExecHandle` 暴露原始流；**`AttemptRunner` 是唯一读取者**。Runtime 不解析 JSONL、不写 Store，只负责进程退出、信号与通道状态。

**终止**

- `Terminate`：init 向 Worker 进程组发 SIGTERM，设定计时器，**继续处理控制循环**；到期再发 SIGKILL。
- 主动脱离进程组的后代不受进程组信号影响，因此**attempt 结束以整个沙箱执行树清空为准**：`cgroup.kill` → 确认 `cgroup.events` 中 `populated 0`（覆盖整个子树）→ 卸载 → 删除 cgroup 目录。Worker 主进程退出不等于回收完成。
- v0.1 不向 Worker 提供可写的 cgroup 管理入口（`/sys/fs/cgroup` 在沙箱内不可写）。是否创建 cgroup namespace 是另一维度，本规格不将其作为安全保证。

## 3. Worker 协议 v1

### 3.1 通道

| 通道 | 方向 | 用途 |
|---|---|---|
| stdin | 宿主 → Worker | 控制消息，JSONL |
| stdout | Worker → 宿主 | 事件，JSONL |
| stderr | Worker → 宿主 | 自由格式日志，宿主保留最后 64 KiB 环形缓冲 |
| `/run/agentbox/gateway.sock` | Worker → Gateway | 全部外部访问 |
| `/workspace/in` | 只读 | 输入 |
| `/workspace/out` | 读写 | 产物来源 |

### 3.2 引导、阶段与公共规则

- **固定的 bootstrap envelope**：`init` 的顶层字段 `type`、`bootstrap: 1`、`protocol_versions: [..]` 永不改变。Worker 先只读这三项，选定版本后再按该版本解析其余字段。无共同版本时，Worker 写出固定格式 `{"type":"handshake_error","bootstrap":1,"code":"no_common_version"}` 并退出。这是唯一的固定格式例外。
- 协商后所有消息携带选定的 `v`。
- Worker 事件携带严格递增的 `seq`（每 attempt 从 1 开始）；缺号或重复是协议错误。SSE 的事件 ID 是宿主分配的每任务独立序号。
- `ts` 仅用于诊断，不决定顺序或截止时间；所有期限由宿主单调时钟执行。
- **阶段**：`awaiting_init → ready → running → terminal_sent → exited`。`ready` 之前发送 `artifact`/`checkpoint`/`result` 是协议错误；重复 `init` 或重复 `ready` 是协议错误。
- 宿主发出 `init` 后 `T_ready`（默认 30 s）内未收到 `ready` → `ready_timeout`。
- **终态提议**：`result`、`error`、`paused` 每 attempt 至多一个；其后任何业务事件均为协议违规。三者都适用 `exit_grace`（默认 10 s）：发出终态提议后到期仍未退出，宿主终止执行。
- **归属**：协议中不携带 `attempt_gen`。所有提交校验 `tasks.current_attempt_id = 本 attempt_id`；`attempt_no` 仅作显示序号。该标识作为后续跨节点所有权校验的基础。

### 3.3 消息

| 方向 | 类型 | 主要字段 |
|---|---|---|
| 宿主→Worker | `init` | bootstrap envelope + `task_id, attempt_id, attempt_no, traceparent, config, config_version, budget_limits, input_refs[], resume?{checkpoint_id, step_id, state \| state_ref, refs[]}` |
| 宿主→Worker | `checkpoint_result` | `checkpoint_id, status: committed \| conflict \| rejected \| retryable_error \| not_found, code?` |
| 宿主→Worker | `artifact_result` | `artifact_id, status: saved \| rejected, version?, sha256?, code?` |
| 宿主→Worker | `cancel` / `pause` | `reason, grace_ms`（持续时间，Worker 协作退出的时间预算） |
| Worker→宿主 | `ready` | `protocol_version, worker{name, version}, capabilities[]` |
| Worker→宿主 | `progress` | `step_id?, kind, message, data{}`。`kind ∈ {step_started, step_finished, step_failed, tool_error, …}`；可恢复的工具失败放在此处 |
| Worker→宿主 | `artifact` | `artifact_id, path, declared_sha256, declared_size, media_type, visibility: output \| internal` |
| Worker→宿主 | `checkpoint` | `checkpoint_id, step_id, state（≤256 KiB）\| state_ref, refs[sha256]` |
| Worker→宿主 | `checkpoint_query` | `checkpoint_id` |
| Worker→宿主 | `paused` | `checkpoint_id` |
| Worker→宿主 | `result` | `summary, outputs[artifact_id]` |
| Worker→宿主 | `error` | `code, message, retryable`（**仅为建议**） |

稳定错误码包括：`missing_ref`、`ref_not_authorized`、`state_too_large`、`stale_attempt`、`commit_in_flight`、`cancelled`、`artifact_too_large`、`not_regular_file`、`path_invalid`、`hash_mismatch`、`save_timeout`、`no_common_version`。

### 3.4 Checkpoint 规则

1. `state` 与 `state_ref` 必须且只能提供一个。`state_ref` 为 UTF-8 JSON，≤ 16 MiB。
2. `refs[]` 与 `state_ref` 中的每个 sha256 都必须已完整保存，并**已授权关联到当前任务**（存在于 `task_blobs`）。仅存在于 BlobStore 不足以引用。
3. 插入新 checkpoint 时分配单调递增的 `commit_seq`，并在同一事务内推进 `latest_checkpoint`。重复提交已存在的 `checkpoint_id` 只是读取：内容哈希相同 → 返回原结果；不同 → `conflict`。重试旧 checkpoint 永远不会让指针回退。
4. 每个 attempt 同时至多一个在途提交；SDK 强制，宿主对第二个返回 `commit_in_flight`。
5. 重试同一 checkpoint 使用新的事件 `seq`、相同的 `checkpoint_id`。
6. `checkpoint_query` 返回已存储结果、`not_found` 或 `retryable_error`。`not_found` 不是永久拒绝。
7. Store 超时或暂时不可用返回 `retryable_error`，不返回 `rejected`。
8. Worker 未在期限内收到结果时，用同一 `checkpoint_id` 重发或查询，不会因宿主丢弃 ACK 而永久等待。
9. 宿主写 stdin：每次写消息前设置 write deadline，写完清除。
   - 0 字节写出：未送达。**仅对 `checkpoint_result` / `artifact_result`** 视为可等 Worker 重试或查询。
   - 部分写出：控制流已损坏，关闭 stdin 并终止 attempt；新 attempt 从宿主已提交的 checkpoint 恢复。
   - `cancel` / `pause` 无法送达：升级为 `Terminate`。
   - `StartExec` 在创建时验证 `SetWriteDeadline` 可用，失败即返回错误，不忽略。
10. 恢复时，`init.resume` 原样携带 `state_ref`，不展开；Worker 通过 Gateway 读取。

### 3.5 产物

- attempt 启动时，宿主创建 `/workspace/out`，并以 `openat2(<宿主 workspace 根目录 fd>, "out", RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS, O_DIRECTORY | O_NOFOLLOW)` 打开并在整个 attempt 期间持有该目录 FD。
- 协议只接受相对、非空、无 NUL、≤ 4 KiB、不含 `.` 或 `..` 路径分量的 `path`。
- 所有 artifact 路径相对该目录 FD 解析：`RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_XDEV`，`O_RDONLY | O_NOFOLLOW | O_NONBLOCK`。
- `fstat` 必须为 `S_ISREG`（排除 FIFO、设备）。
- 从已打开的 FD 复制到临时 blob，边复制边计算哈希；`declared_sha256` / `declared_size` 是待验证数据；校验通过后原子 rename 到内容地址，再写入 `task_blobs` 与产物记录，最后发送 `artifact_result`。
- 保存有独立的超时、大小上限，且可取消。保存完成的副本是权威内容；Worker 之后对文件的修改不产生影响。
- 若 Worker 之后将 `out/` 改名，宿主持有的 FD 仍指向原目录。
- **版本**：同一 `(task_id, artifact_id, sha256)` 重复登记返回同一版本；不同内容生成新版本。`artifact_result` 返回 `{version, sha256}`。宿主处理 `result` 时，将每个输出**固定**为 `(artifact_id, version, sha256)` 并不可变地存储，后续上传不改变历史结果。

### 3.6 事件处理与完成屏障

- 读取 goroutine 持续将 stdout 读入有界队列；处理器按 `seq` 顺序处理。一个 artifact 保存完成之后，才处理其后的 checkpoint。
- 取消、超时、进程退出走独立控制路径，不等待处理器。
- **完成屏障**：收到进程退出状态后：
  - **(A) 管道收尾**：等待 stdout/stderr EOF，期限默认 5 s。超时则终止执行树（`cgroup.kill`）并标记 `output_incomplete`；末尾不完整的行丢弃。
  - **(B) 事件处理**：处理所有已完整接收的事件（含产物保存），期限 `finalize_timeout`，默认 120 s，独立于单个产物的保存超时。
  - 两阶段完成后，actor 才在事务中做最终裁决。
- 只在正常协议与正常退出路径上承诺不丢失末尾输出。

### 3.7 宿主裁决规则

Worker 只提出结果，宿主作出裁决：

| 情况 | 宿主裁决 |
|---|---|
| `result` + exit 0，所有输出已保存、协议无违规 | `succeeded` |
| `result` + 非零退出 | `failed`（`exit_after_result`） |
| `result` 后仍有事件 | `failed`（`protocol_violation`） |
| 终态提议后超过 `exit_grace` 未退出 | 终止执行，再按提议与退出原因分类 |
| `paused` + exit 0，宿主确有暂停请求，且 checkpoint 有效 | `paused` |
| 宿主的 cancel/pause 已生效后退出 | 按宿主意图（`cancelled` / `paused`），**不判为 crashed、不重试** |
| 无终态事件即退出 | 按退出原因分类，见 6.3 |
| 协议违规，或 `retryable: false` | 不重试，无论 Worker 如何建议 |

### 3.8 暂停与取消

- **暂停是协作式的**：停止安排新步骤 → 到达可提交边界 → 提交 checkpoint → 发出 `paused` → exit 0。`paused.checkpoint_id` 必须等于该任务最新的已提交 checkpoint，否则为协议违规。
- `grace_ms` 到期：宿主终止。
  - 存在已提交 checkpoint → `paused`，从该 checkpoint 恢复；
  - 不存在 → `paused`，`resume_point: initial`，UI 明示将从头重跑。
  - 该点之后的工作丢失，规格如实说明。
- **取消**：Worker 在 `grace_ms` 内停止并退出，无须提交 checkpoint；到期 → `Terminate`。

### 4.2 事务规则（SQLite `BEGIN IMMEDIATE`，写者串行化）

- **生命周期转换**同时检查版本与允许的来源状态：
  ```sql
  UPDATE tasks SET status = ?, row_version = row_version + 1
  WHERE task_id = ? AND row_version = ? AND status IN (/* 允许的来源状态 */);
  ```
  版本 CAS 检测冲突；来源状态条件保证终态不可变。
- **控制写入（API）**：
  - 事务内检查 `tasks.status` 非终态，否则返回 `task_ended`；
  - 已接受的 cancel 不可被之后的 pause/resume 覆盖（返回 `cancel_pending`）；
  - resume 要求 `status = paused`；
  - 每次接受递增 `control_version`；
  - **提交后**才向客户端确认接受，然后尽力通知 actor。actor 也在唤醒与周期检查时比较 `control_version > applied_control_version`，通知丢失不影响正确性。
- **创建 attempt**（单事务）：要求 `status = queued`、`task_control.desired = run`、不存在未停止的旧执行环境（上一个 attempt 已有 `stopped_at` 或不存在）；插入 attempt 与 `attempt_access(active)`，递增 `attempts_total`，仅当本次为故障重试时递增 `fault_retries_used`，设置 `current_attempt_id`，CAS `queued → running`。检查不通过 → 归还 admission 槽位，不创建。
- **checkpoint 提交**：要求 `attempt_id = tasks.current_attempt_id`、`tasks.status IN (running, pausing)`、`attempt.status IN (active, finishing)`、`task_control.desired ≠ cancel`（否则 `rejected: cancelled`）。
- **最终裁决**：完成屏障之后，单个事务读取 `task_control` 并写入裁决：
  - `desired = cancel` → `cancelled`；若已有固定的有效 result，额外记录 `completed_during_cancel`；
  - `desired = pause` → 按 3.8 进入 `paused` 并保存恢复点；有效 result 保留其固定产物并记录 `completed_during_pause`，但**不提交成功**；
  - `desired = run` → 按 Worker 提议、退出状态与屏障结果裁决（3.7、6.3）。
  - 产物留存承诺：**已成功保存并固定引用的产物保留；尚未完成保存的产物不保证留存。**
  - 由于取消 API 与裁决事务串行化：取消先被接受 → 不能再提交成功；成功先提交 → 取消返回 `task_ended`。
- **终态与对应的宿主事件在同一事务提交**，包括事件序号分配，通过共享的事务内事件追加函数实现。数据库与 SSE 历史不会出现分歧。

### 4.3 任务状态机

```
             grant（创建 attempt 事务）           attempt 结束 → 裁决
 queued ─────────────────────────► running ──────────────────────────► succeeded | failed
   ▲  ▲                                │  │ 故障类别且有剩余重试 → queued（not_before = 退避）
   │  │                     暂停请求   │  │ 取消请求
   │  │                                ▼  ▼
   │  │                           pausing  cancelling ── attempt 结束 ──► cancelled
   │  │                              │ attempt 结束
   │  └──── resume ────────────── paused ── cancel ──► cancelled
   ├──── queued + pause ─────────► paused（resume_point = 最新 checkpoint 或 initial；不创建 attempt）
   └──── queued + cancel ────────► cancelled
```

- cancel 优先于 pause：`pausing` 中收到取消 → `cancelling`。
- `starting` / `handshaking` 阶段收到 cancel 或 pause：尚无 `ready`，无法协作，立即停止执行，然后进入 `cancelled`，或以现有恢复点进入 `paused`。
- 重试计数分开：只有故障重试消耗 `fault_retries_used`（上限 `max_fault_retries`，`not_before` 指数退避）；暂停再恢复只增加 `attempts_total`。
- `worker_oom_likely` 的重试计入持久化的 `oom_retries_used`（上限 1）。
- `task_deadline_exceeded`：任务级累计**运行**时间超限（不含排队与暂停），新 attempt 不重置。

### 4.4 Attempt 状态机

```
created → starting → handshaking → active → finishing → ended{succeeded | failed | crashed | cancelled | paused | lost}
          （intent、     （已发 init，              （已见退出，
           建沙箱、       等待 ready）               屏障 A+B）
           StartExec）
```

- `lost` 只由 Reconciler 设置。Reconciler 无法确认旧执行树已停止时，将该 attempt 置为 `stop_blocked`（非终态，继续占用槽位并阻止替代 attempt）；确认停止后再转为 `ended{lost}`。
- `active` 之前的失败（创建错误、`ready_timeout`、`protocol_mismatch`）直接进入 `ended`，并**总是发起停止**；`ended` 不意味着 `stopped_at`。
- **清理**：`cleanup_state: pending → in_progress → done | stuck`。cleanup loop 只处理 `status = ended` 的 attempt；`stuck` 按 `next_retry_at` 退避重试并在 `inspect` 中提示需要人工处理。重启后 `in_progress` 的清理直接重做（各操作幂等）。

### 4.5 停止与最终清理

| 操作 | 允许的阶段 | 目的 |
|---|---|---|
| 停止执行树（`cgroup.kill` → `populated 0`） | starting / handshaking / active / finishing | 及时响应取消、超时与异常；**不等待 Store** |
| 最终清理（卸载、删除、关闭残留入口、释放 intent） | `ended` 之后 | 资源回收 |

- 每 attempt 的 **resource coordinator** 串行化该 attempt 的所有物理操作，各操作幂等；停止路径与清理循环都通过它提交操作，不并发卸载或删除。
- **`stopped_at` 的条件**：
  1. 不存在仍可能产生执行树的在途创建或启动操作；
  2. 已存在的执行树确认停止，或确认从未创建。
- `Create` 与 `StartExec` 有界、可取消；若在停止请求后返回，coordinator 立即补偿（停止其产物）。停止不会无限排在卡住的创建之后。
- `Create` 返回时，不留下仍在继续创建资源的后台操作；按名称幂等仅防止同名重复创建。
- **intent 规则**：资源获取操作未结束时，该 attempt 的清理不能判定为最终完成。迟到的 Create 结果触发清理；周期核对兜底；重启时根据 intent 与独立的资源扫描重新判断，**不能仅凭沙箱列表为空认定无残留**。部分创建的资源必须可被 `List` 或 intent 驱动的原始资源扫描（实例目录、挂载点、cgroup 目录）发现。`failed` 只在确认无残留时设置。
- 物理停止不等待 Store；`stopped_at` 随后持久化。Store 不可用期间，admission 保守地将未确认停止的 attempt 视为仍占用槽位，不丢失资源归属。

### 4.6 新 attempt 启动前的条件

1. 旧 attempt 的 Gateway 访问已撤销（`attempt_access.state = revoked` 已提交；listener 与连接已关闭）。
2. 旧 attempt 已有 `stopped_at`。
3. admission 已授予槽位。

不必等待历史文件删除。**每个任务至多一个可能拥有执行树的 attempt**；无法确认停止的旧环境阻止替代 attempt 启动。

### 4.7 Admission 计量

- `queued` 不占槽位。
- 槽位从授予持续到 **`stopped_at`**，而非 `ended`。
- 已停止但未清理的 attempt 计入独立的磁盘/待清理指标；超过阈值时暂停授予新槽位。
- `stop_blocked`、归属不明（隔离中）或无法核算的资源**计入占用**，不视为空闲容量。
- 启动时按核对后的实际资源重建容量，不按 `queued`/`running` 行数计算。

## 5. Gateway

### 5.1 Edge：绑定与撤销

- **每 attempt 一个 listener**：Unix socket 位于 `<data>/attempts/<attempt_id>/gw.sock`（`<data>` 默认 `/var/lib/agentbox`），作为 `listener` intent 记录，bind-mount 到沙箱的 `/run/agentbox/gateway.sock`。HTTP/1.1。每个连接以接受它的 listener 所属 `attempt_id` 标记——**Worker 从不发送身份**。
- 每 attempt 上限：16 个连接、32 个活跃请求；请求体 ≤ 4 MiB。
- **撤销**：`AttemptAccess.Revoke` 先提交 `attempt_access.state = revoked`，再关闭 listener，再关闭存活连接（通过 `http.Server.ConnState` 跟踪）。关闭 listener 只是清理，**持久化检查才是撤销的执行点**。
- 撤销时机：attempt 结束时；**取消生效时立即撤销**。暂停不撤销，因为当前步骤可能仍需 Gateway 才能到达提交边界。
- 撤销时取消该 attempt 面向 Worker 的请求上下文：
  - 原因是**用户取消**：同时取消上游 try，结果按已知程度结算或转 unknown；
  - 原因是 **attempt 结束或被替换**：上游 try 继续至期限，以便写入 journal 并结算；这些 try 仍占用任务预算与上游并发额度。

### 5.2 访问检查

- **所有请求**（包括 replay、`/v1/budget`、blob 读取）首先在一致快照中检查：`attempt_access.state = active`、`tasks.current_attempt_id = 本 attempt_id`、`task_control.desired ≠ cancel`。最后一项覆盖"取消已持久化、actor 尚未撤销"的窗口。
- 发起新调用时，在预留事务内再次检查上述条件。
- trace 信息是观测数据，不用于身份或权限判断。

### 5.3 端点

| 端点 | 说明 |
|---|---|
| `POST /v1/chat/completions` | OpenAI 兼容子集。**v0.1 拒绝 `stream: true`**；仅支持声明的 provider adapter、模型与纯文本消息 |
| `POST /v1/search` | `{query, max_results}` → 规范化结果 |
| `POST /v1/fetch` | `{url}`，仅 GET；不接受 Worker 指定的请求头或请求体 |
| `GET /blobs/{sha}` | 只读，按 `task_blobs` 限定在本任务 |
| `GET /v1/budget` | Worker 视角的剩余预算 |

- 产生费用或副作用的调用必须携带 `X-Agentbox-Call-Id`。SDK 以 `<step_id>/<kind>/<ordinal>` 确定性生成，≤ 256 字节。
- 模型与搜索结果、抓取内容保存为 blob 并加入 `task_blobs`，响应头 `X-Agentbox-Blob: <sha256>` 供后续 checkpoint 引用。

### 5.4 Journal：调用身份、指纹、重放

- `calls`：PK(`task_id, call_id`)，`fingerprint, endpoint, state (in_flight | completed | failed | unknown), result_ref, tries_used, cost_charged, first_attempt_id, upstream_request_id, supersedes_call_id?, supersede_reason?, possible_external_duplicate`。
- `call_tries`：`task_id, call_id, try_no, attempt_id, state, outcome, latency_ms, cost_micro, reservation_id`。
- **指纹**：`sha256(JCS({endpoint, adapter_version, resolved: {provider, model, applied_defaults}, body}))`，JCS 即 RFC 8785。解析器严格，**拒绝重复的 JSON 属性名**（`400 duplicate_json_key`）。
- **调用所有权绑定宿主维护的 try，而非客户端连接。** 每个逻辑调用同时至多一个由本平台执行的 try。

| 已有记录 | 相同指纹的请求 |
|---|---|
| 无 | 进入调用前事务 |
| `completed` | 返回已持久化结果，`X-Agentbox-Replayed: true`，不计费 |
| `in_flight`，宿主仍有执行中的 try（包括旧 attempt 留下的 try） | `409 call_in_progress` |
| `unknown` | 按不确定结果策略：在累计上限内新建 try |
| `failed` | 返回持久化的失败；仅当失败类别可重试、未达累计上限，且请求带 `X-Agentbox-Retry: true` 时新建 try |
| 任意状态，**指纹不同** | `409 fingerprint_mismatch`，宿主事件 `replay_divergence` |

- 旧的供应商请求可能已脱离本地控制；这种情况记为 `possible_external_duplicate`，不据此宣称外部无重复执行。
- **指纹冲突处理**：SDK 抛出 `CallDivergence` 交给编排层。编排层决定这是恢复错误，还是确实需要新调用；若接受新调用，以新 ID 发起并携带 `X-Agentbox-Supersedes: <old_call_id>` 与原因，Gateway 记录关联，新 ID 进入后续 checkpoint。**不做任何透明的自动换 ID。**
- `result_ref` 用于重放，属于任务数据，与任务同样留存，不属于审计日志。**请求体不存储**，只保留指纹。

### 5.5 两个原子提交点

**调用前事务**：检查访问与指纹 → 确认没有竞争中的 try → 检查 `tries_used` 累计上限 → 分配 `try_no` → 创建 reservation → 更新预算 → 写调用状态为 `in_flight`。**提交成功后才发起上游请求。**

**调用后**：先完整保存响应 blob → 单个事务内完成 reservation 结算、try 状态、`calls.completed` 与 `task_blobs` → 再向 Worker 返回结果。正常成功路径上不会出现"Worker 已拿到结果而宿主没有可重放记录"。

- 结算按 reservation 状态幂等（`… WHERE state = 'held'`）。超时已转 unknown 后迟到的响应，其实际用量只写入 `call_tries` 供诊断，不再次结算。
- 撤销不阻止宿主完成必要的记账；它只阻止 Worker 发起新操作或获取响应。

### 5.6 预算

- `budgets`：`task_id, limit_micro, reserved_micro, spent_micro, unknown_micro`。
- `reservations`：`reservation_id, task_id, call_id, try_no, amount_micro, state (held | settled | released | charged_unknown)`。
- **互斥记账**：每笔 reservation 只能转入 `spent`、`unknown`、`released` 之一，并同时从 `reserved` 扣除，不重复计数。
- **预留额是保守估算，不是严格费用上限**：
  - 每个 provider adapter 声明计量方法、输出上限、价格表版本；
  - 模型调用：`input_estimate × 输入单价 + max_tokens × 输出单价`；`max_tokens` 必填或由 adapter 补默认值并截断；`input_estimate` 由 adapter 定义并包含序列化的工具定义；
  - 搜索：adapter 声明按请求或按结果计价；
  - 抓取：独立配额——请求次数、响应字节、并发数，不依赖 token 预算。
- 预留条件：`limit − spent − reserved − unknown ≥ amount`，与 5.2 的访问检查同一条件更新。不满足 → `402 budget_exhausted` 或 `403 attempt_revoked`。
- **结算**：
  - 上游返回 usage → 按实际费用记入 `spent`，释放余额；实际费用超出预留时如实结算，允许出现**预算赤字**，此后阻止新调用；
  - 确定未发送（连接被拒、DNS 失败）→ 全额释放；
  - **结果未知**（发送后超时、响应中途断开、Gateway 崩溃）→ 全额预留转入 `unknown_micro`。v0.1 不自动退回；`unknown` 是保守准入策略，**不代表实际费用已被确认**。

### 5.7 重试

- **每个逻辑调用累计最多 3 次 try**，持久化于 `calls.tries_used`，覆盖 Gateway 自动重试、SDK 重连与 Worker 恢复。
- 每次 try 都重新检查：attempt 权限、剩余预算、累计次数、剩余调用期限（默认 120 s，超出向 Worker 返回 `504`）。
- 429、5xx 与发送前失败只表示**可以考虑重试**；是否收费仍依据 usage 与供应商语义，无法确定即按 unknown。
- 指数退避加抖动；遵从 `Retry-After`，但受调用期限约束。
- 并发：每任务上游在途调用 ≤ 4；每 provider 全局限额。

### 5.8 出站防护（SSRF）

1. 仅 `http`/`https`，默认端口 80/443；拒绝含 userinfo 的 URL。
2. 模型与搜索上游地址在配置中固定。**所有出站拨号走同一个验证 dialer。** 私有地址仅允许显式配置的上游（`upstream_allow_private`，例如本地 Ollama）。
3. Gateway 自行解析 DNS，拒绝 loopback、私有、link-local、CGNAT、组播、未指定地址、IPv6 ULA 及上述地址的 IPv4-mapped 形式。
4. **连接已检查的解析结果 IP**，保留原始 Host/SNI，防止 DNS rebinding。
5. 重定向最多 5 跳，每跳从第 1 步重新检查。
6. 大小上限作用于**解压后的正文**，超限立即停止读取：抓取 5 MiB / 20 s；模型与搜索响应 8 MiB。
7. 不继承代理环境变量。

### 5.9 凭据与审计

- 供应商 Key 只从宿主环境变量或文件加载到 core，从不进入沙箱，从不写入日志。
- 审计内容是 `calls` / `call_tries` 的元数据：端点、模型、token、延迟、状态、费用、上游请求 ID；不含 Key，不含提示词。

## 6. 恢复与错误处理

### 6.1 启动顺序

1. 创建/确认数据目录。
2. 在固定路径 `<data>/agentbox.lock` 获取独占 `flock`，持有至进程结束；运行中不删除、不重建锁文件。单实例约束仅适用于受支持的**本地**文件系统部署（不含 NFS 等）。
3. 打开 Store，执行 migrations。
4. 在一个事务中**撤销**所有 `active` 的 attempt 访问权限。
5. **账本转换**：遗留 `held` reservation → `charged_unknown`；`in_flight` call → `unknown`。幂等（按状态条件更新），reservation 与预算余额在同一事务内更新；连续两次恢复中途崩溃不会重复计入 unknown。
6. **扫描与核对**：`provider.List` 加独立的原始扫描（实例目录、挂载、cgroup、listener socket），逐层报告，区分完整沙箱与部分创建残留。
7. **停止**未结束 attempt 的执行树（经 coordinator）。
8. 提交 `lost`、对应事件与恢复安排（6.2）。
9. 计入运行时限的未记账区间（6.4）。
10. 按核对后的实际资源重建 admission。
11. 依次启动 cleanup loop、actor、API。

**执行就绪条件**：Store 健康，且全局启动核对、权限撤销、账本恢复及 admission 重建均已完成，才启用执行。

**资源归属**：

- 持久化的 `install_id` 同时存于 Store 与数据目录。
- 实例目录在任何挂载之前写入 `owner.json {install_id, attempt_id}`（属于创建 intent 的一部分）；cgroup 路径为 `agentbox-<install_id>/att-<attempt_id>`。
- 清理所需的归属信息在执行前已持久化；不因数据库不可读而猜测路径。

| 扫描结果 | 处理 |
|---|---|
| 确认属于本安装、但无对应记录 | 作为孤立资源回收 |
| 归属不明或信息冲突 | 写入 `quarantined_resources`，报警，**不自动销毁**，计入占用 |
| 属于其他安装 | 不操作 |

**停止失败的分支**：

- 已确认停止 → 提交 `lost`，按任务意图安排后续；
- 尚不能确认停止 → attempt 处于 `stop_blocked`：对应任务不运行，槽位保持占用，带退避继续尝试，在 `inspect` 中暴露诊断；
- Store 不可用 → 不启动 actor，不执行任何任务。

**可见性**：启动过程逐阶段写日志。超过恢复期限（默认 60 s）仍未就绪时，API 以**诊断模式**启动：只开放只读的 `status` / `inspect`，禁止执行。`stop_blocked` 只阻塞其所在任务。

### 6.2 Reconciler 对任务的处理

| 持久化情况 | 恢复行为 |
|---|---|
| cancel 已接受 | 停止旧环境 → `cancelled`，不重试 |
| pause 已接受 | 停止并清理旧环境 → `paused`，保留恢复点 |
| `desired = run`，无未完成 attempt | 保持排队，保留原有重试计数与 `not_before` |
| `desired = run`，有因本次重启丢失的 attempt | 核对并确认停止后，按故障恢复策略排队 |
| `desired = run`，此前已完成故障分类并安排重试 | 不再增加重试次数 |
| 裁决已提交 | 保留终态，只处理残留资源 |

**只有在实际创建替代性故障重试 attempt 的事务中，才递增 `fault_retries_used`。** Reconciler 只安排恢复，不提前递增。

### 6.3 故障分类（`outcome_class` → 宿主策略）

| 类别 | 是否故障重试 |
|---|---|
| `crashed_signal`（**不含平台主动终止**）、`control_lost`、`ready_timeout`、`lost_on_restart` | 是 |
| `create_failed_transient`（临时资源不足、短暂宿主错误） | 是，有界 |
| `create_failed_env`（rootfs 缺失、配置错误、内核能力不支持、权限不足） | 否，报告为环境问题 |
| `create_outcome_unknown` | 先核对资源，不直接重建 |
| `store_unavailable` | Store 恢复后是 |
| `worker_oom_likely` | 一次（持久化计数），之后失败 |
| `worker_error`，`retryable: true` | 是，除非错误码在拒绝列表中（`budget_exhausted`、`protocol_*`） |
| `worker_error` 不可重试、`protocol_mismatch`、`protocol_violation`、`output_limit_exceeded`、`exit_after_result` | 否 |
| `task_deadline_exceeded` | 否（任务级终止原因） |
| `cancelled`、`paused`、`completed_during_*` | 非故障 |

- 平台主动发出的 SIGKILL（取消、超时、清理）按其原因分类，不归入 `crashed_signal`；`platform_killed` 与 OOM 诊断并列记录。
- **OOM 只作资源诊断**：`ResourceDiag.OOMKillDelta > 0` 说明该 attempt 内发生过 OOM kill，不说明受害进程。被 SIGKILL 且 `OOMKillDelta > 0` → `worker_oom_likely`；Worker 正常退出但 `OOMKillDelta > 0` → 按 Worker 结果裁决，另记 `oom_observed_in_attempt` 诊断事件。
- 所有重试同时受 `max_fault_retries` 与 `not_before` 约束。
- Gateway 的调用超时按 5.7 处理，与任务级时限分开。

### 6.4 累计运行时限

- 运行时间 = attempt 持有执行环境的时间（从 `starting` 到 `stopped_at`），不含排队与暂停。
- actor 以单调时钟计时，每 10 s 持久化到 `tasks.run_time_ms` 与 `run_time_persisted_at`。
- 重启后，从上次持久化时刻到恢复时刻的**未记账区间按墙钟差全额计入**（保守策略）。反复杀死 server 不会重置或少计运行时限。

### 6.5 Store 故障

- 每个 Store 操作有超时（默认 2 s）。连续失败达到阈值（N = 5 次或 T = 30 s）→ attempt 以 `store_unavailable` 终止。
- AttemptRunner 中每个 channel 发送都 `select` 在 `ctx.Done()` 上，取消能解除阻塞。
- 即使 Store 不可写，也先完成物理终止与不依赖数据库写入的清理；状态持久化失败交由 Reconciler 与周期核对修复，不为写入失败原因而阻塞回收。

### 6.6 诊断

- **全链路标识**：所有日志为结构化 JSON，携带 `task_id`、`attempt_id`，适用时携带 `step_id`、`call_id`、`try_no`。
- **Trace**：`init` 提供父上下文；SDK 为每个步骤与工具调用创建子 span，并在请求中传播**当前**上下文；Gateway 在其下创建 call/try span。宿主根据 `step_started / step_finished / step_failed` 事件构建步骤 span，其余 `progress` 作为 span event。宿主权威绑定 task/attempt，不信任 Worker 通过 trace 属性改写归属。
- 导出：配置时走 OTLP，否则写本地 JSONL（按大小轮转，64 MiB × 5）。导出队列有界，满时丢弃并计数；OTLP 不可用、写盘失败或磁盘不足**不得阻塞任务终止与清理**。
- **`agentbox inspect <task_id>`** 输出单一时间线：attempt 及其 outcome class、退出与 OOM 诊断、清理状态、checkpoint、调用与 try 及费用、预算变动。故障复盘以此为证据来源。

### 7.1 测试分层

**环境与可重复性**

- Linux 测试先运行环境自检：cgroup 控制器、所需内核接口（`openat2`、`cgroup.kill` 等）、挂载与 namespace 权限。**发布门禁不把环境不支持导致的 skip 计为通过。** 若托管 runner 不满足要求，改用固定的 Linux runner。
- 随机竞态测试记录 seed，失败可重放。关键顺序用**确定性屏障**覆盖；1000 次随机测试作为补充。
- 故障注入点只在 `faultinject` 构建标签下编译（如 `before_commit`、`after_upstream_send`、`before_stop_confirm`）。涉及外部事实的注入点由 fake upstream 确认（例如确认已收到请求），不以 hook 名称代替外部事实。
- 至少保留一条**不带 `faultinject`** 的发布构建冒烟测试。

### 7.2 不变量检查（`agentbox verify-invariants`）

每个故障实验之后运行。资源检查**独立扫描实际目录、挂载与 cgroup**，不只从数据库记录推导。

1. 清理状态为 `done` 的 attempt 不存在任何挂载、cgroup 或 listener。
2. 每个任务至多一个可能拥有执行树的 attempt；无法确认停止的旧环境存在时，没有替代 attempt 在运行。
3. `reserved_micro` 等于 `held` reservation 之和；每笔 reservation 恰在一个桶中。
4. 每个任务的事件 `task_seq` 连续。
5. 每个固定的输出都以正确哈希存在于 `blobs`。
6. 每个已提交 checkpoint 的 state 与 refs 都存在、完整，且属于该任务授权范围；`latest_checkpoint` 未回退。
7. 每个任务至多一个有效访问身份；恢复完成后，旧 attempt 无法再调用或提交。
8. 每个隔离资源都已报警。

### 7.3 故障实验

| # | 注入 | 必须成立 |

| 1 | 第 2 个 checkpoint 提交后杀死 Worker | 新 attempt 从 checkpoint 2 恢复；`fault_retries_used = 1`；产物完整 |

### 7.4 性能测量（`bench/`）

- **分阶段**：排队等待；创建 → init 就绪；Worker 启动 → `ready`；Gateway 转发开销（fake upstream 零延迟）；`cancel → stopped_at`（停止延迟）；`cancel → cleanup done`（完整回收成本）。
- **cold 的定义**：每次新建沙箱与 Worker。是否清空宿主文件缓存另行说明；新进程启动不等同于宿主冷缓存。
- 每个并发度（1 / 8 / 32）200 个样本；报告 P50 / P95 / P99 与失败率，**保留原始数据**并注明样本量（P99 在该样本量下估计不稳定）。附环境说明：内核、CPU、内存、WSL2 或裸机。
- sim-worker 立即发出 `ready`，以单独测量 Runtime；deepresearch 的 `ready` 时间单独报告（Python 导入成本是另一类瓶颈）。
- 不把模型响应延迟算作 Runtime 启动延迟。
- 输出 JSON 与生成的 markdown 表，README 引用。

| G6 预留—结算、未知全额保守计费 | 两个原子提交点；互斥记账；幂等结算；启动账本转换 | 实验 3、5；不变量 3 |

## 9. 对 M1 计划的修订

在完成 M1 Task 6–11 时合入：

1. **Task 7**：`reapLoop` 改为在 `reg.mu` 下执行 `Wait4` + 查表 + 删除登记，维护 `pid → exec_id` 登记表；锁内仅非阻塞入队；`EINTR` 重试。
2. **Task 8**：控制通道改用 `SOCK_SEQPACKET`；以 `StartExec` / `ExecHandle` 替代阻塞式 `Exec`；SCM_RIGHTS 传递三个管道 FD 及完整失败协议（2.4）；`os.StartProcess` 启动，不用 `exec.Cmd.Wait`；非阻塞终止。
3. **Task 9**：`provider.Create` 按名称幂等，写入 `owner.json` 后再挂载；`Create` 有界、可取消，返回时不留后台操作；新增 `ResourceDiag`（读取 cgroup `memory.events`）。
4. **Task 10**：Close 以 `cgroup.kill` + `cgroup.events populated 0` 判定执行树清空，不依赖 Pdeathsig。
5. **Task 11**：`List` 能报告部分创建的资源；提供逐层的原始资源扫描。

## 11. 已知局限与信任边界

- 容器级隔离，共享宿主内核；内核漏洞即逃逸面。
- API、Gateway 与特权 Runtime 共处一个进程，控制面未做最小权限分离。
- 能访问 Gateway socket 的任意沙箱内代码，在撤销前拥有该任务范围的 Gateway 能力；生成代码与编排 Worker 的隔离在 v0.2 处理。
- 不保证 exactly-once 外部调用；`possible_external_duplicate` 如实记录。
- 预算是保守估算，可出现赤字；`unknown` 费用不自动退回，也不代表费用已确认。
- 单实例锁仅适用于本地文件系统。
- 不做 blob 垃圾回收。
- v0.1 不支持模型流式响应。
