## 0. 证据边界

| 证据类型 | 证明什么 | 不证明什么 |
|---|---|---|
| CI 确定性测试与故障实验（fake upstream、fault hook） | 在注入的故障下，恢复、记账、回收、仲裁逻辑符合规格 | 生产故障分布；真实供应商计费语义 |

| 性能报告 | 在注明环境、样本量下的分布 | 性能"达标"；其他环境的表现；隔离强度 |

## 1. 目标与边界

### 1.1 发布主张

一个单执行主机上的 Agent Runtime：Go 负责执行与权限边界，Python 负责研究编排。长任务在隔离环境中运行，供应商凭据不进入沙箱，模型生成的代码在独立沙箱中执行，Worker 故障后从已提交进度恢复，会话可冻结与驱逐后重建，受限的并行子研究共享预算并可取消，所有故障可从 `task_id` 追到 `call_id`。

### 1.2 对外保证

| 编号 | 保证 |
|---|---|
| G1 | Worker 与生成代码分别运行在独立的 namespace + cgroup 环境中；环境回收以整个执行树清空为准 |
| G2 | 宿主已提交的 checkpoint 不丢失、不回退；故障后新 attempt 从最近一次已提交 checkpoint 恢复 |
| G3 | 沙箱中不注入供应商 API Key；所有外部访问经由 Gateway；exec 环境无 Gateway 入口、无网络 |
| G4 | 已撤销的 attempt 不能再发起调用、读取结果或提交状态 |
| G5 | 已完成且指纹一致的调用在恢复后由 journal 重放，不再访问上游 |
| G6 | 费用按"预留—结算"记账；结果未知按全额预留保守计入；task 与 sub-run 两层账本一致 |
| G7 | 任务终态唯一且不可变；已接受的取消不会被成功结果覆盖；sub-run 终态不可回退 |
| G8 | 控制面重启后按持久化意图恢复，不遗留、不重复执行环境；失去所有权时停止执行并退出 |
| G9 | 会话的成功任务与 session 状态推进原子提交；冻结不等于释放内存，驱逐后可从已提交状态重建 |
| G10 | 缓存不改变已记录的调用结果；缓存条目完整性受校验；Redis 故障只影响延迟与费用 |
| G11 | 每次失败可经 `task_id → attempt_id → subrun_id → step_id → call_id → try_no` 定位，由 `agentbox inspect` 汇总 |
| G12 | 事件流续传无缺失、无重复，不触发重新执行；创建与控制请求按 `request_id` 幂等 |

### 1.3 不保证（明确声明）

- **不保证 exactly-once 外部调用或 exec。** 结果未持久化前崩溃，恢复后可能重复；记为 `possible_external_duplicate` / exec 重跑，不被掩盖。重跑的 exec 可能产生不同结果。
- **不保证严格费用或资源上限。** 预留是保守估算加余量；实际超出时如实结算，账本可出现赤字并阻止新的付费操作。
- **不防御内核级逃逸。** 容器级隔离，共享宿主内核。权限边界测试是回归测试，不是"无逃逸"证明。
- **不在编排 Worker 内部提供对抗恶意代码的隔离。** 编排 Worker 是可信平台代码；能访问 Gateway socket 的代码在撤销前拥有该 attempt 范围内的 Gateway 能力。凭据隔离 ≠ 无调用权限。
- **不保证跨主机故障接管。** 单执行主机、固定数据目录。
- **不实现控制面最小权限分离。** API、Gateway 与特权 Runtime 共处一个进程；服务本身不是 rootless。
- **不保证模型 token 流式输出。** 进度 SSE 是任务事件流。
- **缓存签名不保证新鲜度或可用性，不防止有效期内合法旧条目被重放。**
- **持久 workspace 不随 checkpoint 回滚。**

### 1.4 非目标

多节点与跨主机接管、MicroVM、消息队列、跨任务请求合并与后台缓存刷新、notebook 式有状态 exec、递归多 Agent、跨会话长期记忆、blob 垃圾回收。

## 2. 术语与实体

| 实体 | 含义 |
|---|---|
| **task** | 一次用户提交的工作，可选属于一个 session |
| **attempt** | task 的一次执行尝试；在某个 environment 中运行 |
| **session** | 会话：有序的多个 task、持久 workspace、session 状态（经 session checkpoint 提交） |
| **incarnation** | 常驻编排 Worker 进程的一次生命周期；v0.2 中与其 environment 一一对应 |
| **environment** | 物理沙箱及其资源生命周期。`kind ∈ {task, session, exec}`：独立 task 的每个 attempt 一个 `task` 环境；session 的每个 incarnation 一个 `session` 环境；每次 exec 一个 `exec` 环境 |
| **sub-run** | 同一 task 内、可信编排进程中的并发研究单元；调度与资源治理单位，不是安全边界 |
| **call / try** | Gateway 上的逻辑调用及其一次实际上游执行 |
| **reservation** | 一次 try 的费用或配额预留 |
| **checkpoint** | 宿主提交的应用进度；`scope ∈ {task, session}` |
| **scope** | blob 授权范围：`(task, task_id)` 或 `(session, session_id)` |

**执行所有权规则**（全文统一）：

- 每个 task 至多一个**可能拥有执行树**的 attempt。
- 故障恢复或替换：旧 environment 必须撤销访问并确认停止（`stopped_at`），才创建替代执行。
- session 正常切换任务：同一 incarnation 在上一任务**释放**（12.4）后可复用。
- 无法确认停止的旧环境阻止替代执行启动。

## 3. 架构

### 3.1 部署与进程模型

单执行主机，固定数据目录 `<data>`（默认 `/var/lib/agentbox`），一个 `agentbox server` 进程，外部依赖 PostgreSQL（唯一元数据存储）与 Redis（仅缓存）。最小运行方式为 `docker compose up`（PostgreSQL + Redis）加本机 server。

```
CLI / Vue ── REST + SSE ──► agentbox server（单进程，特权）
                            ├─ api          OpenAPI；request_id 幂等；SSE
                            ├─ task         每 task 一个 actor
                            ├─ session      每 session 一个 actor
                            ├─ admission    全局：run slots / 环境内存 / exec slots
                            ├─ runner       AttemptRunner：执行流唯一读取者、事件处理、完成屏障
                            ├─ coordinator  每 environment 串行化物理操作
                            ├─ store        PostgreSQL（pgx）
                            ├─ blob         本地内容寻址 BlobStore
                            ├─ cache        Redis 客户端（可降级）
                            ├─ gateway/edge 每 incarnation/attempt 的 Unix listener、连接绑定、撤销
                            ├─ gateway/core 访问检查、journal、两层预算、上游、exec 调度
                            ├─ reconcile    启动核对 + 周期清理
                            └─ provider/local  namespace + cgroup + init（M1）
                                   │
              ┌────────────────────┴───────────────────────┐
     编排环境（task / session）                        exec 环境
     python Worker（可信），stdin/stdout 协议            生成代码，无协议
     /run/agentbox/gateway.sock                          无 Gateway socket
     /workspace/{attempt,session,out}                    /in（只读）、/out（tmpfs）
     独立 netns 仅 lo                                    独立 netns 仅 lo
```

### 3.2 并发模型与写入所有权

| 组件 | 负责 | 不做 |
|---|---|---|
| task actor | task/attempt 生命周期决策；异步发起创建、启动、等待，结果以带 `attempt_id` 的消息返回 | 阻塞 I/O |
| session actor | session 生命周期、incarnation 创建与替换、授予 session 内 attempt 创建 | task 生命周期 |
| admission | 三维容量：run slots、环境内存、exec slots | 单任务决策 |
| AttemptRunner | 读取执行流、按序处理事件、完成屏障 | 写生命周期字段 |
| gateway/core | 访问检查、journal、预算、exec 调度，经 Store 原子操作 | 让请求经过 actor |
| coordinator | 串行化单个 environment 的物理操作；写 `stopped_at`、intent | 决定任务状态 |
| Reconciler | 启动阶段运行完毕后才启动 actor 与 API | 与 actor 同时修改同一对象 |
| cleanup loop | 只写 `cleanup_*` 列 | 写生命周期字段 |

**过期结果规则**：异步结果携带不可复用的 `attempt_id` / `env_id`。若已非当前，不得改变状态；携带的资源转交清理，admission 授予归还。

### 3.3 依赖关系与包划分

包名、职责、允许的依赖、事务用例接口与所有权以 [代码组织设计](2026-10-03-code-organization.md) 为准。本节的组件名与包的对应：coordinator 与 cleanup loop → `internal/resource`；Gateway core → `internal/gateway/call`、`upstream`、`cache`；Store → `internal/persistence/postgres`（各消费者定义窄接口）；Reconciler → `internal/reconcile`（生成 `RecoveryPlan`）与 `internal/recovery`（执行计划），二者都不调用 actor。

## 4. Runtime

### 4.1 `StartExec` 与执行句柄

M1 计划中的阻塞式 `Exec` 不适合长驻 Worker；另据计划文本，Task 7 的 `reapLoop`（`Wait4(-1)`）与 Task 8 的 `exec.Cmd` 等待会争抢同一子进程的退出状态（依据代码判断，未复现）。替代为：

```go
StartExec(ctx, envID, ExecSpec) (ExecHandle, error)

type ExecHandle interface {
    Stdin()  io.WriteCloser
    Stdout() io.ReadCloser
    Stderr() io.ReadCloser
    Wait() (ExitStatus, error)          // 进程退出状态或控制连接错误
    Terminate(grace time.Duration) error
}
type ExitStatus   struct{ Code int; Signal syscall.Signal }
type ResourceDiag struct{ OOMKillDelta uint64; OOMObserved bool; CPUUsageUsec uint64 }  // 由 Runtime 读取环境 cgroup
```

`AttemptRunner` 是 stdout/stderr 的唯一读取者。Runtime 不解析 JSONL、不写 Store。

### 4.2 控制通道

- socketpair 使用 `SOCK_SEQPACKET`；一条消息一帧，帧 ≤ 64 KiB，`spec` ≤ 32 KiB；进程数据不经控制通道。
- 每端一个写 goroutine 经队列串行写出。
- `start{exec_id, spec}` 与三个管道 FD 在同一 `sendmsg` 中传递。接收使用 `recvmsg(MSG_CMSG_CLOEXEC)`，检查 `MSG_TRUNC` 与 `MSG_CTRUNC`；`start` 必须恰好 3 个 FD，其他消息 0 个；任何违规关闭全部已收 FD 并按协议错误处理。
- 宿主在 `sendmsg` 返回后总是关闭子端副本；发送失败时同时关闭父端。init 在启动返回后关闭其副本。
- 回复 `start_ack{exec_id, pid}` / `start_err{exec_id, reason}`。ACK 前连接断开 → `ErrControlLost`，attempt 失败并拆除环境。

### 4.3 进程启动与收割

- init 是沙箱内子进程的唯一 reaper；宿主等待自己启动的 init。
- 一把锁 `reg.mu` 覆盖：**启动**（启动 → 登记 `pid → exec_id` → 入队 `start_ack`）与**收割**（循环 `Wait4(-1, WNOHANG)` → 查表 → 删登记 → 入队 `exit`，直至 0 或 `ECHILD`；`EINTR` 重试，其他错误显式处理）。
- 锁内只做非阻塞入队；队列溢出视为控制通道故障并终止环境。由于 ACK 在锁内先入队、写出 FIFO，`start_ack` 必先于对应 `exit`；宿主仍防御性暂存先到的 `exit`。
- 不调用 `Process.Wait` / `exec.Cmd.Wait`。workload 经 stage-2 helper 启动（4.6）。

### 4.4 终止与回收

- `Terminate`：init 向进程组发 SIGTERM，设定计时器，继续服务控制循环，到期 SIGKILL。
- 环境回收以执行树清空为准：`cgroup.kill` → `cgroup.events` 中 `populated 0`（覆盖整个子树）→ 卸载 → 删除 cgroup → 删除目录。
- **停止**（任何阶段可发起，不等待 Store）与**清理**（`ended` 之后，经 coordinator）分离。`stopped_at` 条件：无在途创建/启动操作；已有执行树确认停止或确认从未创建。`Create`/`StartExec` 有界、可取消，停止请求后返回的产物立即补偿停止。

### 4.5 隔离配置（所有环境）

| 项 | 编排环境（task / session） | exec 环境 |
|---|---|---|
| user namespace | 独立 UID/GID 范围（默认 4096）；session 在整个生命周期保留其范围 | 每个环境独立范围 |
| rootfs | 模板只读 bind，`ro,nosuid,nodev` | 同左 |
| 可写区域 | `/tmp`、`/run`（限额 tmpfs）；`/workspace/{attempt,session,out}`（宿主创建并 chown 到映射 UID） | `/tmp`（tmpfs）；`/out`（tmpfs，`size=64M,nr_inodes=1024`） |
| 只读输入 | — | `/in` |
| 网络 | 独立 netns，仅 `lo`；bind-mount 的 Gateway socket（属主为映射 uid 1000，0600） | 独立 netns，仅 `lo`；无 Gateway socket |
| `/proc` | 见下方掩蔽清单 | 同左 |
| `/sys`、cgroupfs | 不挂载 | 不挂载 |
| 资源 | `pids.max`、`memory.max`、`memory.swap.max=0`、`cpu.max`；`RLIMIT_CORE=0`、`RLIMIT_NOFILE` | 同左，另 `RLIMIT_FSIZE` |
| 磁盘 | workspace 无硬配额：监控，超阈值告警后终止（已知局限） | `/out` tmpfs 即配额 |

- 运行时不支持安装软件包，依赖预装进镜像。不提供可写 rootfs 选项。
- **workspace 的宿主侧准备（执行中修订，Plan 2 Task 13）**："宿主创建并 chown 到映射 UID"的实现：每次启动环境前，provider
  把 workspace 连同其中全部条目（不跟随符号链接）chown 到该环境的映射 uid/gid 1000（宿主 `UIDBase+1000`；同一任务的后续 attempt
  可能换 UID 范围）；runner 新建的 `out/<attempt>` 目录归 workspace 属主。沙箱 init 以 user namespace 中的映射 root 运行，对宿主
  root 所有的上级目录只有"其他人"的权限，因此数据目录与 `<data>/workspaces` 以 **0711** 建立（可穿越、不可列出；已有 0700 目录补 o+x），
  provider 启动前校验每个上级目录都有 o+x。
- **不提供 `/dev/shm`**（环境限制）：依赖 POSIX 共享内存的用法（如 Python `multiprocessing` 的部分同步原语）不可用。目前没有必需且经过验证的 Worker 场景依赖它；出现明确依赖时再加入，并同时规定限额、挂载权限与资源测试。
- `/proc` 掩蔽（`internal/sandbox/procmask.go`）：掩蔽 `/proc/acpi`、`/proc/asound`、`/proc/kcore`、`/proc/keys`、`/proc/latency_stats`、`/proc/timer_list`、`/proc/timer_stats`、`/proc/sched_debug`、`/proc/scsi`；只读 `/proc/bus`、`/proc/fs`、`/proc/irq`、`/proc/sys`、`/proc/sysrq-trigger`。
- **UID 范围回收**：只有当环境清理完成、范围拥有的文件已不存在（session workspace 在关闭时删除；exec tmpfs 已卸载）、无残留挂载时才归还；存疑则隔离该范围。
- 这是特权 Runtime 用 user namespace 隔离 workload，服务本身不是 rootless。

**seccomp**（`orchestrator` 与 `exec` 两套配置，纯 Go 生成 BPF）：

- **默认动作：允许；显式拒绝列表**（返回 `EPERM`，`clone3` 除外）。
- 首先检查 `seccomp_data.arch`：仅支持原生 `x86_64` 与 `aarch64`；其他 ABI（含 i386 compat、x32 的 `__X32_SYSCALL_BIT`）→ `SECCOMP_RET_KILL_PROCESS`。
- 拒绝：`mount`、`umount2`、`pivot_root`、`unshare`、`setns`；`clone` 带任何 `CLONE_NEW*` 标志；`ptrace`、`process_vm_readv/writev`；`bpf`、`perf_event_open`、`userfaultfd`、`io_uring_setup/enter/register`、`keyctl`、`add_key`、`request_key`、`open_by_handle_at`、`init_module`、`finit_module`、`delete_module`、`kexec_load`、`kexec_file_load`；`socket()` 除 `AF_UNIX` 外的所有地址族。
- **`clone3` 整体返回 `ENOSYS`**（seccomp 不能解引用其结构体参数），依赖 glibc 回退到 `clone`；spike 验证 Python 线程与 `subprocess` 正常。
- 这是适配工作负载的拒绝列表，配有回归测试，不是"无逃逸"证明。

### 4.6 降权启动序列

> 状态：按 Plan 1B spike 结论回写（[实验记录](../experiments/2026-10-05-spike-1b.md)，WSL2 内核 6.6.87.2、x86_64 上 16.2 全部通过）。
> 本节是实验验证过的序列；生产实现须另外满足本节末尾的**实现门槛**并通过 16.2 的生产验收，二者分开判定。

```
宿主 server：分配 UID/GID 范围与 cgroup；以 re-exec 启动专用启动进程（每个环境一个，短生命周期）
→ 专用启动进程（root）：清空自身附加组并断言 Groups 为空（server 进程与其他任务的凭据不变）
→ clone（CLONE_INTO_CGROUP）：NEWUSER|NEWNS|NEWPID|NEWUTS|NEWIPC|NEWNET；
   启动进程依次写 setgroups=deny → gid_map → uid_map；子进程在 ns 内 setgid(0)/setuid(0)（不调用 setgroups）后 execve init
→ init（ns uid 0）：
   控制 socket 立即以 F_DUPFD_CLOEXEC 移到高位并关闭原 fd（ExtraFiles 继承时不带 FD_CLOEXEC）
   mount("/", MS_REC|MS_PRIVATE)
   rootfs：新挂载 API——open_tree(OPEN_TREE_CLONE|AT_RECURSIVE) → mount_setattr(AT_RECURSIVE, RDONLY|NOSUID|NODEV,
     MS_PRIVATE)（树游离时设置）→ move_mount；/in 同法。回退：mount(2) MS_BIND|MS_REC 后逐个子挂载 remount ro。
     不采用"clone 前宿主侧挂载"：宿主可见，且 pivot_root 视其为锁定挂载
   tmpfs：/tmp、/run（限额）；exec 环境 /out；/dev = tmpfs + bind null/zero/random/urandom 后 remount ro
   编排环境 bind Gateway socket（属主为映射 uid 1000，0600）；session bind workspace
   新 proc 实例（nosuid,nodev,noexec）→ 4.5 掩蔽清单（目录：只读空 tmpfs；文件：bind /dev/null）→ 只读路径
   打开 helper 二进制 O_PATH|O_CLOEXEC 并移到高位（pivot_root 之前）
   pivot_root(".", ".") → umount2(".", MNT_DETACH) → chdir("/")
   全部线程：bounding = {KILL, SETUID, SETGID, SETPCAP}；permitted = effective = {KILL}；inheritable = 0；不设 securebits
→ 每个 workload（持 reg.mu）：
   recvmsg(MSG_CMSG_CLOEXEC) 恰好 3 个 FD；exec-status 管道 pipe2(O_CLOEXEC)；源 FD 全部移到高位
   阻塞全部信号 → clone(SIGCHLD) → 子进程：dup3 到 0/1/2 与 3（exec-status），setpgid(0,0)，清空信号掩码，
     execveat(helper_fd, "", AT_EMPTY_PATH)
   stage-2 helper（CGO_ENABLED=0；LockOSThread；身份与能力调用经 AllThreadsSyscall 作用于全部线程）：
     PR_SET_NAME → fd 3 设 FD_CLOEXEC，close_range(4, ~0, CLOSE_RANGE_CLOEXEC)
     → 清空 bounding → 设置并锁定 securebits（NOROOT|NO_SETUID_FIXUP 及其 LOCKED 位）
       （必须在 setresuid 之前：切换 UID 后 CAP_SETPCAP 不可用；不能在 init 中设置：否则 helper 经 execveat 拿不到能力）
     → setresgid/setresuid(1000) → 显式清空 eff/prm/inh 与 ambient → 显式设置 RLIMIT_NOFILE 等（4.5）
     → no_new_privs → seccomp(SECCOMP_FILTER_FLAG_TSYNC，clone3 → ENOSYS) → execve workload
   init：exec-status 管道有数据 → start_err{reason}；EOF 无数据 → 结合 reaper 的 wait 状态按下方"exec 提交点"判定后才 start_ack
→ 任何步骤失败：init 阶段 → 环境创建失败；workload 阶段 → start_err，workload 不运行
```

实验得出的两处修正（相对原候选序列）：**附加组在 clone 之前、宿主侧清空**——`setgroups=deny` 之后命名空间内不能再调用
`setgroups`，而 Go 的 `SysProcAttr.Credential{Groups: []}` 在该配置下静默跳过，宿主的组 0 会留在 workload 中；**securebits
在 helper 中、`setresuid` 之前设置并锁定**。失败行为表（init 9 个注入点、每次启动 12 个注入点，workload 均未运行）见实验记录 §8。

**实现门槛（生产启动路径验收的前提）：**

1. **进程级凭据边界**：清空附加组只在专用启动进程中进行。Go server 不得为启动沙箱改变自身凭据（`setgroups` 等经
   `AllThreadsSyscall` 作用于整个进程），也不得影响其他任务的启动。
2. **exec 提交点与启动判据**（2026-10-05 决定，见 [决策说明](2026-10-05-startup-success-decision.md)）：
   - **提交点定义**：helper 的 `execve(workload)` 返回成功（内核已替换进程映像）即为"已启动"。`start_ack` 是"启动路径到达
     提交点"的证据，**不是** workload 首条指令已执行的证明（与 runc 的 exec.fifo 提交点一致）。
   - **判据组合**（不单凭管道 EOF、不依赖进程名、不轮询）：(a) 降权任一步或 `execve` 失败 → helper 经 O_CLOEXEC 的 exec-status
     管道写 `helper/<step>: errno` 后 `exit(126)`，init 读到字节 → `start_err`，workload 未运行；(b) `execve` 成功 → 内核因
     CLOEXEC 关闭管道，init 读到 EOF 无字节；(c) init 同时取 reaper 对该子进程的 wait 状态：EOF 无字节且子进程存活或以非 126
     退出码正常退出 → `start_ack`（随后才投递其 `exit`）；EOF 无字节且子进程以信号终止、且 reaper 记录该终止早于或等于 EOF
     观察 → `start_err{helper/died_before_exec}`。
   - **EOF 与 wait 的内核顺序（实现必须处理）**：进程死亡时内核先置 `PF_EXITING`、再关闭其 FD（产生管道 EOF）、最后才使其可被
     wait；因此 reaper 的终止记录必然晚于 EOF。init 在 EOF 无字节时**读一次** `/proc/<pid>/stat` 的**状态与标志字段**（跳过最后一个
     `)` 之后解析，绝不读取进程名字段）：状态为 Z/X 或标志含 `PF_EXITING` → 阻塞等待 reaper 记录后按 wait 状态分类；否则进程
     存活 → `start_ack`。ENOENT（已被收割）→ 直接用记录。不循环、不轮询。
   - **顺序**：`start_ack` 必须先于同一 exec 的 `exit` 投递；reaper 持登记表锁时的事件投递非阻塞；判定过程中不持 `reg.mu`。
   - **残余竞争窗口（显式承认，不 overclaim）**：helper 在写完最后一步与 `execve` 返回之间被 SIGKILL，与 workload 在 `execve`
     返回后立即被 SIGKILL，在"EOF 无字节 + 信号终止"上不可区分；按提交点归为 `died_before_exec`。消除它需要内核正向 exec 事件
     （ptrace 或 seccomp user-notif），已评估并**不采用**（需扩大 init 能力集、复杂度高、本环境无法验证）。
   - init 能力集保持 permitted = effective = {KILL}，**不扩展**。
3. helper 以 `CGO_ENABLED=0` 构建（cgo 下 `AllThreadsSyscall` 返回 ENOTSUP），构建与 CI 固定此设置。
4. `hostcheck` 检查新挂载 API 与 `close_range` 可用。

## 5. Worker 协议 v1

### 5.1 通道

| 通道 | 方向 | 用途 |
|---|---|---|
| stdin | 宿主→Worker | 控制消息 JSONL |
| stdout | Worker→宿主 | 事件 JSONL |
| stderr | Worker→宿主 | 日志（宿主保留最后 64 KiB） |
| `/run/agentbox/gateway.sock` | Worker→Gateway | 全部外部访问与 exec |

### 5.2 模式与协商

- 镜像清单 `/etc/agentbox/worker.json` 声明支持的模式（`task`、`session`）与扩展（`subruns`）。宿主据此在启动前选择模式。
- `init` 的 bootstrap envelope `type`、`bootstrap: 1`、`protocol_versions: [..]` 永不改变；Worker 先只读这三项，选定版本再解析其余字段。无共同版本 → Worker 输出固定格式 `{"type":"handshake_error","bootstrap":1,"code":"no_common_version"}` 并退出。
- `ready` 必须确认 `protocol_version`、`mode`，以及使用到的扩展（`session_ext: 1`、`subruns: 1`）。不一致 → 在发送任何任务前拒绝该 Worker。
- task 模式即基础 v1；session 与 sub-run 是经协商的增量扩展。

### 5.3 公共规则

- 协商后所有消息携带选定的 `v`；Worker 事件携带严格递增的 `seq`（task 模式每 attempt、session 模式每 incarnation，从 1 开始）；缺号或重复为协议错误。
- `ts` 仅用于诊断；所有期限由宿主单调时钟执行。
- 同一主版本内未知字段忽略、**未知消息类型为错误**；破坏性变更进入 v2。
- 阶段：`awaiting_init → ready → running → (task 模式) terminal_sent → exited`。`ready` 前发送 `artifact`/`checkpoint`/`result` 为协议错误；重复 `init` 或 `ready` 为协议错误。`T_ready` 内无 `ready` → `ready_timeout`。
- **终态提议** `result`、`error`、`paused`：每 attempt 至多一个，其后该 attempt 的业务事件为违规。task 模式下提议后 `exit_grace` 内须退出；session 模式下提议结束的是 attempt 而非进程。
- 归属校验：提交检查 `tasks.current_attempt_id = attempt_id`。该标识是后续跨节点所有权校验的基础。

### 5.4 消息

### 5.5 Checkpoint 规则

1. `state` 与 `state_ref` 必须且只能提供一个；`state_ref` 为 UTF-8 JSON，≤ 16 MiB。
2. `refs[]`、`state_ref`、`subruns[].result_ref` 中每个 sha256 都必须已完整保存并**授权到当前 scope**（`scope_blobs`）。scope 由宿主按 attempt → task → session 推导，Worker 不能指定。
3. 插入新 checkpoint 时分配单调 `commit_seq` 并同事务推进指针；重复提交已存在的 ID 只是读取：内容哈希相同返回原结果，不同返回 `conflict`。重试旧 checkpoint 不回退指针。
4. 每 attempt 同时至多一个在途提交（SDK 强制；宿主返回 `commit_in_flight`）。SDK 由单一状态所有者生成共享状态与各 sub-run 状态的一致快照。
5. 重试使用新 `seq`、相同 `checkpoint_id`。`checkpoint_query` 返回已存储结果、`not_found` 或 `retryable_error`。Store 暂不可用返回 `retryable_error`。
6. checkpoint 中的 `subruns[]` 须是合法状态转换：终态不可回退；已 `cancel_requested`/`cancelled` 的 sub-run 不能被改为 `completed`（`invalid_transition`）。
7. **session scope 只能经当前 task 的 `result.session_state` 提议写入**（12.3），任务执行期间不提交 session checkpoint；`quiesce` 不生成新 checkpoint。
8. 宿主写 stdin：每条消息前设置 write deadline，写完清除（`StartExec` 创建时验证 `SetWriteDeadline` 可用）。0 字节写出 → 未送达，仅对 `checkpoint_result`/`artifact_result`/`task_outcome` 可等待 Worker 重试或查询；部分写出 → 控制流损坏，关闭 stdin 并终止；`cancel`/`pause`/`subrun_cancel_requested` 无法送达 → 升级终止。
9. 恢复时 `state_ref` 原样传递，不展开。

### 5.6 产物

- 每个 attempt 有独立 `out_dir = /workspace/out/<attempt_id>`。宿主创建并以 `openat2(<宿主 workspace 根 fd>, "out/<attempt_id>", RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS, O_DIRECTORY|O_NOFOLLOW)` 打开，持有至 attempt 结束。
- `path` 必须相对、非空、无 NUL、≤ 4 KiB、不含 `.`/`..` 分量；相对 out_dir FD 以 `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS|RESOLVE_NO_XDEV` 与 `O_RDONLY|O_NOFOLLOW|O_NONBLOCK` 打开；`fstat` 须为普通文件。
- 从已打开 FD 复制并计算哈希；声明的哈希与大小是待验证数据；原子发布到 BlobStore 后写入 `scope_blobs`（task 及其 session）与产物记录，再发送 `artifact_result`。保存有独立超时、大小上限且可取消；已保存副本为权威内容。
- 登记只保证路径范围与 attempt 归属，不证明内容由本任务新生成。
- **版本**：`(task_id, artifact_id, sha256)` 重复登记返回同一版本；不同内容由 `artifact_heads` 分配新版本。处理 `result` 时将输出固定为 `(artifact_id, version, sha256)`。

### 5.7 事件处理与完成屏障

- 读取 goroutine 持续读入有界队列；处理器按 `seq` 处理；artifact 保存完成后才处理其后的 checkpoint。取消、超时、退出走独立路径。
- **task 模式屏障**：进程退出后 (A) 管道收尾（默认 5 s，超时则终止执行树、标记 `output_incomplete`、丢弃末尾半行）；(B) 处理全部已完整接收的事件（`finalize_timeout` 默认 120 s）；然后最终裁决。
- **session 模式屏障**：收到终态提议且之前事件全部处理完成后裁决；之后进入释放流程（12.4）。
- 宿主在终态提议到达时保存其内容（含 `session_state`），最终事务提交的必须是该已保存内容。

### 5.8 宿主裁决

| 情况 | 裁决 |
|---|---|
| `result` + exit 0（task 模式）/ `result`（session 模式），输出已保存、协议无违规 | `succeeded` |
| task 模式 `result` + 非零退出 | `failed`（`exit_after_result`） |
| `result` 后、裁决提交前仍有该 attempt 的**业务事件** | `failed`（`protocol_violation`） |
| 裁决已提交后发现该 attempt 的协议违规 | 不改写终态；记录诊断事件，撤销访问，session 模式下销毁 incarnation |
| 终态提议后超过 `exit_grace`（task 模式）未退出 | 终止，再按提议与退出原因分类 |
| `paused` + 宿主确有暂停请求 + checkpoint 有效 | `paused` |
| 宿主 cancel/pause 已生效后结束 | 按宿主意图，不判 crashed、不重试 |
| 无终态提议即退出 | 按退出原因分类（14.3） |
| 协议违规或 `retryable: false` | 不重试 |

**业务事件**指 `progress`、`artifact`、`checkpoint`、`subrun_*` 与终态提议本身。终态提议之后仍允许的消息：`checkpoint_query`、`task_outcome_query`、`task_released`。

### 5.9 暂停与取消

- 暂停是协作式的：停止安排新步骤 → 到达提交边界 → 提交 checkpoint → `paused`。`paused.checkpoint_id` 必须是最新已提交 checkpoint。
- `grace_ms`（持续时间）到期：宿主终止。有已提交 checkpoint → `paused` 于该点；无 → `paused`，`resume_point: initial`，UI 明示将从头重跑。
- 取消：Worker 在 `grace_ms` 内停止；到期终止。

### 5.10 大小限制（UTF-8 字节，可配置默认值）

| 项 | 上限 | 项 | 上限 |
|---|---|---|---|
| 单条事件 | 1 MiB | 单个产物 | 256 MiB |
| inline state | 256 KiB | 每任务产物合计 | 2 GiB |
| `state_ref` | 16 MiB | `init` / `task_start` | 1 MiB |
| 每 checkpoint refs | 1024 | 其他控制消息 | 16 KiB |
| 每 attempt 事件合计 | 64 MiB | | |

超限 → `output_limit_exceeded`。

| JSON 结构限制（对整行生效，自由格式字段同样受限） | 上限 |
|---|---|
| 对象与数组的嵌套层数（消息顶层对象计 1） | 64 |
| 数字字面量的字符数（含负号、小数点、指数符号与指数正负号） | 32 |
| 重复键（任意层级，按解码后的键名比较；孤立代理项转义按 U+FFFD 计） | 不允许 |
| 浮点字面量 | 不得上溢为无穷；非零值不得下溢为零 |

违反上述限制为 `malformed_json`，在消息类型判定之前检查；编码时同样检查，违反为 `invalid_field`（不发出对端会拒绝的行）。键名区分大小写：在已定义字段的对象中（消息顶层及其结构化子对象），与已定义字段只差大小写的键为 `invalid_field`（按 Unicode 简单大小写折叠比较），其余未知键忽略。整数类型字段只接受整数形式（拒绝 `1.0`、`1e0` 与布尔值），取值在 int64 范围内。

## 7. 事务与并发

### 7.1 隔离级别与锁顺序

`READ COMMITTED` + 显式行锁。所有事务按下列顺序（取其子集）加锁：

```
sessions → session_control → session_progress
→ tasks → task_control → task_progress → task_event_seq
→ subruns → attempts → attempt_access → environments → artifact_heads
→ budgets → subrun_budgets → exec_quotas → calls → reservations
```

- 生命周期、控制、裁决、attempt 创建、checkpoint 提交：从 `tasks FOR UPDATE` 开始。session 事务，以及**属于 session 的 task 的 attempt 创建与最终裁决**（会推进 `session_progress`）从 `sessions FOR UPDATE` 开始，再锁 `tasks`。
- Gateway 事务：`tasks FOR SHARE → task_control FOR SHARE → subruns FOR SHARE → attempt_access FOR SHARE → budgets → subrun_budgets → exec_quotas → calls → reservations`。Gateway 请求彼此并行，但**会等待生命周期更新**，这是接受的正确性成本。
- 事务内只做检查、预留、journal 与行更新；绝不包含上游网络调用、文件复制或沙箱操作。
- 固定顺序**降低并约束**死锁风险，不消除（同表多行、锁升级、外键、唯一约束仍可能参与）；保留检测与重试。记录 `store_lock_wait_seconds{tx}`，先测量再决定是否拆分访问控制行。

### 7.2 序号与幂等插入

- 序号来自行锁：`UPDATE task_event_seq SET next = next + 1 WHERE task_id = $1 RETURNING next`；`commit_seq` 同理来自 progress 行；产物版本来自 `artifact_heads`（不存在则 `INSERT … ON CONFLICT DO NOTHING`，再 `SELECT … FOR UPDATE`）。不使用 `MAX()+1`。
- 幂等插入：`INSERT … ON CONFLICT DO NOTHING` 后，用**独立语句**读取既有记录并比较内容哈希或指纹。
- 终态及其 host 事件（含序号分配）在同一事务中提交；host 事件以 `event_key` 去重。

### 7.3 超时与重试

- 每个 Store 操作有一个整体 context deadline（默认 2 s），覆盖连接池获取、事务与重试；数据库侧另设 `lock_timeout = 1s`、`statement_timeout = 2s`。任何错误回滚整个事务。迁移使用独立超时（5 min）。
- 诊断区分 `lock_contention`（单次操作失败，可重试，不计入 Store 不健康）与 `connection_error`/`timeout`（计入阈值）。
- `40001`/`40P01`：确认中止后重跑整个事务。
- **COMMIT 结果未知**：先按操作身份查询，再决定是否重试：

| 操作 | 操作身份 | 结果未知时 |
|---|---|---|
| checkpoint 提交 | `checkpoint_id` | 查询 checkpoint |
| 创建 attempt | 事务前生成的 `attempt_id` | 查询 `attempts` |
| API 创建与控制 | `request_id`（`api_requests`） | 同 ID 同内容返回同结果；不同内容 `409 request_conflict` |
| 应用控制 | `applied_control_version` CAS | 重读 |
| host 事件 | `event_key` | 追加幂等 |
| reservation | 事务前生成的 `reservation_id` | 查询 |
| 结算 | reservation 状态条件 | 可安全重跑 |
| 产物登记 | `(task_id, artifact_id, sha256)` | 查询 |
| 裁决 | 来源状态 CAS | 重读状态 |

### 7.4 所有权：单执行主机

- 启动顺序：确认数据目录 → 固定路径 `<data>/agentbox.lock` 上取得 `flock`（持有至退出，不删除重建）→ 连接 PostgreSQL 并在专用连接上取得会话级 advisory lock → **安装身份引导与校验**（下述）→ 执行尚未应用的迁移 → 恢复。
- **安装身份引导**（持有 advisory lock 时执行；[修订提案](2026-10-05-installation-identity-amendment.md)）。`installation` 表为 `install_id, state (pending|complete), bootstrap_token_hash`；数据目录身份文件为 `<data>/install_id`，数据目录引导令牌为 `<data>/bootstrap_token`（32 字节随机数，十六进制），两者的写入方式均为临时文件 + fsync + rename + fsync 父目录。令牌严格解析：不存在、读取失败、损坏是三种状态，后两者使启动失败；有效令牌只复用、不覆盖。pending 记录只能由持有对应令牌的数据目录继续。

  | 数据库状态 | 数据目录 `install_id` | 处理 |
  |---|---|---|
  | 无 `schema_migrations` 且无任何 agentbox 表（空库） | 不存在 | 全新安装：持久化引导令牌（已有则复用）→ **在同一事务中**执行全部迁移并插入 `installation(新 ID, pending, 令牌哈希)`（PostgreSQL 事务性 DDL；事务未提交则库仍为空，重启后重新引导；**提交结果未知则本次启动失败**，下次启动按本表恢复）→ 写数据目录身份文件 → 置 `complete` |
  | 有 `schema_migrations` 但无 `installation` 记录 | 任意 | 拒绝启动：初始迁移与记录原子提交，该状态只能来自外部改动或损坏 |
  | 空库 | 存在 | 拒绝启动（数据库丢失或被替换），需人工处理 |
  | 无 `schema_migrations` 但存在 agentbox 表 | 任意 | 拒绝启动（未知 schema） |
  | `installation.state = pending` | 不存在，且令牌哈希与记录一致 | 继续中断的引导：写身份文件 → 置 `complete` |
| `pending` | 不存在，且无令牌、令牌不一致或记录无哈希（修订前的旧记录） | 拒绝启动：该安装由另一个数据目录发起，或无法证明由本目录发起 |
  | `pending` | 与数据库一致 | 置 `complete` |
  | `pending` 或 `complete` | 与数据库不一致 | 拒绝启动 |
  | `complete` | 不存在 | 拒绝启动（数据目录丢失或被替换） |
  | `complete` | 一致 | 正常启动 |

  "表不存在"本身不被当作全新安装；只有整个库为空且数据目录无身份时才初始化。
- advisory lock 防止重复启动，**不提供跨主机故障接管**。
- 锁连接断开或无法确认所有权 → 进入不可逆的 `ownership_lost`：不再启动新的业务操作；取消在途数据库操作与上游请求；停止本机全部执行树（物理操作，不写数据库）；有期限清理后退出。重启走完整恢复，不原地恢复服务。
- 从锁丢失到被检测之间存在窗口，此前已在途的事务可能提交；本设计不宣称锁丢失后绝对零提交（那需要额外的数据库执行权隔离，属于多节点阶段）。

## 8. 状态机

### 8.1 Task

```
             grant（创建 attempt 事务）           attempt 结束 → 裁决
 queued ─────────────────────────► running ──────────────────────────► succeeded | failed
   ▲  ▲                                │  │ 故障类别且有剩余重试 → queued（not_before）
   │  │                     暂停请求   │  │ 取消请求
   │  │                                ▼  ▼
   │  │                           pausing  cancelling ── 结束 ──► cancelled
   │  │                              │ 结束
   │  └──── resume ────────────── paused ── cancel ──► cancelled
   ├──── queued + pause ─────────► paused（resume_point = 最新 checkpoint 或 initial）
   └──── queued + cancel ────────► cancelled
```

- 生命周期转换：`UPDATE tasks SET status=…, row_version=row_version+1 WHERE task_id=… AND row_version=… AND status IN (允许的来源状态)`。
- **控制写入**：事务内检查非终态（否则 `task_ended`）；已接受的 cancel 不可被 pause/resume 覆盖（`cancel_pending`）；resume 要求 `paused`；递增 `control_version`；提交后才确认接受，再尽力通知 actor（actor 也周期比较 `control_version > applied_control_version`）。
- **创建 attempt**：要求 `queued`、`desired = run`、无未停止的旧执行；session task 另需 session actor 授予，校验与交接在持有 `sessions FOR UPDATE` 的同一事务中完成：`blocked_by_task_id` 为空或等于本 task（阻塞者本人恢复；同事务清除该标记并设置 `current_task_id`），其他 task 一律等待；并满足以下两种准入之一——(a) **正常切换**：上一任务已释放（12.4），复用同一 incarnation；(b) **故障恢复或替换**：旧环境已撤销且 `stopped_at` 已记录，在新 incarnation 中运行。同事务插入 attempt 与 `attempt_access(active)`、递增 `attempts_total`（仅故障重试时递增 `fault_retries_used`）、设置 `current_attempt_id`、CAS `queued → running`。不通过 → 归还槽位。
- **最终裁决**（完成屏障之后，单事务读取 `task_control`）：
  - `desired = cancel` → `cancelled`；已有固定的有效 result 时另记 `completed_during_cancel`；
  - `desired = pause` → `paused`（5.9）；有效 result 保留固定产物并记 `completed_during_pause`，不提交成功；
  - `desired = run` → 按 5.8 与 14.3。
  - 成功的 session task 同事务推进 `session_progress`（12.3）。
  - 已成功保存并固定的产物保留；未完成保存的产物不保证留存。
- cancel 优先于 pause；`starting`/`handshaking` 阶段的 cancel/pause 直接停止执行。
- 重试计数：故障重试消耗 `fault_retries_used`；`worker_oom_likely` 另计 `oom_retries_used`（上限 1）；暂停恢复只增加 `attempts_total`。
- `task_deadline_exceeded`：累计运行时间（14.4）超限，新 attempt 不重置。

### 8.2 Attempt

```
created → starting → handshaking → active → finishing → ended{succeeded|failed|crashed|cancelled|paused|lost}
                                                  （Reconciler 无法确认停止时：stop_blocked → 确认后 ended{lost}）
```

- `active` 之前的失败直接 `ended` 并总是发起停止；`ended` 不意味着 `stopped_at`。
- `stop_blocked`：非终态，占用槽位，阻止替代执行。

### 8.3 Environment

`creating → running → (frozen ⇄ running，仅 session) → stopping → stopped(stopped_at) → cleanup: pending → in_progress → done | stuck`

- cleanup loop 只处理已停止且所属 attempt/incarnation 已结束的环境；`stuck` 按 `next_retry_at` 退避并在 `inspect` 中提示；`in_progress` 重启后重做（操作幂等）。
- intent 规则：获取操作未结束时不能判定清理最终完成；迟到的创建结果触发清理；重启时依据 intent 与独立原始扫描判断，不能仅凭环境列表为空认定无残留；`failed` 仅在确认无残留时设置。

### 8.4 Sub-run

`started → end_proposed → completed（仅当已提交 checkpoint 列出）`；`started|end_proposed → cancel_requested → cancelled`；`→ failed`；`→ timed_out`。终态（`completed`、`cancelled`、`failed`、`timed_out`）不可回退。

### 8.5 Session

见 12.2。

## 9. Gateway

### 9.1 Edge：入口、绑定与撤销

- **独立 task**：每 attempt 一个 listener；**session**：每 incarnation 一个 listener。socket 位于 `<data>/gateway/<attempt_id>.sock`（执行中修订，M2 Plan 7：不在环境目录内、不记录 `listener` intent，edge 撤销时删除、启动时清空该目录），bind-mount 到 `/run/agentbox/gateway.sock`，属主为环境映射 uid 1000（由 provider 启动器 chown），0600。HTTP/1.1。
- 连接在接受时绑定到该入口当前的 attempt；session 空闲时拒绝连接。每 attempt 上限 16 个连接、32 个活跃请求；请求体 ≤ 4 MiB。
- 撤销：`AttemptAccess.Revoke` 先提交 `attempt_access.state = revoked`，再关闭该 attempt 绑定的全部连接（独立 task 同时关闭 listener）。关闭连接只是清理，持久化检查才是执行点。
- 撤销时机：attempt 结束；**取消生效时立即撤销**；暂停不撤销（当前步骤可能仍需 Gateway 到达提交边界）。
- 撤销时取消面向 Worker 的请求上下文。宿主托管的上游 try（含共享请求）是否继续，**只按离开原因判定**，与是否还有连接或 waiter 无关：

  | 离开原因 | 上游 try / 共享请求 |
  |---|---|
  | 客户端断开连接、HTTP 请求被 Worker 取消 | 继续至调用期限，写入 journal 并结算，供后续重放 |
  | attempt 结束或被替换（非取消原因的撤销） | 同上；期间仍占用任务预算与上游并发 |
  | 用户取消任务，或该 sub-run 的取消生效 | 取消；按"未发出释放 / 有 usage 按实际 / 无法确认转 unknown"结算 |
- 归属：独立 task 中"T1 的请求不会计到 T2"不适用（一 attempt 一入口）；session 中该性质依赖可信编排 Worker 不跨任务保留后台工作，以及释放核验（12.4）。

### 9.2 访问检查

所有请求（含 replay、`/v1/budget`、blob 读取、exec）首先在一致快照中检查：`attempt_access.state = active`、`tasks.current_attempt_id = 绑定的 attempt_id`、`task_control.desired ≠ cancel`；带 sub-run 头时检查该 sub-run 属于本任务、绑定当前 attempt、状态允许调用（否则 `409 subrun_closed`）。新增费用或配额的操作在预留事务内再次检查。trace 信息不参与身份或权限判断。

### 9.3 端点

| 端点 | 说明 |
|---|---|
| `POST /v1/chat/completions` | OpenAI 兼容子集；拒绝 `stream: true`；仅声明的 adapter、模型与纯文本消息 |
| `POST /v1/search` | `{query, max_results}` |
| `POST /v1/fetch` | `{url}`，仅 GET，不接受 Worker 指定请求头或请求体 |
| `POST /v1/exec` | 第 10 节 |
| `GET /blobs/{sha}` | 只读，按 scope 授权 |
| `GET /v1/budget` | 剩余预算与配额 |

- 计费、配额或副作用调用必须携带 `X-Agentbox-Call-Id`（SDK 以 `<subrun_id|root>/<step_id>/<kind>/<n>` 确定性生成，≤ 256 字节）；sub-run 内调用携带 `X-Agentbox-Subrun`（可信归属头，宿主仍校验 9.2 条件）。
- 结果保存为 blob 并加入 scope 授权，响应头 `X-Agentbox-Blob` 供 checkpoint 引用。

### 9.4 Journal

- **指纹**：`sha256(JCS({endpoint, adapter_version, resolved: {provider, model, applied_defaults}, cache_directive, body}))`（RFC 8785）；解析器拒绝重复 JSON 属性名（`400 duplicate_json_key`）。exec 的指纹见 10.1。
- 调用所有权绑定宿主维护的 try，而非连接；每个逻辑调用同时至多一个由本平台执行的 try。

| 已有记录 | 相同指纹的请求 |
|---|---|
| 无 | 解析流程（11.2） |
| `resolving` / `in_flight`（宿主仍有执行中的 try，含旧 attempt 留下的） | `409 call_in_progress` |
| `completed` | 返回持久化结果，`X-Agentbox-Replayed: true` |
| `unknown` | 按不确定结果策略，在累计上限内新建 try |
| `failed` | 返回持久化失败；仅可重试类别、未达上限且请求带 `X-Agentbox-Retry: true` 时新建 try |
| 任意状态、指纹不同 | `409 fingerprint_mismatch`，host 事件 `replay_divergence` |

- 指纹冲突：SDK 抛出 `CallDivergence` 交给编排层；编排层显式以新 ID 发起并携带 `X-Agentbox-Supersedes` 与原因，Gateway 记录关联，新 ID 进入后续 checkpoint。不做透明自动换 ID。
- 可能已脱离本地控制的上游请求记为 `possible_external_duplicate`。
- `result_ref` 是任务数据，用于重放；请求体不存储，只存指纹。

### 9.5 两个原子提交点

- **调用前事务**：检查访问与指纹 → 确认无竞争 try → 检查累计 try 上限 → 分配 `try_no` → 创建 reservation（task 与 sub-run 两层）→ 更新账本 → 调用状态 `in_flight`。提交后才发起上游请求或 exec。
- **调用后**：完整保存结果 blob → 单事务完成结算、try 状态、`calls.completed`、`scope_blobs` → 返回结果。
- 结算按 reservation 状态幂等；超时已转 unknown 后迟到的响应只记入 `call_tries` 供诊断。撤销不阻止宿主完成记账。

### 9.6 预算与配额

- **两层账本**：task 层是总额（含 root 编排与全部 sub-run），sub-run 层是归属明细，不重复扣费。预留须同时满足 `task 可用 ≥ 预留` 与 `sub-run 可用 ≥ 预留`（有 sub-run 时），两层在同一事务中更新；结算、unknown、释放同步处理。可用 = `limit − spent − reserved − unknown`。
- **互斥记账**：每笔 reservation 只转入 `spent`、`unknown`、`released` 之一，并同时从 `reserved` 扣除。
- **预留是保守估算**：每个 adapter 声明计量方法、输出上限、价格表版本；模型调用为 `input_estimate × 输入单价 + max_tokens × 输出单价`（`max_tokens` 必填或补默认并截断；`input_estimate` 由 adapter 定义并包含工具定义）；搜索按 adapter 声明的按次或按结果计价；抓取另有请求次数、响应字节与并发配额。
- **结算**：有 usage → 按实际记入 `spent`（可超出预留，账本可出现**赤字**）；确定未发送 → 释放；结果未知 → 全额转 `unknown`，不自动退回，也不代表费用已确认。
- **达到或超过上限**（可用 ≤ 0）：拒绝需要新增付费预留的调用（`402 budget_exhausted` / `subrun_budget_exhausted`），免费缓存命中与已有结果的处理不受影响。单次预留失败（`budget_insufficient_for_request`）不等于终止 sub-run；是否终止由编排策略决定。

### 9.7 重试

- 每个逻辑调用累计最多 3 次 try（`calls.tries_used`），覆盖 Gateway 自动重试、SDK 重连与 Worker 恢复。
- **调用期限持久化**：首次登记调用（Tx1，`resolving`）时写入 `created_at` 与 `deadline_at = created_at + 调用期限`（默认 120 s；exec 为排队上限 + wall 超时 + 30 s）。期限覆盖缓存解析、等待并发槽位与全部 try，按数据库时间判断；Worker 重连、attempt 恢复、server 重启都不重置。超过 `deadline_at`：不再新建 try，返回 `504 call_deadline_exceeded`；尚无 try 的调用置为 `failed`，在途 try 被取消并按 9.6 结算。
- 每次 try 重新检查访问、预算/配额、累计次数、剩余调用期限（`deadline_at − now`）。
- 429、5xx 与发送前失败只表示可以考虑重试；收费依据 usage 与供应商语义，无法确定即 unknown。指数退避加抖动，遵从 `Retry-After` 但受期限约束。
- 并发：每任务上游在途 ≤ 4；每 sub-run 占用上限 2（不承诺公平性）；每 provider 全局限额。

### 9.8 出站防护

1. 仅 `http`/`https`，默认端口 80/443；拒绝含 userinfo 的 URL。
2. 模型与搜索上游地址在配置中固定；所有出站拨号走同一验证 dialer；私有地址仅允许显式配置的上游（`upstream_allow_private`）。
3. Gateway 自行解析 DNS，拒绝 loopback、私有、link-local、CGNAT、组播、未指定、IPv6 ULA 及其 IPv4-mapped 形式。
4. 连接已检查的解析结果 IP，保留原始 Host/SNI。
5. 重定向最多 5 跳，每跳重新检查。
6. 大小上限作用于解压后正文：抓取 5 MiB / 20 s；模型与搜索响应 8 MiB。
7. 不继承代理环境变量。

### 9.9 凭据与审计

供应商 Key 只从宿主环境变量或文件加载到 core，不进入沙箱、不写日志。审计内容为 `calls`/`call_tries` 元数据：端点、模型、token、延迟、状态、费用、上游请求 ID；不含 Key、不含提示词。

## 10. Exec 沙箱

### 10.1 模型：单次、无状态

- 每次 `POST /v1/exec` 使用全新 `exec` 环境，执行一次后销毁；调用间不保留状态。后续调用需要文件时显式引用前次输出 blob。
- 请求：`language`（v0.2 仅 `python3`）、`code`（≤ 256 KiB）、`inputs[]{sha256, path}`（须授权到本任务；路径相对、无 `..`、不重复，合计 ≤ 256 MiB）、`limits`（按任务策略截断）。
- 响应：`exit{code, signal}`、`ResourceDiag`、`stdout`/`stderr`（各 ≤ 1 MiB，带截断标志；超额继续读取并丢弃）、`outputs[]{path, sha256, size}`。
- 指纹：`language, code, inputs（sha + path）, 镜像 digest, 生效 limits`。completed → 重放；unknown → 确认旧 exec 环境停止后可按策略重新执行。重新执行可能产生不同结果并消耗额外资源，不保证确定性或 exactly-once。

### 10.2 流程

```
调用前事务（访问、调用身份、exec 配额预留）
→ coordinator 创建 exec 环境（intent、owner.json、UID 范围）
→ 宿主将输入 blob 放入只读 /in
→ StartExec（stdin 关闭；代码即入口，无 Worker 协议）；开始计 wall time（排队时间单独记录）
→ 等待退出或超时
→ 停止整个执行树，确认 populated 0
→ 读取 cpu.stat、memory.events（删除 cgroup 之前）
→ 保留挂载，按 5.6 的打开规则收集 /out：仅普通文件，≤ 256 个，其余报告并跳过
→ 卸载、删除、释放 UID 范围（满足 4.5 回收条件后）
→ 调用后事务（结算、journal、scope_blobs）→ 返回
```

收集的是停止全部写入者后的稳定文件，不承诺构成某一瞬间的原子文件系统快照。

### 10.3 配额

- `exec_count` 在实际启动时扣除；journal replay 不扣。
- CPU：预留 `cpu.max 速率 × wall 超时 × (1 + 余量)`，是估算而非严格物理上界（周期边界效应与停止检测延迟）。停止后按 `cpu.stat usage_usec` 结算；读取失败按全额预留计入；超额如实记账并阻止该任务后续 exec。
- wall time 与排队时间分开记录。
- 并发：全局 exec slots；每任务至多 2 个。

### 10.4 结果语义

- 宿主确认已停止并取得诊断 → `completed`、`timed_out` 或 `cancelled`（附实际用量）。
- 仅当无法确认执行停止或结果（例如 server 崩溃）→ `unknown`。
- attempt 结束、撤销或取消时，其 exec 环境**总是被终止**。用户取消的任务不会自动重跑 exec。

## 11. 缓存（Redis）

### 11.1 范围与原则

- 缓存公开搜索结果与抓取页面，跨任务共享；**不缓存模型调用**。
- **journal 是任务内事实，缓存是共享优化**：查找顺序 journal → 缓存 → 上游。已记录的调用结果永不被缓存覆盖。
- Redis 不保存任务状态、预算、恢复依据、会话或任何正确性依赖的锁。
- 在明确的单租户信任边界内，缓存符合准入规则的结果；不宣称参数黑名单能证明内容公开。

### 11.2 调用流程

```
Tx1：检查访问（含 desired ≠ cancel）、call_id、指纹 → 登记 calls.state = resolving（无 try、无预留）
查缓存（事务外）
 ├─ 命中 → Tx2：重新检查访问 → 写入 scope_blobs → journal completed（source = cache，无预留）→ 返回
 └─ 未命中 → Tx2：重新检查访问、预算、累计次数 → 预留、创建 try → 上游（9.5）
```

- `resolving` 视为进行中（重复请求得到 `call_in_progress`）。Redis 查询、策略检查或数据库提交失败后，调用回到可重新解析状态；重启时遗留的 `resolving` 同样复位。未创建 try，不产生 unknown 费用、不消耗上游重试次数。
- Redis 错误 → 视为未命中；PostgreSQL 或访问检查失败 → 返回错误，不绕过。
- 命中免费：释放无预留，但计入抓取请求次数与字节配额。
- 取消先提交，则命中结果不能随后被授权提交；结果先提交、取消随后到达时，已发出的响应字节无法撤回，仍按撤销流程取消连接。
- 每次命中重新检查**当前**策略：抓取检查 URL 校验器与配置的拒绝规则；搜索检查 provider 仍启用（adapter 版本在键中）。

### 11.3 键、值与新鲜度

- 键：`v1:{search|fetch}:{provider}:{adapter_version}:sha256(JCS(规范化参数))`。抓取 URL 规范化：scheme/host 小写、去默认端口、去 fragment，查询串原样保留。`Accept-Encoding` 由 Gateway 固定发送并计入键。
- 值（≤ 4 KiB，限长解析）：`{blob_sha256, status, content_type, final_url, size, fetched_at, expires_at, kid}` 及 HMAC（覆盖键、元数据、`expires_at`、`kid`）。正文存于 BlobStore。
- **准入**：仅 GET、200、≤ 2 MiB；不缓存含 `Set-Cookie`、`Cache-Control: no-store|private|no-cache`、`Vary: *` 或 `Vary` 含 `Accept-Encoding` 以外维度的响应；不缓存查询串含凭据类参数（`token`、`sig`、`signature`、`key`、`auth`、`X-Amz-*` 等）的 URL；不缓存错误响应。
- **新鲜度**（RFC 9111 子集）：寿命取 `s-maxage`，否则 `max-age`，否则 `Expires − Date`；无显式新鲜度不缓存（不使用启发式）。年龄按完整计算（`Age`、`Date`、请求/响应时间差与缓存驻留时间）。`expires_at` 固定为原响应的新鲜度截止点，上限 24 h，不设下限、不延长；重写 Redis 或命中都不延长。无效、冲突或不支持的头 → 不缓存。
- 搜索使用 adapter 定义的 TTL（默认 6 h），只缓存成功结果。
- **过期即未命中**：不返回过期条目，过期后同步请求上游；无后台刷新。

### 11.4 请求合并

- 进程内 singleflight，键为 `(task_id, attempt_id, subrun_id | "root", cache_key)`；不跨 sub-run、不跨 attempt、不跨任务合并。跨任务复用只经已完成的缓存条目。
- 共享请求使用 Gateway 自有 context 与期限，不使用首个 HTTP 请求的 context。waiter 离开不终止它；只有 9.1 表中的取消类原因（任务取消或该 sub-run 取消生效）才取消它——合并键限定在同一 task、attempt、sub-run 内，取消原因对全部 waiter 一致。leader 的 try 付费；follower 各自完成访问复查、配额计数与 journal 提交（`source = coalesced`，无上游费用）。
- `no-cache`：不读旧缓存，不加入任何 singleflight，结果仍写入缓存；计入指纹。journal 重放仍优先，已完成的 call ID 不会因 `no-cache` 重新执行。
- 取消结算：尚未发出 → 释放；已取得 usage → 按实际；无法确认 → unknown。

### 11.5 完整性与降级

- 只有 Gateway 写缓存。每次命中校验 HMAC、`expires_at`（Gateway 时钟，不依赖 Redis TTL）、blob 存在且内容哈希一致；任一失败 → 视为未命中、删除条目、记录 `cache_integrity_failure`。
- 密钥存于 `<data>/cache.key`（0600，安装时生成）；`agentbox cache rotate-key` 轮换；当前与上一 `kid` 可验证，其他 `kid` 视为未命中。
- 边界：签名与内容哈希用于验证来源及完整性；不保证可用性，不防止有效期内合法旧条目的重放。
- 降级：读 50 ms、写 100 ms 超时后视为未命中；连续 5 次失败熔断 30 s；写入异步、可丢弃。指标：`hit`、`miss`、`bypass`、`coalesced`、`error`、`breaker_open`、`integrity_failure`。
- 缓存 blob 保留在 BlobStore（无 GC），README 声明磁盘增长。

## 12. 会话

### 12.1 关系与所有权

- `session 1 ─< tasks`（FIFO，同时至多一个运行中）；`session 1 ─< incarnations`（同时至多一个存活）；`task 1 ─< attempts`。
- session actor 拥有 session 生命周期与 incarnation；task actor 拥有 task/attempt；session task 的 attempt 创建须经 session actor 授予。
- session 在整个生命周期保留其 UID 范围；workspace 位于 `<data>/sessions/<session_id>/workspace`。

### 12.2 生命周期

```
creating → idle ⇄ running(task)
idle ──idle_ttl──► quiescing ──quiesced 且条件满足──► frozen ──thaw──► idle
                      │ 超时或条件不满足 → evicting
frozen ──frozen_ttl / 容量压力──► evicting ──► evicted
evicted ──wake / 新任务──► restoring ──ready──► idle
任意 ──close / TTL──► closing ──► closed
```

| | frozen | evicted |
|---|---|---|
| 进程 | 保留（`cgroup.freeze`） | 无 |
| 内存 | **保留，计入环境内存容量** | 释放 |
| 磁盘 | workspace（rootfs 只读，无可写层） | workspace |
| session 状态 | 进程内存，且等于最新已提交 session checkpoint | 最新已提交 session checkpoint |
| 唤醒 | thaw（延迟为待测指标） | 新环境 + 新 incarnation + `session_resume` |

**冻结前条件**：无运行或释放中的任务；无存活 exec 环境；session 空闲因而 Gateway 拒绝新连接；`quiesced.session_checkpoint_id` 等于最新已提交 session checkpoint；宿主写 `cgroup.freeze = 1` 并等到 `cgroup.events` 中 `frozen 1`（有期限）后才记录 `frozen`；失败则驱逐。

- 驱逐：从 frozen 直接销毁（状态已提交，无需解冻）；从 idle 先 quiesce。内存压力下按 LRU 先驱逐 frozen、再驱逐 idle——这是单机容量回收，不是弹性扩缩容。
- 唤醒仅支持显式方式：向 session 提交任务或 `POST /sessions/{id}/wake`。不承诺后台监听透明恢复。
- 恢复：撤销并确认旧 incarnation 停止 → 新环境（同一 UID 范围与 workspace）→ 新 incarnation 与新 listener → `init.session_resume`。
- **冷恢复的 state 读取**：此时尚无 task attempt，空闲 session 的 Gateway 拒绝连接，且不为此放开。若 session checkpoint 使用 `state_ref`，宿主在创建新环境时先校验该 blob 已完整保存并授权到本 session scope，再把它放入只读路径 `/run/agentbox/restore/<sha256>`；`session_resume` 以 `staged_state_path` 指向它，不携带 `state_ref` 供 Worker 自行读取。只暂存 state 本身；`refs` 中的其他 blob 只在之后某个 task attempt 内经 Gateway 读取。暂存文件在 incarnation 进入 `idle` 后由宿主卸载。

### 12.3 会话状态一致性

- 任务执行期间不提交共享 session 状态变化。`task_start` 绑定 `base_session_checkpoint_id`；中间变化进入 task checkpoint。
- 成功：`result.session_state` 作为提议在到达时由宿主保存；最终裁决事务同时提交任务终态、固定产物、新的 session checkpoint 与 `session_progress` 指针推进。
- 失败、取消、暂停：指针保持 `base`。
- 宿主随后发送 `task_outcome`；Worker 成功时采用已提交状态，否则丢弃工作副本回到已提交状态；确认丢失可经 `task_outcome_query` 查询；`T_release` 内无法达成一致 → 销毁 incarnation。
- 任务中途恢复：新 incarnation 以 `base_session_checkpoint_id` 恢复 session 状态，再应用 task checkpoint。`base` 必须等于当前 session 指针，否则为协议违规。
- 暂停的 session task 阻塞该 session 的队列（`blocked_by_task_id`），直到恢复或取消；不支持 rebase。恢复时由其本人的 attempt 创建事务清除标记（8.1）；取消时在裁决事务中清除。

### 12.4 任务释放

```
终态提议 → 裁决 → task_outcome → draining → task_released → 宿主核验 → idle（允许下一 task_start）
```

宿主核验：`task_released` 之前的事件已处理；该 attempt 绑定的 Gateway 连接无在途请求且已关闭（宿主托管的 try 可继续）；该 attempt 的 exec 环境已停止；编排环境 `cgroup.procs` 等于基线（init 与 Worker 主进程）。SDK 以结构化并发取消并等待本任务的后台工作。**进程数核验不能发现 Worker 内部遗留的线程、协程或计时器，编排进程内部的正确性依赖可信 Worker 假设。** `T_release` 内未完成 → 销毁 incarnation，下一任务在新 incarnation 中运行。**释放失败发生在裁决之后**：它是 incarnation 故障（记入 `incarnations.end_reason = release_timeout`），不是任务故障——已提交的任务终态与 session 指针保持不变，该任务不重跑，不消耗其故障重试次数。

### 12.5 Workspace

| 路径 | 生命周期 | 恢复时回滚 |
|---|---|---|
| `/workspace/attempt` | 每 attempt 新建，释放或清理时删除 | 不适用（总是新建） |
| `/workspace/out/<attempt_id>` | 仅作产物登记来源 | 不适用 |
| `/workspace/session` | 跨任务、跨驱逐保留 | **否**；视为缓存或提示 |
| 已提交产物 | blob | 不可变 |

正确性依赖 checkpoint 与不可变 blob。

### 12.6 关闭与重启

- 关闭（显式或 TTL）：拒绝新任务 → 排队与暂停的任务明确取消 → 活跃任务走取消与释放 → 确认相关环境停止后删除 workspace → 已提交的历史产物保留。之后保留产物的读取按 task 历史授权，session scope 失效。
- server 重启：不接管任何存活环境；Reconciler 停止所有环境，session 变为 `evicted` 并保留最新 session checkpoint；运行中的任务按 14.2 处理。

## 13. 受限多 Agent（sub-run）

### 13.1 模型

- sub-run 是同一可信编排进程、同一 task 与 attempt 内的并发研究单元，共享沙箱；它是调度与资源治理单位，不是安全边界。
- 每个任务至多创建 **4 个逻辑 sub-run**（恢复时复用既有 ID，不重复计数）；不允许递归。

### 13.2 启动与归属

- `subrun_start` → 宿主校验并持久化定义（`subruns`）→ `subrun_started` → SDK 才允许该 sub-run 发起调用。同 ID 同定义幂等，不同定义 `conflict`；超过上限 `subrun_limit`。
- sub-run 头是可信归属，不防止可信 Worker 故意错报；宿主仍校验 9.2 中的归属与状态。

### 13.3 预算与并发

按 9.6 的两层账本；达到上限只拒绝新的付费预留；deadline 与任务取消可强制取消，预算耗尽本身不自动取消。每 sub-run 上游占用 ≤ 2，不承诺公平性。

### 13.4 取消

- 宿主发出 `subrun_cancel_requested`，同时拒绝该 sub-run 的新调用、终止其 exec 环境，在途上游 try 按"未发出释放 / 有 usage 按实际 / 无法确认 unknown"处理。
- SDK 取消并等待该 sub-run 的异步任务，发送 `subrun_end{cancelled}`。
- `T_subrun_cancel` 内未完成 → 终止整个 attempt/incarnation（`subrun_cancel_timeout`），从 checkpoint 恢复。宿主不能单独停止 Python 协程，本设计不作此宣称。

### 13.5 完成与恢复

- `subrun_end{succeeded}` 是提议；只有当已提交的 task checkpoint 在 `subruns[]` 中列出其完成状态与结果引用时，才成为 `completed`。
- 恢复时：

| 状态 | 处理 |
|---|---|
| `completed` | 恢复结果，不重跑 |
| `cancelled`、`timed_out`、不可重试的 `failed` | 保留状态，不重跑 |
| 未完成且允许继续 | 宿主重新绑定 `bound_attempt_id`，传递已提交子状态 |
| `end_proposed` 但未进入 checkpoint | 不视为完成 |

- deadline 为绝对时间，恢复不重置，暂停期间继续计时；恢复时已过期的 sub-run 由宿主标记 `timed_out`，在 `init.resume.subruns` 中告知。

### 13.6 部分失败

编排层决定是否以已有证据继续；`result.subruns[]` 必须列出每个 sub-run 的状态与摘要，报告须标注不完整部分。`inspect` 展示 sub-run 时间线、费用与失败原因。

## 14. 恢复与错误处理

### 14.1 启动顺序

1. 确认数据目录；取得 `flock`；取得 advisory lock；校验 `install_id`。
2. 执行迁移。
3. 单事务撤销所有 `active` 的 attempt 访问。
4. 账本转换（幂等，reservation 与账本余额同事务）：`held` → `charged_unknown`；`in_flight` call → `unknown`；`resolving` call → 可重新解析。
5. 扫描与核对：`provider.List` 加独立原始扫描（环境目录、挂载、cgroup、listener socket、UID 范围文件属主），逐层报告，区分完整环境与部分残留。
6. 经 coordinator 停止所有未结束的环境（不接管存活环境）。
7. 提交 `lost`、session `evicted`、对应 host 事件与恢复安排（14.2）。
8. 计入运行时限未记账区间（14.4）。
9. 按核对后的实际资源重建 admission。
10. 依次启动 cleanup loop、actor、API。

**执行就绪条件**：Store 健康，且全局核对、撤销、账本恢复、admission 重建均完成。超过恢复期限（默认 60 s）未就绪 → API 以诊断模式启动，只开放只读的 `status`/`inspect`，禁止执行。

**资源归属**：持久化 `install_id`；环境目录在任何挂载前写入 `owner.json{install_id, env_id}`；cgroup 路径 `agentbox-<install_id>/env-<env_id>`。清理所需归属信息在执行前已持久化，不猜测路径。

| 扫描结果 | 处理 |
|---|---|
| 属于本安装、无对应记录 | 作为孤立资源回收 |
| 归属不明或冲突 | 写入 `quarantined_resources`，报警，不自动销毁，计入占用 |
| 属于其他安装 | 不操作 |

**停止失败**：已确认 → `lost` 并按意图安排；无法确认 → `stop_blocked`（只阻塞其任务/会话，占用容量，退避重试，`inspect` 可见）；Store 不可用 → 不启动 actor、不执行。

### 14.2 Reconciler 对任务的处理

| 持久化情况 | 恢复行为 |
|---|---|
| cancel 已接受 | 停止旧环境 → `cancelled`，不重试 |
| pause 已接受 | 停止并清理 → `paused`，保留恢复点 |
| `desired = run`，无未完成 attempt | 保持排队，保留计数与 `not_before` |
| `desired = run`，有本次重启丢失的 attempt | 确认停止后按故障恢复策略排队 |
| 已完成故障分类并安排重试 | 不再增加计数 |
| 裁决已提交 | 保留终态，只处理残留资源 |

只有在实际创建替代性故障重试 attempt 的事务中才递增 `fault_retries_used`。

### 14.3 故障分类

| `outcome_class` | 故障重试 |
|---|---|
| `crashed_signal`（不含平台主动终止）、`control_lost`、`ready_timeout`、`lost_on_restart`、`subrun_cancel_timeout` | 是 |
| `release_timeout`、裁决后的协议违规 | 不适用：属于 incarnation 故障，任务终态已提交，不重跑、不计重试 |
| `create_failed_transient` | 是，有界 |
| `create_failed_env`（rootfs 缺失、配置错误、内核能力不支持、权限不足） | 否，报告环境问题 |
| `create_outcome_unknown` | 先核对资源，不直接重建 |
| `store_unavailable` | Store 恢复后是 |
| `worker_oom_likely` | 一次（`oom_retries_used`），之后失败 |
| `worker_error`，`retryable: true` | 是，除非错误码在拒绝列表（`budget_exhausted`、`protocol_*`） |
| `worker_error` 不可重试、`protocol_mismatch`、`protocol_violation`、`output_limit_exceeded`、`exit_after_result` | 否 |
| `task_deadline_exceeded` | 否 |
| `cancelled`、`paused`、`completed_during_*` | 非故障 |

- 平台主动 SIGKILL（取消、超时、清理）按原因分类；`platform_killed` 与 OOM 诊断并列记录。
- OOM 只作资源诊断：被 SIGKILL 且 `OOMKillDelta > 0` → `worker_oom_likely`；正常结束但 `OOMKillDelta > 0` → 按 Worker 结果裁决，另记 `oom_observed_in_attempt`。
- 所有重试受 `max_fault_retries` 与 `not_before` 约束。

### 14.4 累计运行时限

运行时间 = 持有执行环境的时间（`starting` 至 `stopped_at`），不含排队与暂停；session task 计其 attempt 期间。actor 以单调时钟计时，每 10 s 持久化；重启后未记账区间按墙钟差全额计入（保守）。

- **时限的确定与存储**：创建任务时确定有效时限并随任务持久化（`limits.max_run_time_ms`）。未指定时取默认值（19：3600 s）；显式值须为正整数且不超过服务端上限，否则创建失败（`400 invalid_limits`）。之后修改服务配置不影响已创建任务。
- 额度跨 attempt 累计：重试、恢复、server 重启都不重置。到期按 `task_deadline_exceeded` 终止，不再创建 attempt。
- 本时限与 Gateway 单次调用期限、sub-run 的绝对 deadline 相互独立。

### 14.5 Store 故障

- 整体 deadline 与阈值见 7.3；连续失败达阈值（N = 5 或 T = 30 s）→ `store_unavailable` 终止 attempt。
- AttemptRunner 中每个 channel 发送 `select` 在 `ctx.Done()` 上。
- Store 不可写时先完成物理终止与不依赖数据库写入的清理。Store 不可用期间 admission 保守，未确认停止的环境视为占用。
- **在线补偿（server 未重启）由现有所有者执行**：actor 与 coordinator 对失败的持久化操作带退避重试，并保留待提交的事实（例如"环境已停止"、"attempt 已结束及退出原因"）；Store 恢复后由各自所有者提交裁决、状态与事件。周期核对只**报告事实**——把扫描到的实际资源状态作为消息交给对应 actor 或 coordinator——不直接写生命周期字段。启动恢复程序（14.1）只在启动时运行，不在在线服务中重跑。

### 14.6 诊断

- 结构化 JSON 日志，携带 `task_id`、`attempt_id`，适用时携带 `session_id`、`incarnation_id`、`env_id`、`subrun_id`、`step_id`、`call_id`、`try_no`。
- trace：`init`/`task_start` 提供父上下文；SDK 为步骤与工具调用创建子 span 并在请求中传播当前上下文；Gateway 创建 call/try span；宿主据 `step_started/finished/failed` 构建步骤 span，其余 `progress` 作为 span event。宿主权威绑定归属，不信任 trace 属性。导出（OTLP 或本地 JSONL，64 MiB × 5 轮转）队列有界、满则丢弃计数，不阻塞终止与清理。
- `agentbox inspect <task_id>`：attempt 与 outcome、退出与 OOM 诊断、环境与清理状态、checkpoint、sub-run、调用与 try 及费用、预算与配额变动、缓存来源。

### 15.1 API（`api/openapi.yaml` 为唯一契约）

| 资源 | 操作 |
|---|---|
| `/tasks` | `GET`（keyset 分页）、`POST`（`request_id`；可选 `session_id`） |

### 15.2 SSE

- `id = task_seq`；`Last-Event-ID` 续传；所有事件在 v0.2 中保留，游标不会过期。
- 游标超出最新事件或格式非法 → `400 invalid_cursor`。
- heartbeat 为注释行，每 15 s 一次，不占事件序号。
- 终态事件 `task_terminal` 后服务端关闭流；CLI 与 Vue **收到后停止重连**。

### 15.3 访问与浏览器安全

- 默认绑定 `127.0.0.1`；其他地址要求静态 Bearer token（`<data>/api.token`，0600）。远程访问要求可信 TLS 终止（可选内置 `--tls-cert/--tls-key`）。
- 校验 `Origin`/`Host` 显式允许列表，不使用通配 CORS。
- token 不出现在 URL、日志或前端构建产物中。

### 15.4 客户端

- **CLI**（参考客户端）：`task submit|watch|cancel|pause|resume|result|inspect`、`session create|wake|close`、`status`；`watch` 带退避的自动重连并按事件 ID 去重；`result` 校验下载的 sha256。
- **Vue**（M3 接回现有工作台）：服务端是状态与权限的权威，Vue 只维护交互与展示状态（分页、事件去重、连接恢复属于必要的客户端逻辑）。使用由 OpenAPI 生成的 TypeScript 类型；以 `fetch()` 读取 SSE 并自行解析、维护游标与重连（原生 `EventSource` 不能携带 Authorization）。报告 Markdown 安全渲染，禁止未清理的原始 HTML；HTML/SVG 等主动内容产物默认下载，不内联渲染。视图：任务列表、带 sub-run 泳道的事件时间线、产物与版本、预算与配额、会话状态、inspect。

### 16.1 验证分类

| 类别 | 内容 | 判定 |

| **CI** | 单元、fixtures、使用 fake upstream / fake Gateway 的故障实验、发布构建冒烟（无 `faultinject`） | 全部通过 |

| **人工/受控验收** | 真实模型研究演示、报告检查、实验记录 | 有记录 |
| **性能报告** | 原始数据、条件、样本量 | 报告完整；不等同于"达标" |

CI 环境含 PostgreSQL 与 Redis 服务容器、root、cgroup v2、user namespace；先运行 hostcheck。随机竞态测试记录 seed；关键顺序以确定性屏障覆盖，随机迭代作补充。fault hook 只在 `faultinject` 标签下编译；涉及外部事实的注入点由 fake 确认，不以 hook 名称代替。

### 16.2 降权启动验收（spike 与生产实现分别判定）

**范围**：Plan 1B spike 在 WSL2（内核 6.6.87.2、x86_64）上全部通过，记为"WSL2 指定环境实验通过"，不代表已在其他 Linux 环境或其他 CPU 架构上验证。发布门槛另行要求在明确列出的 Linux 目标环境上复验；**硬件形态（虚拟机/裸机）与 CPU 架构是两个维度**，首发支持范围为 x86_64，aarch64 只有在单独验证后才列入（4.5 的 seccomp 对 aarch64 的处理保留，但不构成支持主张）。生产启动路径以同一清单在生产实现上再次验收，另加启动成功判据（见末项）。

在 workload 内核验：

- 逐线程（`/proc/self/task/*/status`）：`CapInh`、`CapPrm`、`CapEff`、`CapBnd`、`CapAmb` 全为 0；`NoNewPrivs: 1`；`Seccomp: 2` 且 `Seccomp_filters ≥ 宿主基线 + 1`（WSL2 的 init 给每个进程预装 1 个 filter，"≥ 1"无判别力）。
- `prctl(PR_GET_SECUREBITS)` 显示预期位且已锁定。
- uid、gid、附加组符合预期。
- FD：排除检查器自身打开的 FD 后，除 0/1/2 外无继承 FD；逐个解析剩余 FD 目标，无指向宿主路径、控制 socket 或 helper 二进制的 FD。
- `clone3` 返回 `ENOSYS` 时 Python 线程与 `subprocess` 正常。
- 挂载为私有传播，旧根已脱离。
- Gateway socket 对编排环境的 uid 1000 可访问；exec 环境不可见。
- session 恢复后以保留的 UID 范围访问 workspace。
- （生产实现）启动成功判据：workload 快速退出报告为 `start_ack` + 退出状态；helper 在 execve 前失败或被 SIGKILL 报告为 `start_err`，workload 未运行；workload 与 helper 同名不影响判定。专用启动进程之外的 server 凭据（附加组）在启动前后不变。

spike 结论（最终序列、失败行为、内核版本、结果）回写 4.6。

### 16.3 不变量（`agentbox verify-invariants`）

资源类检查独立扫描实际目录、挂载、cgroup 与文件属主，不只从数据库推导。分三类：**[A] 始终成立**、**[B] 期限内成立**（超期则须有占用记录与报警）、**[Q] 静止时成立**（实验结束、清理完成后）。

| 编号 | 类别 | 不变量 |
|---|---|---|
| I1 | Q | `cleanup_state = done` 的环境不存在任何实际挂载、cgroup、listener 或目录 |
| I2 | A | 每个任务至多一个可能拥有执行树的 attempt；无法确认停止的旧环境存在时，无替代执行在运行 |
| I3 | A | 每层账本 `reserved` 等于该层 `held` reservation 之和；每笔 reservation 恰在一个桶中 |
| I4 | A | 每个任务事件 `task_seq` 连续 |
| I5 | A | 每个固定输出以正确哈希存在于 `blobs` |
| I6 | A | 每个已提交 checkpoint 的 state 与 refs 存在、完整、在授权范围内；指针未回退 |
| I7 | A | 每个任务至多一个 active 访问身份；恢复完成后旧 attempt 无法调用或提交 |
| I8 | B | 每个隔离资源都已报警 |
| I9 | A | 每个 session 至多一个存活 incarnation；frozen session 的 `quiesced` ID 等于最新已提交 session checkpoint |
| I10 | A | session 指针只在成功 task 裁决的同一事务中推进 |
| I11 | A / Q | 存活环境的 UID 范围互不相同 [A]；已归还范围不拥有任何文件或挂载 [Q] |
| I12 | A / B / Q | 已结束 attempt 不启动新 exec [A]；其 exec 环境在期限内停止并清理，否则保留占用记录并报警 [B]；清理完成后实际资源不存在 [Q] |
| I13 | A | `completed` sub-run 均出现在已提交 checkpoint 中；sub-run 终态不回退；各 sub-run 账本之和每桶不超过 task 账本 |
| I14 | A | 已记录的调用结果不改变；每个缓存来源的调用都有 `scope_blobs` 记录 |
| I15 | Q | 恢复完成后不存在没有活跃 attempt 的 `resolving` 调用 |
| I16 | A | 每个 `request_id` 恰对应一个资源 |

### 16.4 故障实验

**M1 可靠执行**

| 编号 | 注入 | 必须成立 |
|---|---|---|
| E1 | 第 2 个 checkpoint 提交后杀死 Worker | 新 attempt 从 checkpoint 2 恢复；`fault_retries_used = 1`；产物完整 |
| E2 | sim-worker 主进程超出 `memory.max`（主进程为预期受害者） | `worker_oom_likely` → 重试一次 → `failed`；无残留 cgroup |
| E3 | 子进程 OOM，Worker 主进程正常结束 | 按 Worker 结果裁决；记 `oom_observed_in_attempt`；不归因为 Worker OOM |
| E4 | 取消与 result 竞争（确定性屏障 + 1000 次随机，记录 seed） | 恰一个裁决；取消先被接受则永不 `succeeded`；无泄漏 |
| E5 | 在每个 hook 点 SIGKILL server | 按 14.2 恢复；无重复执行；孤儿回收；无误隔离 |
| E6 | 随机断开 SSE | 事件无缺失、无重复；任务不重新执行 |
| E7 | 丢弃 `checkpoint_result` | 重试或查询得到相同结果；指针不回退 |
| E8 | Store 阻塞（持锁 / 慢查询），**server 不重启** | 阻塞期间：规定时间内停止执行树、完成不依赖数据库写入的清理、保守保留容量；恢复后：由现有 actor 与 coordinator 提交保留的事实、补齐状态与事件（不重跑启动恢复），不变量通过 |
| E9 | Worker 双重 fork 并 `setsid` 长睡眠进程 | 清理等待 `populated 0`；执行树清空 |
| E10 | 产物经符号链接、`../in`、FIFO 提交，或登记后改写 | 拒绝，或已保存副本保持权威 |
| E11a | 注入 attempt 创建、控制写入的 COMMIT 响应丢失 | 按操作身份查询后无重复 attempt 或控制事件 |
| E12 | 控制事务与 Gateway 事务同时进入（屏障）；注入死锁 | 无循环等待；死锁被重试 |
| E13 | 终止 advisory lock 连接，业务连接仍存活 | 检测到失去所有权后不启动新的业务操作；在途数据库操作被取消；本地执行树停止并退出；记录检测延迟与在途事务最终结果；重启完整恢复 |
| E14 | 任务中途 PostgreSQL 不可用，**server 不重启** | `store_unavailable`；物理停止；数据库恢复后由现有所有者完成裁决与状态补齐 |
| **E15** | `POST /tasks` 响应丢失，同 `request_id` 重试；再以不同内容重试 | **只创建一个任务**；随后 `409 request_conflict` |

### 16.6 业务验收

## 20. 已知局限与信任边界

- 容器级隔离，共享宿主内核；seccomp 是适配工作负载的拒绝列表。
- API、Gateway 与特权 Runtime 共处一个进程；服务不是 rootless。
- 编排 Worker 是可信代码；其沙箱内不提供对抗恶意代码的任务隔离；释放核验不能发现进程内残留工作。
- 能访问 Gateway socket 的代码在撤销前拥有该 attempt 范围的 Gateway 能力。
- 不保证 exactly-once 外部调用或 exec；重跑的 exec 可能结果不同。
- 费用与 CPU 预留是估算，可出现赤字；`unknown` 不自动退回，不代表已确认。
- 单执行主机；advisory lock 不提供跨主机接管；锁丢失到被检测之间已在途的事务可能提交。
- workspace 不随 checkpoint 回滚；无磁盘硬配额。
- 缓存签名不保证新鲜度与可用性；跨任务共享以单租户为前提。
- 不做 blob 垃圾回收；不支持模型流式响应；不支持运行时安装软件包。
- 降权启动序列只在 16.2 列出的环境中经过验证；不提供 `/dev/shm`；性能数据只在注明条件下成立。
